### Run #278 — 2026-06-11 — Lens: Data pipeline integrity
**Scope:** Twentieth data-pipeline-integrity pass. Files read: `geointellisense-ingestion/src/broadcast.rs`, `geointellisense-ingestion/src/usgs.rs`, `geointellisense-ingestion/src/purpleair.rs`, `geointellisense-ingestion/src/aqi.rs`, `geointellisense-ingestion/src/redis_cache.rs`, `geointellisense-ingestion/src/main.rs`, `geointellisense-analytics/app/routes/epa_aqi.py`, `geointellisense-analytics/app/clients/epa_aqs.py`, `geointellisense-analytics/app/routes/water.py`, `geointellisense-analytics/app/clients/usgs_water.py`, `geointellisense-analytics/app/routes/fires.py`, `geointellisense-analytics/app/routes/airnow.py`, `geointellisense-analytics/app/routes/historical_aqi.py`. Cross-checked against Active Recommendations and archived data-pipeline runs #8, 23, 38, 53, 68, 83, 98, 113, 128, 143, 158, 173, 188, 203, 218, 233, 248, 263.

**Findings:**

- OBSERVATION: `broadcast.rs:62-74` — The PurpleAir fetch loop in `spawn_ticker` checks a Redis toggle (`is_source_enabled(conn, "purpleair")`) before fetching. At lines 69-74, when Redis is unavailable (`*guard` is `None`), the code skips the fetch and logs `tracing::debug!("Redis unavailable, skipping PurpleAir fetch")`. At the default `info` tracing level, this `debug!` message is invisible to operators. The result: whenever Redis suffers a transient restart or connection dropout, PurpleAir data stops refreshing silently, the cached readings in `cache` become stale, and the broadcast ticker at line 111 falls back to mock data (`aqi::generate_readings`) with no `warn!` or `info!` log emitted. Users see data labeled `"source": "purpleair"` in SSE events but it is actually mock data generated server-side. The fail-safe rationale in the comment ("don't burn API points") is inverted in practice — a single missed PurpleAir fetch costs far less than silently mis-labeling mock readings as live sensor data. The earthquake poller at `broadcast.rs:149-151` has the identical Redis-down skip pattern. PROPOSAL: Change both Redis-unavailable branches in `broadcast.rs:70-74` and `broadcast.rs:149-151` to default to "proceed" (remove the `else { continue; }` guard and treat an absent toggle as "enabled"), and elevate both `tracing::debug!` calls to `tracing::warn!` so operators see the Redis outage in logs — L/L effort (~4 lines; prevents silent mock-data relabeling during Redis downtime).

- OBSERVATION: `usgs.rs:107` — `fetch_recent` creates a new `reqwest::Client` on every invocation: `let client = reqwest::Client::new();`. `reqwest::Client` holds a connection pool and TLS session cache; constructing a new instance on every poll discards both and forces a fresh TCP handshake + TLS negotiation on each earthquake fetch. This is explicitly flagged as an anti-pattern in the reqwest documentation ("The `Client` holds a connection pool internally, so it is advised that you create one and reuse it"). `PurpleAirClient` at `purpleair.rs:36-47` correctly holds a `http: reqwest::Client` field and reuses it across calls — `usgs.rs` has no equivalent struct. With the default 5-minute poll interval, this creates 288 separate HTTP clients per day. PROPOSAL: Introduce a `UsgsClient` struct in `usgs.rs` mirroring the `PurpleAirClient` pattern — hold a `reqwest::Client` field, construct it once at startup, and pass the struct into `spawn_earthquake_poller`; change `fetch_recent` to accept `&self` — M/L effort (~20 lines; eliminates per-poll TCP+TLS overhead and aligns with the existing purpleair.rs pattern).

- OBSERVATION: `epa_aqi.py:48` + `epa_aqs.py:61-65,72-75` — `EpaAqsClient` is instantiated fresh on every request to `/api/epa-aqi` (`client = EpaAqsClient(...)` at `epa_aqi.py:48`). The rate-limit throttle in `_throttled_get` (`epa_aqs.py:72-75`) uses an instance variable `self._last_request: float = 0.0`, initialized to `0.0` in `__init__`. Because a new client is created per HTTP request, `_last_request` starts at `0.0` on each request — the 6-second pause is always elapsed and **never** actually enforced. Any concurrent callers can each instantiate a fresh `EpaAqsClient` and immediately fire requests, sending 6+ simultaneous calls to the EPA AQS API with no throttle delay. The EPA AQS rate limit is 10 requests/minute (docstring at `epa_aqs.py:5`); bursting 6 county requests simultaneously from one server can consume the entire quota in under 1 second. Additionally, in `epa_aqi.py:53-56`, when `county` is `None` the route sequentially `await`s each county's `get_daily_by_county` call; the 6s throttle is per-instance and ineffective, but even with correct throttling, sequential fetches for 6 counties would block the FastAPI worker for ≥36 seconds with no request-level timeout guard. PROPOSAL: Promote `EpaAqsClient` to a module-level singleton (or use an `asyncio.Lock` + class-level `_last_request`) so the throttle state persists across requests; add an explicit outer timeout for the "all counties" path — M/M effort (~15 lines; makes EPA AQS rate-limit protection effective across concurrent requests).

- OBSERVATION: `water.py:109-110` — The "check DB for recent readings" block at `water.py:86-115` wraps its `pool.fetch` call with a bare `except Exception: rows = []` (lines 109-110) that logs nothing. If the database is down, the `water_readings` table doesn't exist (e.g., a fresh deploy before migrations run), or the schema has changed, this exception is silently discarded and execution falls through to the live USGS API fetch at line 122. The fallback behavior is correct, but without any log entry, operators cannot distinguish "DB returned no recent readings (normal)" from "DB threw an exception (abnormal)" in application logs. In contrast, the companion `_persist_readings` at `water.py:300` logs `logger.error("Water persist error for %s: %s", r.site_id, e)` on every row-level failure, and `fires.py:66-67` logs `logger.error("FIRMS poll failed: %s", e)` in its poll loop. The water-current fallback is the only database access in the route layer that absorbs exceptions completely silently. PROPOSAL: Replace `except Exception: rows = []` at `water.py:109-110` with `except Exception as e: logger.warning("water DB fallback (will fetch live): %s", e); rows = []` — 1-line change that preserves the fallback behavior while making DB failures visible in logs.

**Proposed actions:**
- Change PurpleAir and earthquake poller Redis-unavailable branches in `broadcast.rs:70-74,149-151` to default to "enabled" and elevate to `tracing::warn!` — L/L effort (~4 lines; stops silent mock-data relabeling during Redis downtime)
- Introduce `UsgsClient` struct in `usgs.rs` holding a reused `reqwest::Client`, following the `purpleair.rs:36-47` pattern — M/L effort (~20 lines; eliminates per-poll TCP+TLS overhead)
- Promote `EpaAqsClient` to a module-level singleton in `epa_aqs.py` so the rate-limit throttle persists across requests; add a per-request timeout for the all-counties path — M/M effort (~15 lines; makes EPA AQS rate-limit enforcement effective)
- Add `logger.warning("water DB fallback: %s", e)` in the bare `except` at `water.py:109-110` — L/L effort (1 line; makes DB failures visible without breaking fallback)

### Run #277 — 2026-06-11 — Lens: UX / UI flaws
**Scope:** Nineteenth UX/UI-flaws pass. Files read: `ChatView.tsx`, `Sidebar.tsx`, `App.tsx`, `Header.tsx`, `contexts/UserPreferencesContext.tsx`, `SettingsView.tsx`, `components/dashboard/LiveDashboard.tsx`, `components/dashboard/widgets/AqiGaugeWidget.tsx`, `components/Toast.tsx`, `styles/theme-light.css`. Cross-checked against Active Recommendations and archived UX/UI runs #7, 22, 37, 52, 67, 82, 97, 112, 127, 142, 157, 172, 187, 202, 217, 232, 247, 262.

**Findings:**

- OBSERVATION: `ChatView.tsx:84` uses the deprecated `onKeyPress` DOM event to detect Enter key submission: `onKeyPress={(e) => e.key === 'Enter' && handleSend()}`. The `keypress` event has been deprecated by the W3C UI Events specification and is not reliably fired by all virtual keyboards, IME composition sessions (common on CJK and mobile keyboards), or browser-assistive technology combinations. Some screen-reader and on-screen keyboard implementations dispatch only `keydown` for Enter and skip `keypress` entirely. This means Enter-to-send can silently fail for a subset of users while appearing to work for desktop Chromium users. The `onKeyDown` handler is the spec-preferred replacement and behaves identically for standard Enter on all platforms. PROPOSAL: Replace `onKeyPress` with `onKeyDown` at `ChatView.tsx:84` — L/L effort (one word change: `Press` → `Down`; no logic change required).

- OBSERVATION: `Sidebar.tsx:30-35` defines the Google Maps nav item with `shortcut: 'Alt+G'`, which is interpolated into both `aria-label` (`"Google Maps (Alt+G)"`) and `title` (`"Google Maps - Alt+G"`) at lines 82 and 84. However, `App.tsx:32-86` registers only five keyboard shortcut handlers — `Alt+D`, `Alt+M`, `Alt+E`, `Alt+A`, `Alt+S` — via `useKeyboardShortcuts`. No handler for `Alt+G` is registered anywhere in the application. Pressing `Alt+G` on any page silently does nothing. Screen reader users who hear "Google Maps (Alt+G)" and attempt the shortcut, and sighted keyboard users who read the tooltip, are misled. The shortcut is advertised in accessible attributes and visible tooltips but has no implementation. PROPOSAL: Either add `{ key: 'g', altKey: true, action: () => navigate('/maps'), description: 'Go to Google Maps' }` to the shortcuts array in `App.tsx:32-86` (and add a corresponding entry to the keyboard shortcuts section in `SettingsView.tsx:1008-1022`), or remove the `shortcut: 'Alt+G'` field from `Sidebar.tsx:30-35` and remove it from the `aria-label` and `title` interpolations at lines 82 and 84 — L/L effort (~3 lines either way; removes the gap between advertised and actual keyboard behavior).

- OBSERVATION: `Header.tsx:59-60` constructs the theme-toggle button's `title` and `aria-label` using the binary expression `preferences.theme === 'dark' ? 'light' : 'dark'`. `toggleTheme` at `UserPreferencesContext.tsx:259-264` cycles themes in fixed order: dark → light → system → dark. The binary ternary maps every non-dark state (including 'light') to the label "Switch to dark mode", but when `preferences.theme === 'light'`, clicking `toggleTheme` advances to `'system'` — not to `'dark'`. A user in light mode who reads "Switch to dark mode" and clicks the button enters system mode, which may remain visually light if the OS prefers light. The button icon (MoonIcon in light mode) is consistent with the misleading label but not with the actual outcome. This creates a broken mental model for the three-way theme cycle. PROPOSAL: Replace the binary ternary at `Header.tsx:59-60` with a three-way next-theme lookup: `{ dark: 'light', light: 'system', system: 'dark' }[preferences.theme]`, so the tooltip and aria-label name the actual *next* state in the cycle — L/L effort (~2 lines; corrects the label for the light-mode and system-mode cases without changing toggle logic).

- OBSERVATION: `SettingsView.tsx:738-775` renders "High Temperature Alert" (`min={80} max={120}`) and "Low Temperature Alert" (`min={-20} max={50}`) sliders with `unit="°"` — a bare degree symbol with no F or C qualifier. These hardcoded ranges are Fahrenheit-scaled but `SettingsView` never reads `preferences.dataSettings.temperatureUnit` in those two `SettingRow` blocks. The preference value is available in the component (used for the temperature unit selector at line 609), but the alert sliders at lines 738 and 763 ignore it entirely. A user who selects Celsius in the "Data & Units" section continues to see 80°–120° for the high alert and -20°–50° for the low alert with no indication of scale. The stored threshold value (e.g., `90`) becomes semantically ambiguous — 90°F (a hot summer day) and 90°C (water near boiling) are radically different trigger conditions. No unit conversion is applied on read-back, so the alert condition is evaluated against the raw stored integer regardless of the user's unit preference. PROPOSAL: In both temperature-alert `SettingRow` entries, read `preferences.dataSettings.temperatureUnit` and (a) append 'F' or 'C' to the `unit` prop so the label becomes `°F` or `°C`, and (b) adjust `min`/`max` dynamically (high: F=80/120, C=27/49; low: F=-20/50, C=-29/10) so the slider range is always expressed in the selected scale — M/L effort (~10 lines; makes temperature alert thresholds unit-aware and eliminates ambiguous bare-degree labels).

**Proposed actions:**
- Replace `onKeyPress` with `onKeyDown` at `ChatView.tsx:84` — L/L effort (1 word; forward-compatible Enter detection across all keyboard types)
- Add `Alt+G` handler for `/maps` in `App.tsx:32-86` OR remove `shortcut: 'Alt+G'` from `Sidebar.tsx:30-35` — L/L effort (~3 lines; closes gap between advertised and actual keyboard shortcuts)
- Fix theme-toggle label at `Header.tsx:59-60` to use three-way next-theme lookup instead of binary ternary — L/L effort (~2 lines; corrects misleading "Switch to dark mode" label in light mode)
- Adjust temperature alert sliders in `SettingsView.tsx:738-775` to read `temperatureUnit` preference for label (°F/°C) and min/max range — M/L effort (~10 lines; makes thresholds unit-aware)

### Run #276 — 2026-06-11 — Lens: TS ↔ Python contract

Cross-checked against Active Recommendations and archived TS↔Python runs #6, 21, 36, 51, 66, 81, 96, 111, 126, 141, 156, 171, 186, 201, 216, 231, 246, 261.

**Findings:**

- OBSERVATION: `grounded_search.py:79` and `grounded_maps.py:86` both return `{"text": text, "groundingChunks": []}` — the `groundingChunks` field is permanently hardcoded to an empty list. The TypeScript type `GroundingChunk` (`types.ts:14-30`) models a Gemini Grounding API response shape (`web.uri`, `web.title`, `maps.placeAnswerSources`, etc.) that was declared in the frontend but never implemented in the Python backend. `aiService.ts:30` declares a return type of `{ text: string, groundingChunks: GroundingChunk[] }`, and `AnalysisView.tsx:451` conditionally renders a citation block only when `groundingChunks.length > 0`. Because both Python endpoints always return `[]`, this citation UI block (`AnalysisView.tsx:451-460`) is permanently dead code — it will never render for any user in any session. The Python backend uses Claude's native tool-calling loop for web queries rather than a grounding API, so tool-call source attribution was never ported to the response envelope. PROPOSAL: Either (a) update the Python `grounded_search` and `grounded_maps` endpoints to extract source references from Claude tool-use responses and return them as a citation list under a TypeScript-compatible key, replacing the `GroundingChunk` type with a Claude-appropriate shape; or (b) remove the dead citation block from `AnalysisView.tsx:451-460` and the `groundingChunks` state/setter as dead code. Option (b) is a 2-line fix; option (a) restores the intended UX — M/M effort for (a), L/L for (b).

- OBSERVATION: `chat.py:36` always calls `create_session()` when `req.session_id` is absent (which is every request, because `aiService.ts:16` sends `body: JSON.stringify({ message })` — never a `session_id`). The response at `chat.py:86` returns `{"text": text, "sessionId": session_id}`, but `aiService.ts:28` reads only `data.text` and discards the `sessionId`. The session management infrastructure in `claude.py:24-65` — `_sessions: dict[str, list[dict]]`, `create_session`, `get_session_history`, `append_to_session`, `reset_session`, plus the companion endpoints `/api/chat/reset` (`chat.py:95`) and `/api/chat/session` (`chat.py:105`) — is completely unreachable from the TypeScript client. Every call to `getChatResponse` creates a new session on the server and appends exactly one exchange before the session is silently abandoned; the session store fills up to the `MAX_SESSIONS = 50` LRU cap with orphaned single-turn sessions. Multi-turn conversation context — the primary purpose of the session design — is never accumulated. PROPOSAL: Thread the `sessionId` through `aiService.ts:getChatResponse` (accept and return it as an optional param), store it in React state in the calling component, and pass it on follow-up messages. No backend changes are needed. L/L effort (~5 lines across 2 files; activates existing multi-turn session management without touching Python).

- OBSERVATION: `historical_weather.py:98` returns `"totalPrecipitation": 0.0` with an inline comment `# sensor_readings doesn't have precip; placeholder`. The `HistoricalWeatherRecord` interface in `dataService.ts:70` declares `totalPrecipitation: number` and `Dashboard.tsx:217` reads `record.totalPrecipitation` to populate a precipitation chart series (`entry[\`${record.locationName}_precip\`] = record.totalPrecipitation`). When `dataService.getHistoricalWeather` successfully connects to the live analytics server and returns records, every precipitation chart bar shows exactly `0` for every month with no error thrown and no log emitted. The fallback path in `dataService.ts:383` correctly derives `totalPrecipitation: monthData.precipitation` from `dashboardData`, so charts display valid non-zero values only when the analytics server is unreachable. This creates a silent data quality inversion: the live path silently produces worse data than the fallback. There is no test or assertion that verifies `totalPrecipitation > 0` for any returned record. PROPOSAL: Short-term — filter precipitation bars at the chart layer when all values are 0 (or surface a "precipitation data unavailable" label); long-term — either add a precipitation column to `sensor_readings` fed from a weather API, or officially remove `totalPrecipitation` from the Python response and always source it from `dashboardData`. M/M effort.

- OBSERVATION: `useRealtimeAQI.ts:310-311` maps the Rust SSE `stationName` field (e.g., `"Bakersfield-California"`, `"Fresno-Garland"`) to TS city `id` and `name` via `r.stationName.split('-')[0]`, discarding the UUID `stationId` that `aqi.rs:18` serializes as `stationId` in every `aqi-update` event payload. The UUID is the canonical, stable station identifier (chosen by the Rust author precisely to avoid string fragility), but the hook ignores it entirely. The mock data path (`useRealtimeAQI.ts:79-86`) uses bare city names (`'Bakersfield'`, `'Fresno'`, etc.) as keys, which coincidentally matches the `.split('-')[0]` output today. If a second station in any city is ever added (e.g., `"Bakersfield-Downtown"` alongside `"Bakersfield-California"`), both would map to `id: "Bakersfield"` — a silent collision that would cause one station's AQI to overwrite the other's in the 3D scene and map overlay, misrepresenting data for one location without any error. PROPOSAL: Replace `r.stationName.split('-')[0]` at `useRealtimeAQI.ts:310-311` with `r.stationId` as the city `id` and use the full `r.stationName` (or a dedicated `shortName` field added to `AqiReading`) for display. L/L effort (~2 lines; uses the stable UUID already transmitted in every SSE event).

**Proposed actions:**
- Remove dead citation block from `AnalysisView.tsx:451-460` and `groundingChunks` state, OR port Claude tool-call source attribution to the Python grounded-search/maps response — L/L (cleanup) or M/M (feature restore) effort
- Thread `sessionId` through `aiService.ts:getChatResponse` and persist it in the calling component's React state — L/L effort (~5 lines; activates existing multi-turn chat without backend changes)
- Filter zero-precipitation series from Dashboard charts when all values are 0, and document `totalPrecipitation` as DB-unavailable in `historical_weather.py:98` — M/M effort
- Replace `.split('-')[0]` at `useRealtimeAQI.ts:310-311` with `r.stationId` UUID to avoid future station-name collision — L/L effort (~2 lines)
