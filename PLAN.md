- OBSERVATION: `components/MapView.tsx:42–49` defines a local `getAqiColor()` function and a local `getAqiCategory()` function at lines 51–58. Both are duplicates of `utils/colorScales.ts:getAQIColor()` (lines 39–42) and `getAQICategory()` (lines 27–34), but ALL SIX color values diverge: `MapView.tsx` uses Tailwind CSS hex colors (`#22c55e`, `#facc15`, `#f97316`, `#ef4444`, `#a855f7`, `#881337`) while `colorScales.ts` uses EPA-standard hex colors (`#00e400`, `#ffff00`, `#ff7e00`, `#ff0000`, `#8f3f97`, `#7e0023`). A third implementation in `geointellisense-ingestion/src/aqi.rs:88–97` matches the EPA colors of `colorScales.ts`, not `MapView.tsx`. This means the map markers (driven by `MapView.tsx`) display different colors than chart components and the ingestion service for the same AQI value — e.g., "Unhealthy" AQI renders as `#ef4444` on the map but `#ff0000` everywhere else. No test cross-checks the three implementations. PROPOSAL: Add a vitest unit test (e.g., `tests/aqiColors.test.ts`) that imports `getAQIColor` from `colorScales.ts`, re-implements the expected values, and asserts equality at all 6 breakpoints; simultaneously, replace the local `getAqiColor`/`getAqiCategory` in `MapView.tsx:42–58` with imports from `colorScales.ts` — L/L effort (~1 test file + 2 import replacements; eliminates color divergence and prevents future drift across the three color implementations).

- OBSERVATION: `utils/weatherUtils.ts:33–56` — `calculateSunTimes(date: Date, latitude: number)` calls `Math.acos(-Math.tan(latRad) * Math.tan(declinationRad))` at line 38. `Math.acos()` returns `NaN` whenever its argument is outside the range `[-1, 1]`, which occurs at high latitudes during summer/winter solstices (e.g., `lat = 70°N`, midsummer: `|tan(70°) * tan(23.45°)| ≈ 1.05 > 1`). When `acos` returns `NaN`, `hourAngleDeg = NaN`, `sunriseHour = NaN`, `sunsetHour = NaN`, and `formatTime(NaN)` calls `Math.floor(NaN) = NaN`, producing `"NaN:NaN NaN"` for both sunrise and sunset. The `dayLength` field becomes `NaN` as well. The function has no guard for this polar-day/polar-night case. `utils/weatherUtils.ts` has zero test coverage — no test file exists for it at all. The four exported functions (`calculateFeelsLike`, `calculateET0`, `calculateSunTimes`, `determineWeatherCondition`) are all pure functions, making them ideal candidates for unit tests that would immediately catch this NaN propagation bug. PROPOSAL: Create `tests/weatherUtils.test.ts` testing all four functions; for `calculateSunTimes`, add a clamp guard: `const cosHourAngle = Math.max(-1, Math.min(1, -Math.tan(latRad) * Math.tan(declinationRad)))` before `Math.acos()` at `weatherUtils.ts:38` — L/L effort (~30 test lines + 1 guard line; catches NaN propagation at polar latitudes and provides regression coverage for heat-index, wind-chill, and sun-time calculations).

### Run #244 — 2026-06-10 — Lens: Perf hot paths
**Scope:** Seventeenth perf-hot-paths pass. Files examined: `components/charts/AQITrendChart.tsx` (full), `components/charts/PM25TrendChart.tsx` (lines 1–20), `components/MapView.tsx` (lines 235–268), `geointellisense-ingestion/src/purpleair.rs` (lines 1–100), `geointellisense-ingestion/src/broadcast.rs` (lines 55–131), `geointellisense-analytics/app/context.py` (lines 275–390). Cross-checked against Active Recommendations and archived perf-hot-paths runs #4, 19, 34, 49, 64, 79, 94, 109, 124, 139, 154, 169, 184, 199, 214, 229.

**Findings:**

- OBSERVATION: `components/charts/AQITrendChart.tsx:20` and `components/charts/PM25TrendChart.tsx:20` (and by structure, `TemperaturePrecipitationChart.tsx` and `WeatherForecastChart.tsx`) export their components as plain `React.FC` without `React.memo()`. The parent `Dashboard.tsx` re-renders on any state change (location selection, tab switch, data refresh tick) and passes `data`, `selectedLocations`, and `comparisonColors` as props. Because these props are constructed as new array references on each Dashboard render, all four chart components re-render unconditionally. Critically, `AQITrendChart.tsx:44–53` runs `selectedLocations.map((loc, i) => <Line ... />)` on every render, creating fresh Recharts `<Line>` VDOM nodes regardless of whether the location set changed. Recharts internally re-diffs these child nodes and re-computes its internal `ComposedDataDecorator` on each pass, triggering layout/SVG recalculation. With 6 selected locations, this is 24 fresh `<Line>`/`<Bar>` element allocations per render across the four charts, each driving a Recharts reconciliation cycle. PROPOSAL: Wrap all four chart components in `React.memo()` at their export sites (`AQITrendChart.tsx:20`, `PM25TrendChart.tsx:20`, `TemperaturePrecipitationChart.tsx`, `WeatherForecastChart.tsx`) and memoize the `comparisonColors` slice passed from Dashboard with `useMemo` — L/L effort (~4 component exports + 1 useMemo; eliminates the chart reconciliation cascade on every Dashboard state change that doesn't affect chart data).

- OBSERVATION: `components/MapView.tsx:250,258` — for each AQI reading, `getAqiColor(r.aqi)` is called twice per marker in the same iteration: once at line 250 for the marker icon `fillColor` and again at line 258 inside the info window HTML string `<b style="color:${getAqiColor(r.aqi)}">`. Additionally, `r.source === 'purpleair'` is evaluated twice at line 256 (for the badge background color and for the badge text). All of this occurs inside the `for (const r of aqiData.readings)` loop at line 245, which runs on every call to the marker-rebuild effect (triggered on `aqiData`, `firesData`, `earthquakeData`, `wellsData`, `waterQualityData` changes). The `getAqiColor()` function performs at least one conditional branch per call. With 200 AQI sensors, this is 400 `getAqiColor` calls and 400 `source === 'purpleair'` evaluations where 200 of each are redundant within the same loop iteration. PROPOSAL: Inside the AQI marker loop, extract `const color = getAqiColor(r.aqi)` and `const isLive = r.source === 'purpleair'` before the Marker constructor at `MapView.tsx:245–266` (~4 variable hoists; halves the per-marker redundant function calls and makes the loop body easier to read).

- OBSERVATION: `geointellisense-analytics/app/context.py:286–310` — `_get_fire_context()` makes two sequential `await pool.fetchrow()` calls to PostgreSQL. The first (lines 287–295) performs a `COUNT(*) + SUM(CASE ... ST_Distance)` aggregate over `fire_detections` for the last 48 hours. The second (lines 302–310) immediately re-queries the same table and time window using `ORDER BY geom <-> point LIMIT 1` to find the nearest fire. Since both queries hit the same `fire_detections` rows (same 48-hour window), they constitute two separate full table scans (or index scans) on the same predicate, separated by a network round-trip. `build_context_text()` (the caller) invokes `_get_fire_context()` on every AI chat message outside the 60-second cache window. With a busy fire season (thousands of detections), two sequential PostGIS queries add 100–200ms to every AI context build. Both queries can be merged into a single CTE: `WITH recent AS (SELECT ... WHERE time > now() - interval '48 hours'), counts AS (SELECT COUNT(*) ...), nearest AS (SELECT ... ORDER BY geom <-> ... LIMIT 1) SELECT * FROM counts, nearest` — retrieving counts and the nearest fire in one round-trip. PROPOSAL: Merge the two `pool.fetchrow` calls in `context.py:286–310` into a single CTE query using `CROSS JOIN LATERAL` or a `WITH` expression — M/L effort (~20 SQL lines rewritten; eliminates one DB round-trip per AI message on every fire-context fetch, reducing latency by 50–100ms).

- OBSERVATION: `geointellisense-ingestion/src/purpleair.rs:65–74` — the nearest-station bucketing algorithm iterates every element of `stations` (M stations) for each element of `sensors` (N sensors) via Rust's `Iterator::min_by()`. For each `(sensor, station_a, station_b)` triple in the comparison, `haversine_sq()` is computed for both sides before the `partial_cmp` — i.e., `da` and `db` are computed inline in the closure (lines 69–70). With N=200 PurpleAir sensors and M=6 seeded stations, this yields `N × (M−1) = 1000` calls to `haversine_sq()` per fetch cycle (every `purpleair_secs` seconds, defaulting to 5 minutes). The `haversine_sq()` function (line 226–229 of the same file) computes `sin²(Δlat/2) + cos·cos·sin²(Δlng/2)` — several trig operations per call. While individually cheap, under production load (PurpleAir SJV bounding box can return 500–1000 sensors), this becomes `N × (M−1) = 4500–9000` trig calls per fetch. Because M (number of seeded stations) is small and fixed at startup, the O(N×M) work is avoidable: pre-computing the 6 station coordinates into a `[(lat, lng, id)]` array and replacing `min_by` with a simple indexed scan produces the same result with no algorithmic change, but enables LLVM to vectorize the inner loop. More impactful: since M=6 is fixed and stations never change during a run, the Voronoi partitions (which sensor coordinates map to which station) could be pre-computed once at startup. PROPOSAL: Pre-sort `stations` into a fixed-size array at `PurpleAirClient` construction time and replace the `min_by` closure at `purpleair.rs:66–73` with an explicit indexed `for` loop over the station array, storing the current minimum distance — L/L effort (~10 lines; LLVM-vectorizable; eliminates the closure overhead and enables future Voronoi pre-computation once sensor count scales).

**Proposed actions:**
- Wrap `AQITrendChart.tsx:20`, `PM25TrendChart.tsx:20`, `TemperaturePrecipitationChart.tsx`, `WeatherForecastChart.tsx` in `React.memo()` — L/L effort (~4 export changes; eliminates Recharts reconciliation cascade on every Dashboard re-render)
- Extract `const color = getAqiColor(r.aqi)` and `const isLive = r.source === 'purpleair'` per iteration in `MapView.tsx:245–266` marker loop — L/L effort (~4 lines; halves redundant function calls per AQI marker)

**Findings:**

- OBSERVATION: `rollup 4.53.2` (transitive dependency of `vite 6.4.1`, confirmed at `node_modules/rollup` in `package-lock.json`) is vulnerable to GHSA-mw96-cpmx-2vgc — "Rollup 4 has Arbitrary File Write via Path Traversal" (CWE-22, `npm audit` severity: high, range `>=4.0.0 <4.59.0`). The flaw allows path traversal in the rollup build output step: a malicious rollup plugin or crafted `output.file`/`output.entryFileNames` value containing `../` sequences can write files outside the configured `outDir`. In GeoIntelliSense's `vite.config.ts:18–29`, `manualChunks` defines four hardcoded chunk names (no traversal sequences), but the vulnerability is exploitable through supply-chain compromise of any rollup plugin — `@vitejs/plugin-react` (listed in `package.json:35`) could return adversarial `output.file` values during the `generateBundle` hook. In a CI/CD pipeline running `npm run build`, this could write files to arbitrary paths the Node.js process can access (e.g., overwriting deployment artifacts or container entrypoints). `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"rollup": ">=4.59.0"}` to `package.json` — L/L effort (~1 line; closes path traversal in the vite build pipeline without requiring a vite version bump).

- OBSERVATION: `shell-quote 1.8.3` (transitive dependency of `concurrently 9.2.1`, a direct `devDependency` at `package.json:38`) is vulnerable to GHSA-w7jw-789q-3m8p — "shell-quote quote() does not escape newlines in object .op values" (CWE-77, CWE-78, CVSS 8.1, range `>=1.1.0 <=1.8.3`). The `shell-quote` library is used by `concurrently` to assemble compound shell command strings from structured operator objects (e.g., `{op: '&&'}`). When an `.op` value contains a newline, `quote()` emits it unescaped, allowing `\n` to break out of the intended command and inject an arbitrary shell instruction. `concurrently` is installed but not referenced in any `package.json` script — however, its presence in `node_modules` means it is available to any lifecycle script run during `npm install` or any tool that imports it programmatically. Any concurrently invocation that passes arguments derived from environment variables or user input (common in CI wrapper scripts) is potentially injectable. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Upgrade `concurrently` to a version that depends on shell-quote >1.8.3, or add `"overrides": {"shell-quote": ">1.8.3"}` to `package.json` — L/L effort (~1 line; eliminates shell injection in the dev process runner).

- OBSERVATION: `picomatch 4.0.3` (transitive dependency of `vite 6.4.1`, `vitest 4.0.13`, and `tinyglobby`, confirmed in `package-lock.json`) is vulnerable to GHSA-c2c7-rcm5-vvqj — "Picomatch ReDoS vulnerability via extglob quantifiers" (CWE-1333, CVSS 7.5) and GHSA-3v7f-55p6-f55p — "Picomatch Method Injection via POSIX Character Classes" (CWE-1321, moderate), both fixed at `>=4.0.4`. For GHSA-c2c7-rcm5-vvqj: a crafted extglob pattern causes catastrophic backtracking in the regex picomatch generates, blocking the event loop. Picomatch is used by vite's chokidar file watcher and by `import.meta.glob()` calls; a file with a specially crafted name in the watched directory freezes the vite dev-server event loop. For GHSA-3v7f-55p6-f55p: POSIX character-class injection (`[:`) allows property-name injection leading to prototype pollution in picomatch's internal state, affecting subsequent glob matches during the test or build session. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"picomatch": ">=4.0.4"}` to `package.json` — L/L effort (~1 line; fixes both ReDoS and prototype pollution in glob matching used by vite's file watcher and vitest test discovery).

- OBSERVATION: `postcss 8.5.6` (transitive dependency of `vite 6.4.1`, confirmed in `package-lock.json`) is vulnerable to GHSA-qx2v-qp2m-jg93 — "PostCSS has XSS via Unescaped `</style>` in CSS Stringify Output" (CWE-79, CVSS 6.1, range `<8.5.10`). When PostCSS stringifies a CSS AST node whose value contains the literal string `</style>`, it is emitted unescaped. Vite uses PostCSS during `vite build` to process CSS and can inject processed results inline into `<style>` tags in the output `index.html`; `vite.config.ts:17` defines `build.rollupOptions` with CSS manualChunks and vite inlines critical CSS by default for small stylesheets. If any CSS in `styles/` ever contains `</style>` — in a comment, a CSS string value, or via a supply-chain-compromised CSS dependency — the built `index.html` would contain a prematurely closed `<style>` tag, allowing arbitrary HTML/script injection in the final production artifact. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"postcss": ">=8.5.10"}` to `package.json` — L/L effort (~1 line; prevents CSS-to-XSS via `</style>` injection in the vite-built production HTML).
