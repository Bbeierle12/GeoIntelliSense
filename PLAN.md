**Findings:**

- OBSERVATION: `AnalysisView.tsx:419–426` — The `<textarea>` used for text-prompt entry in four of the six analysis tool modes (Quick Insight, Web Search, Local Info, Deep Dive) has neither an `id` attribute nor an associated `<label>` element. The branch at line 316 renders one of two forms: when `isForecastTool` is `true`, the Predictive AQI and Weather Forecast fields are each wrapped in a `<div>` with a proper `<label htmlFor="start-date">` / `<label htmlFor="end-date">` pair; when `isForecastTool` is `false`, the code falls to `AnalysisView.tsx:419` and renders a bare `<textarea>` with only a `placeholder` prop. Placeholder text is explicitly excluded as an accessible label substitute under WCAG 2.1 Success Criterion 1.3.1 (Info and Relationships) and Success Criterion 2.4.6 (Headings and Labels) — it disappears the moment a user begins typing and is not announced when the field receives focus. Screen readers (NVDA, JAWS, VoiceOver) will announce this control as "text area" with no description of its purpose ("Enter your Quick Insight prompt:", "Enter your Web Search query:", etc.). The contrast between the labeled forecast inputs and the unlabeled text inputs is especially jarring given that the same `AnalysisView.tsx` file includes a proper `<div role="status" aria-live="polite">` for result announcements — accessibility was clearly considered for output but overlooked for input. PROPOSAL: Add `id="analysis-prompt"` to the `<textarea>` at `AnalysisView.tsx:419` and a `<label htmlFor="analysis-prompt">` immediately before it whose text uses `currentTool.name` (e.g., `Enter your ${currentTool.name} query:`) — L/L effort (~2 lines; restores screen reader input accessibility for 4 of 6 analysis tools and brings the non-forecast input path into parity with the labeled forecast inputs at `AnalysisView.tsx:319–362`).

- OBSERVATION: `Dashboard.tsx:482–498` — The `renderDateFilter()` helper renders a `<label>` at line 483 with text "Filter Date Range:" that has no `htmlFor` attribute, and neither `<input type="month">` at lines 484 and 491 has an `id` attribute. These inputs are used to filter every historical chart on the Dashboard — AQI trend, PM2.5 trend, temperature/precipitation, humidity, wind speed, UV index, and agricultural metrics — but their range boundaries are announced to screen readers only as "month spinner" and "month spinner" in sequence, with no indication of which is the start date and which is the end date. In addition, the `<span>` separator at line 490 (`-`) is not decorated with `aria-hidden="true"`, so screen readers will announce "dash" or "hyphen" between the two unlabeled inputs, adding noise without aiding comprehension. The `AnalysisView.tsx` version of the same `<input type="month">` elements at lines 339 and 353 correctly uses `<label htmlFor="start-date">` and `<label htmlFor="end-date">`, making the Dashboard implementation inconsistent with the Analysis page pattern used 15 lines later in the same codebase. PROPOSAL: Add `id="hist-start-date"` to `Dashboard.tsx:484` and `id="hist-end-date"` to `Dashboard.tsx:491`; replace the single unlabeled `<label>` at line 483 with two separate `<label htmlFor="hist-start-date">From:</label>` and `<label htmlFor="hist-end-date">To:</label>` inline with their respective inputs; add `aria-hidden="true"` to the separator `<span>` at line 490 — L/L effort (~5 line changes; fixes WCAG 1.3.1 violation on the Dashboard's most-used filter control and aligns it with the already-correct AnalysisView pattern).

- OBSERVATION: `ChatView.tsx:84` — The chat input `<input type="text">` at `ChatView.tsx:80–87` uses `onKeyPress={(e) => e.key === 'Enter' && handleSend()}` to submit a message on Enter. The `keypress` event was deprecated in the WHATWG DOM Living Standard in 2021 and is marked as deprecated in MDN. React itself logs a deprecation warning for `onKeyPress` as of React 18. Beyond the deprecation: on Android virtual keyboards (the dominant mobile input method globally), many implementations fire `keydown` and `keyup` but deliberately suppress `keypress` for IME composition inputs — this means that users on Android phones cannot send chat messages by pressing Enter; they must tap the "Send" button. Since the app's description targets San Joaquin Valley environmental monitoring (a region with high mobile usage), silent input failure on Android is a meaningful UX regression. The fix requires a one-character change: the semantically correct replacement is `onKeyDown={(e) => e.key === 'Enter' && handleSend()}`, which is standardized, not deprecated, and fires reliably across all keyboard types. PROPOSAL: Change `onKeyPress` to `onKeyDown` at `ChatView.tsx:84` — L/L effort (~1 word change; eliminates silent Enter-key submission failure on Android keyboards and removes the React 18 deprecation warning from the developer console).

- OBSERVATION: `App.tsx:98–104` — The `<main>` element in the Layout component carries `role="main"` (line 99) and `aria-label="Main content"` (line 100). Adding `role="main"` to a `<main>` element is redundant: the HTML specification and ARIA 1.1 §5.4 both state that `<main>` has an implicit ARIA role of `main`. The redundant explicit role causes NVDA on Firefox to announce "main main landmark" when the user navigates to the landmark, reading the role twice. This is a known NVDA+Firefox interaction with redundant `role` attributes documented in the Deque accessibility testing database. Additionally, the `aria-label="Main content"` is a generic non-descriptive label that adds no landmark disambiguation value: the page has exactly one `<main>` element, so there is no disambiguation needed; and the phrase "Main content" conveys nothing contextually meaningful to a screen reader user who is scanning landmarks. WCAG technique ARIA11 states that landmark region labels should uniquely describe their purpose — "Main content" fails this test. Contrast this with `App.tsx:92` (`<SkipLinks />`) and `Sidebar.tsx:65` (`aria-label="Main navigation"`), which both use meaningful labels. PROPOSAL: Remove `role="main"` from `App.tsx:99` (the attribute is implicit) and change `aria-label="Main content"` to `aria-label="Environmental monitoring data"` or remove it entirely since there is only one `<main>` landmark — L/L effort (~1–2 line changes; eliminates the NVDA+Firefox duplicate-landmark announcement and aligns with WCAG ARIA11 landmark labeling guidance).

### Run #246 — 2026-06-10 — Lens: TS ↔ Python contract
**Scope:** Nineteenth TS↔Python contract pass. Files examined: `services/aiService.ts` (full), `components/ChatView.tsx` (full), `geointellisense-analytics/app/routes/chat.py` (full), `geointellisense-analytics/app/claude.py` (lines 1–66), `geointellisense-analytics/app/routes/historical_weather.py` (full), `services/dataService.ts` (lines 60–90), `services/WeatherService.ts` (lines 98–140), `hooks/useLiveData.ts` (lines 216–229), `geointellisense-analytics/app/routes/historical_aqi.py` (lines 66–101), `data/dashboardData.ts` (lines 1–80). **Findings:**

- OBSERVATION: `aiService.ts:8–28` — `getChatResponse(message: string): Promise<string>` sends `{ message }` to `POST /api/chat` and reads only `data.text` from the response. However, `chat.py:86` returns `{ "text": text, "sessionId": session_id }`. The TypeScript function signature has no parameter for `session_id` and no way to receive it. `ChatView.tsx:41` calls `getChatResponse(input)` with only the message string — there is no state variable to hold a `sessionId` across calls. On the Python side, `claude.py:36` calls `create_session()` whenever `req.session_id is None`, generating a new UUID-keyed session dict entry every call. `claude.py:50–58` appends both the user message and AI reply to the session history for potential future turns — but since the frontend never supplies `session_id`, every subsequent chat message starts a brand-new session with zero history. The multi-turn conversation infrastructure in Python (`get_session_history`, `MAX_SESSIONS=100`, `MAX_HISTORY_PER_SESSION=50`, `reset_session`) is completely unreachable from the frontend: the AI gets no context of prior turns, cannot refer back to earlier questions, and cannot use its tool results from the prior round. Each call occupies one of the 100 LRU slots in `_sessions` and is immediately orphaned. PROPOSAL: Change `getChatResponse` signature at `aiService.ts:8` to `(message: string, sessionId?: string): Promise<{ text: string; sessionId: string }>`, add `session_id: sessionId` to the request body, and add `const [sessionId, setSessionId] = useState<string | undefined>()` to `ChatView.tsx:8` so each response's `sessionId` is stored and passed back on the next send — M/L effort (~10 lines across 2 files; restores multi-turn conversation context, enabling the AI to answer follow-up questions coherently).

- OBSERVATION: `historical_weather.py:98` — the Python `historical-weather` endpoint always returns `"totalPrecipitation": 0.0` with an inline comment `# sensor_readings doesn't have precip; placeholder`. The `sensor_readings` table schema has no precipitation column, so this is a permanent stub, not a temporary placeholder. The TypeScript interface `HistoricalWeatherRecord.totalPrecipitation: number` at `dataService.ts:66` provides no indication of this. Any component that renders `totalPrecipitation` from the real analytics API (such as `TemperaturePrecipitationChart.tsx`) will display a flat line of zeros for precipitation regardless of the date range or location selected, while the mock fallback path (`dataService.ts:383`) computes non-zero precipitation values from `dashboardData[loc].historicalWeather[].precipitation`. There is no zero-value guard, no sentinel null, and no `precipitationAvailable` flag in the response — consumers cannot distinguish "truly no rain" from "column not implemented." PROPOSAL: Change `historical_weather.py:98` to return `"totalPrecipitation": None` (Python null) so TypeScript receives `null` instead of `0`; update `HistoricalWeatherRecord.totalPrecipitation` at `dataService.ts:66` to `totalPrecipitation: number | null`; add a null guard in chart components before rendering this axis — M/L effort (~3 lines Python + 1 type change + 1 null guard; prevents silent display of misleading flat-zero precipitation and enables consumers to show a "data unavailable" placeholder instead).

- OBSERVATION: `dataService.ts:83` defines `ForecastRecord.windSpeed: number`. The only code path that creates `ForecastRecord` objects from real API data is `DataService.getWeatherForecast()` at `dataService.ts:237–269`, which calls `weatherService.getForecast()` (`WeatherService.ts:98–140`). `WeatherService.ts:103–111` fetches `/api/forecast` (nws_forecast.py) but casts the response to an anonymous interface that intentionally omits `windSpeed`, discarding the raw NWS value. Then `dataService.ts:257` hardcodes `windSpeed: 0` in every `ForecastRecord` it builds. In parallel, `useLiveData.ts:223` correctly declares `ForecastPeriod.windSpeed: string` because the NWS API returns strings like `"10 mph"` or `"5 to 15 mph"`. Two TypeScript interfaces describe the same API endpoint with incompatible `windSpeed` types (`number` vs `string`) and one of them (`ForecastRecord`) always produces `0`. Any dashboard widget or chart that uses `ForecastRecord.windSpeed` for display or analysis will see constant-zero wind speed regardless of actual conditions. `dataService.ts:83` should align with `useLiveData.ts:223`. PROPOSAL: Remove `windSpeed` from `ForecastRecord` at `dataService.ts:83` and from the hardcoded line at `dataService.ts:257`, or change its type to `string | null` and populate it from the NWS data in `WeatherService.getForecast()` — L/L effort (~3 line changes; eliminates the misleading `windSpeed: 0` and resolves the duplicate-interface divergence).

- OBSERVATION: `historical_aqi.py:84` and `historical_weather.py:78` both call `.sort(["location_name", "year", "month"])` where `month` is a Polars string column produced by `.dt.strftime("%b")` — abbreviated three-letter month names. Polars sorts strings lexicographically, so months within each year are ordered: `Apr, Aug, Dec, Feb, Jan, Jul, Jun, Mar, May, Nov, Oct, Sep` — not chronological. The TypeScript client at `dataService.ts:206` does `return await response.json() as HistoricalAQIRecord[]` and uses the server-returned order directly; no client-side sort is applied. Chart components `AQITrendChart.tsx` and `PM25TrendChart.tsx` pass this array to Recharts, which renders data points in the received array order. Result: when real data is returned from the analytics API (as opposed to mock fallback), the chart x-axis shows months in alphabetical order (e.g., `Apr → Aug → Dec → Feb → Jan → Jul → Jun → Mar → May → Nov → Oct → Sep`) making historical trend lines appear to jump forward and backward in time. The mock fallback (`dataService.ts:318–357`) returns data in the same order as `dashboardData` (chronological), so this bug is only visible when the analytics service is running with real DB data. PROPOSAL: Replace `.sort(["location_name", "year", "month"])` with `.sort(["location_name", "year"])` followed by a secondary sort by numeric month (add `pl.col("time").dt.month().alias("month_num")` before the group_by and include it in the sort) in both `historical_aqi.py:84` and `historical_weather.py:78` — L/L effort (~2 one-line sort changes; ensures chronological month ordering in real-data charts and eliminates the discrepancy with mock-data ordering).

**Proposed actions:**
- Change `getChatResponse` to accept/return `sessionId` and add `sessionId` state to `ChatView.tsx` — M/L effort (~10 lines; restores multi-turn chat context across turns)
- Return `null` for `totalPrecipitation` in `historical_weather.py:98`; update `HistoricalWeatherRecord` type to `number | null` — M/L effort (~3 lines; prevents flat-zero precipitation display in TemperaturePrecipitationChart)
- Remove or fix `ForecastRecord.windSpeed: number` at `dataService.ts:83` to align with `ForecastPeriod.windSpeed: string` — L/L effort (~3 lines; eliminates constant-zero wind speed in ForecastRecord)
- Replace alphabetical `.sort(..., "month")` with numeric month sort in `historical_aqi.py:84` and `historical_weather.py:78` — L/L effort (~2 lines; fixes scrambled month order in real-data historical charts)

PROPOSAL: Create `tests/weatherUtils.test.ts` testing all four functions; for `calculateSunTimes`, add a clamp guard: `const cosHourAngle = Math.max(-1, Math.min(1, -Math.tan(latRad) * Math.tan(declinationRad)))` before `Math.acos()` at `weatherUtils.ts:38` — L/L effort (~30 test lines + 1 guard line; catches NaN propagation at polar latitudes and provides regression coverage for heat-index, wind-chill, and sun-time calculations).
