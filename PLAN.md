**Findings:**

- OBSERVATION: `geointellisense-ingestion/src/routes/mod.rs:15` registers `POST /api/admin/cache/flush` to flush the Rust service's Redis keys under the `geointelli:ingestion:*` namespace (`redis_cache.rs:71-80`). `Caddyfile:21` routes all `/api/*` requests to `analytics:3002` via the catch-all `handle /api/*` block. There is no Caddyfile entry explicitly routing ingestion admin paths to `ingestion:3001`. As a result, every call to `POST /api/admin/cache/flush` through the gateway reaches `analytics:3002/api/admin/cache/flush`, which flushes only `geointelli:analytics:*` keys (`cache.py:80-93`). The ingestion service's `geointelli:ingestion:*` keys — specifically `:snapshot` (AQI broadcast snapshot, 120 s TTL) and `:heartbeat` (30 s TTL) — are permanently unreachable via the gateway admin endpoint. An operator flushing the cache through the API will believe the full cache is cleared when the AQI snapshot cache is untouched. Both services share the same Redis instance (`docker-compose.yml:58,96`: `redis://redis:6379`) but use distinct key prefixes, so only a service-specific scan-and-delete clears each namespace. PROPOSAL: Rename the ingestion admin endpoint to `/api/ingestion/admin/cache/flush` in `routes/mod.rs:15` and add `handle /api/ingestion/admin/* { reverse_proxy ingestion:3001 }` above the `/api/*` catch-all in `Caddyfile:20` — L/L effort (~2 lines across two files; exposes the ingestion cache-flush through the gateway and prevents silent partial-flush).

- OBSERVATION: `docker-compose.yml:110` — the `analytics` service healthcheck runs `python -c "import urllib.request; urllib.request.urlopen('http://localhost:3002/api/health')"` without a `timeout` argument to `urlopen`. Python's `urllib.request.urlopen` defaults to the global socket timeout, which is `None` (infinite) unless explicitly set. If the analytics service enters a partial-hang state (accepting the TCP connection but not sending an HTTP response), each health probe blocks indefinitely; Docker's `timeout: 5s` kills the subprocess, but the file descriptor for the socket remains open until the OS reaps the process. With `interval: 10s` and `retries: 5`, five blocked probes pile up before Docker marks the container unhealthy, consuming 5 process slots and 5 open sockets simultaneously. The ingestion healthcheck at `docker-compose.yml:68` correctly uses `curl -sf http://localhost:3001/health || exit 1`, which self-limits via curl's connect/transfer timeouts. The fix for the analytics healthcheck is trivial: change `urlopen('http://localhost:3002/api/health')` to `urlopen('http://localhost:3002/api/health', timeout=2)` — a 2-second self-imposed limit is well within the 5s Docker timeout and prevents probe accumulation. PROPOSAL: Update `docker-compose.yml:110` to add `timeout=2` to the `urlopen` call — L/L effort (1 character change; prevents socket descriptor accumulation during partial-hang conditions).

- OBSERVATION: `docker-compose.yml:119-135` — the `gateway` service (Caddy reverse proxy) has no `healthcheck` block, making it the only service in the stack without one (`db` at line 16, `redis` at line 35, `ingestion` at line 67, and `analytics` at line 109 all have healthchecks). The `gateway` is the single external entry point for all client traffic; a crashed or misconfigured Caddy instance with `restart: unless-stopped` will restart, but Docker cannot differentiate between "restarting" and "healthy and serving traffic" without a healthcheck. Additionally, `gateway` uses `depends_on: {ingestion: {condition: service_healthy}, analytics: {condition: service_healthy}}`, so it correctly waits for the two backends to be healthy before starting — but nothing ensures the gateway itself is ready before traffic is routed to it. Caddy exposes an admin API at `localhost:2019/config/` by default which returns HTTP 200 when the configuration is loaded; using this as the probe provides an accurate readiness signal. PROPOSAL: Add a `healthcheck` block to the `gateway` service with `test: ["CMD-SHELL", "wget -qO- http://localhost:2019/config/ > /dev/null || exit 1"]`, `interval: 10s`, `timeout: 5s`, `retries: 3`, `start_period: 10s` — L/L effort (~6 lines; gives Docker an accurate readiness signal for the gateway and completes healthcheck coverage across all 5 services).

- OBSERVATION: `geointellisense-analytics/Dockerfile:3-5` — `RUN apt-get install -y --no-install-recommends libgdal-dev` installs the GDAL development package, which includes C headers (`/usr/include/gdal/`), static libraries (`libgdal.a`, ~60 MB), and pkg-config metadata — artifacts needed only to compile C extensions against GDAL at build time. All packages in `requirements.txt` that depend on GDAL use PyPI binary wheels that bundle GDAL natively: `rasterio==1.4.*` wheels include GDAL 3.x compiled-in, and `geopandas==1.0.*` (which uses `pyogrio`) similarly ships with a bundled GDAL wheel. None of these packages compile against the system GDAL during `pip install --no-cache-dir -r requirements.txt` on `python:3.12-slim`; they unpack pre-built `.whl` files. The `libgdal-dev` installation adds approximately 100–150 MB to the final image (headers, static libs, gdal-config, and transitive dev dependencies like `libproj-dev`) with zero runtime benefit. Since the analytics Dockerfile uses a single-stage build, there is no builder/runtime separation — the dev artifacts remain in the final image shipped to production. PROPOSAL: Remove the `apt-get install libgdal-dev` line from `analytics/Dockerfile:3-5`; if any package requires a GDAL runtime shared library (`.so`) at import time, substitute `libgdal35` or `libgdal36` (runtime-only, ~20 MB); verify with a test build that `import rasterio` and `import geopandas` succeed without the dev package — L/L effort (~2 lines; reduces the analytics image by ~100–150 MB with no functional impact).

**Scope:** Nineteenth observability pass. Cross-checked against Active Recommendations and archived observability runs #10, 25, 40, 55, 70, 85, 100, 115, 130, 145, 160, 175, 190, 205, 220, 235, 250, 265.

**Findings:**

- OBSERVATION: `chat.py:88`, `deep_analysis.py:87`, `predictive_analysis.py:99`, `low_latency.py:39` — all four AI route exception handlers call `traceback.print_exc()` (Python stdlib) to emit the stack trace, bypassing the `logging` framework entirely. Each module defines a `logger = logging.getLogger(__name__)` but never calls it inside the `except` block. `traceback.print_exc()` writes directly to `sys.stderr`; in production, uvicorn routes application `logging` calls through its log handler (typically JSON to stdout), but stderr is a separate stream that may be discarded, redirected differently, or not aggregated by the same log shipper. As a result, exceptions in the four highest-cost AI routes (Sonnet chat, Opus deep-analysis, Sonnet predictive-analysis, Haiku low-latency) produce no structured log entries and cannot be monitored, filtered, or alerted on by log-based tooling. The error detail IS returned in the HTTP response body (`"details": str(e)`), but the stack trace is unreachable outside raw stderr. PROPOSAL: Replace `traceback.print_exc()` with `logger.exception("<endpoint> error")` in each of the four handlers — `logger.exception` emits the full traceback at ERROR level through the logging framework and does not require the traceback import — L/L effort (4 one-line changes; enables log-based alerting for AI route failures).

- OBSERVATION: `claude.py:271-272` — `execute_tool` (the function that runs Claude's tool calls at runtime) catches all exceptions and returns a JSON error string to Claude, but never calls `logger.warning` or `logger.error`. The module defines `logger = logging.getLogger(__name__)` at `claude.py:8`, but this logger is never used in the tool execution error path. Tool calls are the mechanism by which Claude fetches live environmental data (AQI snapshots, earthquakes, fires, water levels, NWS forecasts). When a tool call fails due to a network timeout, 5xx from a downstream API, or service unavailability, Claude receives a JSON error message and may generate a plausible-sounding but factually incorrect response using stale system-prompt data instead. The application log is completely silent about these failures, making it impossible to diagnose systematic tool failures (e.g., the AQI snapshot endpoint has been timing out for the past hour, so Claude has been answering from stale data) without correlating user-facing response quality degradation. The chat and deep-analysis loops at `chat.py:51-76` and `deep_analysis.py:46-76` may run up to 5 and 3 rounds of tool calls respectively, each silently failing. PROPOSAL: Add `logger.warning("tool %s failed (input=%s): %s", tool_name, tool_input, e)` before the `return json.dumps(...)` at `claude.py:272` — L/L effort (1 line; makes tool failures visible in application logs and enables systematic monitoring of AI data freshness).

- OBSERVATION: `middleware.py:64-75` — `check_rate_limit` returns a 429 `JSONResponse` when a client exceeds the sliding-window limit, but never emits a log entry at any level for the throttle event. `logger = logging.getLogger(__name__)` at `middleware.py:17` is defined but only called for the Redis-failure warning at line 77. As a result, operators cannot tell from application logs alone: (a) which clients or IP addresses are being rate-limited and how frequently; (b) whether the configured thresholds (`ai_chat: 20/min`, `ai_deep: 5/min`, `ai_low_latency: 30/min`) are correctly calibrated or too tight for legitimate users; (c) whether a client is systematically probing or abusing the API. The client identifier is already computed at `middleware.py:46` (`client = _client_id(request)`) and the current request count is available in `count = results[2]`, so all the information needed for a useful log entry exists at the point the 429 decision is made — it is simply never logged. Observing rate-limit events requires scraping HTTP access logs and joining on status code 429, which loses the tier and client-identity context that is available at this level. PROPOSAL: Add `logger.warning("rate_limited tier=%s client=%s count=%d limit=%d", tier, client, count, max_requests)` immediately before the `return JSONResponse(status_code=429, ...)` at `middleware.py:64` — L/L effort (1 line; makes rate-limit events observable with full context: tier, client, current count, and limit).

- OBSERVATION: `health.py:6-12` (Python) and `health.rs:11-17` (Rust) — both health endpoints return `{"status": "ok"}` unconditionally without probing actual dependency health (database pool, Redis connection). In the Python service, `database.py` and `cache.py` each hold a module-level singleton (`_pool`, `_client`) that can fail silently after startup (connection dropped, auth token rotated, DB restarted); the health route never imports or queries these. In the Rust service, `main.rs:30` creates a `PgPool` and `main.rs:33` creates a Redis connection, but `routes/health.rs:11-17` never accesses either. In a containerized deployment (Kubernetes, Docker Swarm, Docker Compose with `healthcheck`), the orchestrator uses the health endpoint to decide whether to route traffic to an instance or restart it. An instance with a severed DB connection or Redis connection still returns HTTP 200, so the orchestrator continues routing traffic to it instead of draining and replacing it. This extends incidents: during a DB failover or Redis restart, degraded instances keep serving user traffic (producing 500 errors from DB calls) instead of being automatically recycled. The fix is a shallow dependency liveness check (a single `SELECT 1` and `PING` call with a short timeout), not a deep health check. PROPOSAL: In `health.py`, import `get_pool` and `get_redis`, issue a `SELECT 1` and `PING` with `asyncio.wait_for(timeout=2.0)`, and return `{"status": "degraded", "db": False, "redis": False}` with HTTP 503 on failure; mirror the pattern in `health.rs` using sqlx's `executor.execute("SELECT 1")` — M/L effort (~20 lines across both files; makes the health endpoint an accurate dependency liveness signal for orchestrators and prevents routing to degraded instances).

**Proposed actions:**
- Replace `traceback.print_exc()` with `logger.exception(...)` in `chat.py:88`, `deep_analysis.py:87`, `predictive_analysis.py:99`, `low_latency.py:39` — L/L effort (4 one-line changes; enables log-based alerting for AI route exceptions)
- Add `logger.warning("tool %s failed: %s", tool_name, e)` at `claude.py:272` before returning the error JSON — L/L effort (1 line; makes Claude tool failures visible in application logs)
