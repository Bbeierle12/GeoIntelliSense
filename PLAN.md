### Run #259 — 2026-06-11 — Lens: Perf hot paths
**Scope:** Nineteenth perf-hot-paths pass. Cross-checked against Active Recommendations and archived perf runs #4, 19, 34, 49, 64, 79, 94, 109, 124, 139, 154, 169, 184, 199, 214, 229, 244.

**Findings:**

- OBSERVATION: `components/AirQualityMapView.tsx:267-277` — The `aqiDataPoints` memo uses `// eslint-disable-next-line react-hooks/exhaustive-deps` and lists `[useRealtimeData, realtimeAqiDataPoints.length, cityDataLen]` as deps instead of the actual `realtimeAqiDataPoints` array. On the first SSE event, `realtimeAqiDataPoints.length` transitions from 0 to 6 and the memo executes, capturing the first event's array. From that point, `.length` never changes again (the SJV city set is fixed at 6), so all subsequent SSE updates (arriving every 5 seconds) produce new `realtimeAqiDataPoints` arrays with fresh AQI values, but the memo never re-runs — it permanently returns the first event's stale data. Both `TerrainMesh` (at line 511 via `aqiDataPoints` prop) and `CrossSectionView` (at line 487) receive this frozen value. The 3D AQI overlay and cross-section view therefore display static data from initial connection, not live readings. The `eslint-disable` comment was added to avoid the lint warning about the missing dep, trading correctness for what is not even a valid performance optimization (since the memo would only be expensive if it ran, and it no longer runs). PROPOSAL: Remove the `eslint-disable` comment at `AirQualityMapView.tsx:277`; add `realtimeAqiDataPoints` as a dep; introduce a `useDebouncedValue(realtimeAqiDataPoints, 30_000)` helper that only passes through a new reference every 30 seconds — H/L effort (~10 lines across `AirQualityMapView.tsx` + a small debounce utility; restores live updating of the 3D AQI overlay while rate-limiting texture regeneration to once per 30 seconds instead of once per 5 seconds).

- OBSERVATION: `components/3d/TerrainMesh.tsx:239-241` and `components/3d/TerrainMesh.tsx:202` — Two distinct GPU memory leak paths. (1) The `aqiTexture` memo calls `createAQIOverlayTexture()` → `generateInterpolatedMatrix()` (IDW, 128×128 grid = ~98,304 arithmetic ops) synchronously on the main thread whenever `aqiData` changes. Once the stale-dep bug above is fixed and `aqiData` correctly refreshes, this blocks the React render thread for the IDW computation duration every 30–60 seconds. More critically, the old `THREE.DataTexture` returned by the previous memo invocation is never `.dispose()`d before the new one replaces it: GPU-side texture memory accumulates with each call, never freed until the browser tab closes. (2) `RegionBoundary` at line 202 inlines `new THREE.Line(geometry, new THREE.LineBasicMaterial(...))` directly in JSX. React Three Fiber's `<primitive object={…}>` does not participate in R3F's reconciler cleanup — when `RegionBoundary` re-renders or unmounts, the old `THREE.Line` and its `LineBasicMaterial` are never `.dispose()`d. Since `RegionBoundary` is re-mounted each time `TerrainMesh` re-renders (e.g., on layer toggle), each toggle leaks one `THREE.Line` + `THREE.LineBasicMaterial` into GPU memory. PROPOSAL: In `TerrainMesh.tsx`, add a `useEffect(() => () => aqiTexture.dispose(), [aqiTexture])` cleanup to free GPU textures; refactor `RegionBoundary` to use `useRef` for the `THREE.Line` object created once on mount (via `useMemo`) and returned via `<primitive>` without re-creating on each render — M/M effort (~20 lines; eliminates progressive GPU memory leakage in the 3D hot render path).

- OBSERVATION: `geointellisense-analytics/app/context.py:60-68` — `build_live_context()` contains the comment "Run all queries concurrently-ish (asyncpg handles connection pooling)" but then uses 7 sequential `await` calls (`_get_aqi_context`, `_get_forecast_context`, `_get_fire_context`, `_get_earthquake_context`, `_get_water_context`, `_get_enviroscreen_context`, `_get_prediction_context`). asyncpg's connection pool only helps concurrency when multiple coroutines are in flight simultaneously — it does not parallelize sequential awaits. Each DB query takes ~10–50ms. Sequential execution takes 70–350ms for context building. Since all 7 AI route handlers call `build_context_text()` → `build_live_context()` on every request (confirmed in `routes/chat.py:7`, `grounded_search.py:7`, `grounded_maps.py:7`, `deep_analysis.py:7`, `predictive_analysis.py:8`, `low_latency.py:7`, `weather_forecast.py:8`), this sequential DB round-trip is added to the latency of every AI response the user receives. `asyncio.gather()` across the 7 independent async fetchers would reduce this to the latency of the single slowest query (~10–50ms total instead of 70–350ms). PROPOSAL: Replace the 7 sequential awaits at `context.py:61-68` with `results = await asyncio.gather(_get_aqi_context(pool), _get_forecast_context(pool), ..., return_exceptions=True)` and unpack into the context dict, keeping `_get_inversion_context()` (sync) outside the gather — L/L effort (~8 lines; reduces context-building latency from sum to max of independent query times, directly improving response latency for every AI endpoint).

- OBSERVATION: `geointellisense-analytics/app/clients/airnow.py:83-103` and `105-135` — Both `get_all_sjv_current()` and `get_all_sjv_forecast()` iterate `SJV_LOCATIONS` (6 entries) with sequential `for loc in SJV_LOCATIONS: obs = await self.get_current_observations(...)` loops. The `httpx.AsyncClient` is capable of concurrent requests, but the sequential `await` inside the for loop serializes all 6 HTTP calls. Each AirNow API round-trip takes ~1–3 seconds. Total ingestion time is 6–18 seconds for current observations and another 6–18 seconds for forecasts — 12–36 seconds of sequential network I/O to populate a single cache entry. The `/api/airnow/current` and `/api/airnow/forecast` routes both have a 1-hour TTL cache (AIRNOW_TTL = 3600), but on cache miss (startup, first request after TTL, or cache flush) the user waits the full sequential time. `asyncio.gather()` with `return_exceptions=True` would fire all 6 network requests simultaneously, reducing total ingestion time to ~1–3 seconds (single-request latency) regardless of city count. PROPOSAL: In both `get_all_sjv_current()` and `get_all_sjv_forecast()`, replace the sequential for loop with `asyncio.gather(*[self.get_current_observations(loc["lat"], loc["lng"], ...) for loc in SJV_LOCATIONS], return_exceptions=True)`, then filter out exceptions (preserving the existing per-city error tolerance) — L/L effort (~15 lines across two methods; reduces AQI ingestion latency from 6–18s sequential to 1–3s parallel, directly improving cache-cold startup time and TTL-expiry refresh latency).

**Proposed actions:**
- Remove `eslint-disable-next-line react-hooks/exhaustive-deps` at `AirQualityMapView.tsx:277`; add `realtimeAqiDataPoints` dep; add a 30s debounce to rate-limit texture regeneration — H/L effort (~10 lines; restores live 3D AQI overlay updates which are currently permanently stale after first SSE event)
- Add `useEffect(() => () => aqiTexture.dispose(), [aqiTexture])` in `TerrainMesh.tsx`; refactor `RegionBoundary` to create the `THREE.Line` once via `useMemo` not inline in JSX — M/M effort (~20 lines; eliminates GPU texture and geometry memory leaks)
- Replace 7 sequential `await` calls in `context.py:61-68` with `asyncio.gather()` — L/L effort (~8 lines; cuts AI response latency by 60–85ms per request)

### Run #258 — 2026-06-11 — Lens: Dependency health
**Scope:** Eighteenth dependency-health pass. Tools used: `npm audit --json`, `package-lock.json` inspection, `package.json` review, `vite.config.ts` review. **Findings:**

- OBSERVATION: `node_modules/shell-quote@1.8.3` (devDependency of `concurrently@9.2.1`, declared at `package.json:devDependencies.concurrently:"^9.1.2"`) — GHSA-w7jw-789q-3m8p, **critical** severity. `shell-quote`'s `quote()` function does not escape newline characters (`\n`) in object `.op` values. An attacker who controls a string passed to `concurrently`'s shell-quoting path can inject a newline and have the text after it interpreted as a separate shell command by the underlying shell. While `concurrently` is a devDependency used only for parallel script execution (e.g., running the Vite dev server and the analytics backend simultaneously via `npm run dev`), any CI pipeline or developer machine that executes concurrently with environment variables or arguments sourced from untrusted input is exposed. The installed version `1.8.3` is the last vulnerable version in the range `>=1.1.0 <=1.8.3`; the fix requires `shell-quote >=1.9.0`. Running `npm update concurrently` to pull a version of concurrently whose dependency tree includes `shell-quote >=1.9.0` resolves the transitive exposure. PROPOSAL: Run `npm update concurrently` to pull a fixed concurrently that depends on `shell-quote >=1.9.0`; commit the updated `package-lock.json` — L/L effort (~0 code change, one npm command; eliminates critical GHSA-w7jw-789q-3m8p shell-injection vector in the dev script runner).

- OBSERVATION: `node_modules/rollup@4.53.2` (dependency of `vite@6.4.1`, resolved transitively from `package.json:devDependencies.vite:"^6.2.0"`) — GHSA-mw96-cpmx-2vgc, **high** severity. Rollup 4.x in range `>=4.0.0 <4.59.0` has an Arbitrary File Write via Path Traversal in its plugin API: a crafted plugin output path can escape the intended output directory and write to arbitrary locations on the filesystem during `npm run build`. In a CI/CD pipeline (including the Docker build referenced in `geointellisense-analytics/Dockerfile`), this means a malicious or compromised rollup plugin — or crafted build input — could overwrite production artifacts, environment config files, or Docker layer contents during the frontend build step. The installed `rollup@4.53.2` is within the vulnerable range. This finding is distinct from and additive to the two existing vite CVEs in Active Recommendations (#8 — GHSA-p9ff-h696-f583 and GHSA-4w7w-66w2-5vf9); upgrading `vite` to `>=6.5.0` resolves all three simultaneously by pulling `rollup >=4.59.0`. PROPOSAL: Upgrade `vite` in `package.json:devDependencies` from `"^6.2.0"` to `"^6.5.0"` — L/L effort (~1 line in `package.json`; eliminates arbitrary-file-write risk in production builds via rollup GHSA-mw96-cpmx-2vgc, along with existing vite path-traversal CVEs from Active #8).

- OBSERVATION: `node_modules/picomatch@4.0.3` (transitive dependency of `vite@6.4.1`, `vitest@4.0.13`, and `tinyglobby`, each requiring `picomatch ^4.0.2` or `^4.0.3`) — GHSA-c2c7-rcm5-vvqj (**high**, CVSS 7.5, ReDoS via extglob quantifiers) + GHSA-3v7f-55p6-f55p (**moderate**, method injection via POSIX character classes causing incorrect glob matching). The ReDoS advisory: `picomatch`'s extglob quantifier parser (`+(...)`, `*(...)`, `@(...)`) contains a polynomial-time backtracking regex; a crafted glob pattern or file path with deeply nested extglob constructs causes the regex engine to hang indefinitely. In Vite's dev server, file-system watch events pass asset paths through `picomatch` for HMR routing; in Vitest, test file discovery uses `picomatch` for include/exclude pattern matching (`test: { include: [...] }` in `vite.config.ts:34`). A crafted file path in the project (e.g., an adversarially named asset or fixture file) can cause Vite's watcher or Vitest's runner to hang the CI pipeline. The installed `4.0.3` is the last vulnerable version; the fix is `>=4.0.4`. Upgrading `vite` to `>=6.5.0` and `vitest`/`@vitest/ui`/`@vitest/coverage-v8` to `>=4.1.0` (both already in Active Recommendations #6 and #8) resolves the picomatch ReDoS transitively at no additional cost. PROPOSAL: The picomatch ReDoS is fully resolved by the upgrades already proposed in Active Recommendations #6 (vitest ≥4.1.0) and #8 (vite ≥6.5.0) — no separate fix required; flagged here to document that the CI pipeline hang risk is an additional consequence of the pending dependency upgrades.

- OBSERVATION: `package.json:10` — `"@googlemaps/markerclusterer": "latest"` is the only production dependency in `package.json` pinned to the `latest` dist-tag rather than a semver constraint. Every other production dependency uses a caret range (e.g., `"react": "^19.2.0"`, `"recharts": "^3.3.0"`). The `latest` dist-tag is a mutable server-side pointer on the npm registry: any time the `@googlemaps/markerclusterer` maintainers (or an attacker who compromises their npm account) publish a new version and tag it `latest`, all subsequent `npm install` executions — including Docker builds, CI pipelines, Vercel/cloud deployments, and new developer setups — will silently resolve to that version with no semver guard. The currently resolved version is `2.6.2` (visible in `package-lock.json`), but the `package.json` declaration provides no lower or upper bound to constrain a future install. The `markerclusterer` library is rendered directly in the browser map view (`AirQualityMapView.tsx`) and handles all city marker clustering; a malicious version could exfiltrate the Google Maps API key visible in the DOM, hijack map click events, or execute arbitrary JavaScript in every user's browser session. PROPOSAL: Change `package.json:10` from `"@googlemaps/markerclusterer": "latest"` to `"@googlemaps/markerclusterer": "^2.6.2"` — L/L effort (one-character change in `package.json`; pins the map clustering library to the current known-good major version, preventing silent supply-chain substitution on future installs).

**Proposed actions:**

**Findings:**

- OBSERVATION: `hooks/useRealtimeAQI.ts:8` — The hook imports a domain type directly from a component: `import type { CityData } from '../components/3d/CityMarkers';`. `CityData` is defined as an interface at `components/3d/CityMarkers.tsx:20` alongside JSX rendering logic for the 3D city marker component. In a clean layered architecture, hooks are below components — hooks should not import anything from the `components/` tree. This upward dependency creates a bidirectional coupling: any refactor of `CityMarkers.tsx` (e.g., renaming or restructuring `CityData` as the 3D visualization evolves) propagates a breaking change into `useRealtimeAQI.ts`, which in turn can break every consumer of that hook. Because `CityData` (`{ id, name, lat, lng, aqi, category, pm25, temperature, humidity }`) is a pure domain-data interface with no JSX or visual dependencies, there is no technical reason for it to live inside a component file. PROPOSAL: Move the `CityData` interface from `components/3d/CityMarkers.tsx:20` to `types.ts` (which is already the designated home for shared domain types in this repo); update `useRealtimeAQI.ts:8` to `import type { CityData } from '../types'` and update the import inside `CityMarkers.tsx` similarly — L/L effort (~5 line change across 2 files; breaks the upward hook→component dependency, makes `CityData` a stable shared contract not coupled to the 3D visualization layer).

- OBSERVATION: `geointellisense-analytics/app/claude.py:103,116` and `geointellisense-analytics/app/routes/chat.py:7`, `grounded_search.py:7`, `grounded_maps.py:7`, `deep_analysis.py:7`, `predictive_analysis.py:8`, `low_latency.py:7`, `weather_forecast.py:8` — A logical circular dependency exists between `claude.py` and the route layer. Seven route files import from `claude.py` (e.g., `from app.claude import get_client, CHAT_SYSTEM, TOOLS, execute_tool`) making it the shared AI orchestration module. However, `claude.py` itself lazy-imports from a route module at lines 103 and 116: `from app.routes.fires import get_current_smoke_context`. The lazy import avoids Python's circular import error at module load time, but the logical cycle (routes → claude.py → routes.fires) persists. Concretely: if `fires.py` is renamed, split, or its `get_current_smoke_context()` function is moved to a background task, `claude.py`'s runtime import silently fails with an `ImportError` at the moment an AI tool call tries to include smoke context — an error that would not be caught by static analysis or tests that don't exercise that specific branch. The function `get_current_smoke_context()` at `fires.py:25` reads module-level state (`_smoke_context`) set by the route's polling loop, meaning `claude.py` is coupled to both the specific route module and its internal polling architecture. PROPOSAL: Extract a `geointellisense-analytics/app/stores/context_store.py` module with a simple `ContextStore` class holding `smoke_context`, `inversion_context`, and other live state fields; have `fires.py`'s polling loop call `context_store.set_smoke(...)` and have `claude.py` import from `context_store` instead of from `routes.fires` — M/M effort (~30 lines across new `context_store.py` + `fires.py` + `claude.py`; eliminates the logical cycle, decouples AI orchestration from route internals, makes polling state refactoring safe).

- OBSERVATION: `geointellisense-analytics/app/context.py:323,471` — The context builder (a utility module that constructs the live-data paragraph injected into Claude's system prompt) also lazy-imports from route modules: `from app.routes.fires import get_current_smoke_context` at line 323 and `from app.routes.inversion import get_current_inversion` at line 471. This means two non-route modules (`claude.py` and `context.py`) both reach into the `routes/` layer to read polling state. The pattern forces route modules to serve two distinct roles simultaneously: (1) HTTP request handlers via FastAPI routers and (2) live-state registries with module-level state accessors (`get_current_smoke_context`, `get_current_inversion`) exposed as non-HTTP exports. Any developer working on a route file must be aware that its internal polling state is consumed by external callers — a responsibility invisible from the route file itself and undocumented in any interface. The direction inversion is architecturally significant: utilities that aggregate data (context.py) depend on specific route implementations, so adding a new data source to the live context (e.g., traffic, pollen) requires modifying `context.py` to lazy-import from yet another route file, spreading the coupling further with each addition. PROPOSAL: Apply the same `ContextStore` fix as Finding 2: `fires.py` and `inversion.py` write to `context_store` on each poll cycle; `context.py` reads from `context_store` instead of lazy-importing route modules — M/M effort (covered by the same `context_store.py` module; eliminates both upward dependencies from utility layer to routes, makes adding new live-data sources a single-file change in `context_store.py`).

The type safety run #256 documented that this data flows through an `any`-typed pipeline; the module boundary problem compounds that risk — any structural change to `dashboardData` silently propagates to 7 consumer files. PROPOSAL: Move `LocationKey` and location constants (`locations`, `cityLocations`) to `types.ts` so they are importable without depending on the data module; expose `dashboardData` access only through `dataService.ts` (which already has the fallback logic) — M/M effort (~20 lines: type moves to `types.ts`, component imports updated; reduces the blast radius of `dashboardData` structure changes from 7 files to 1).
