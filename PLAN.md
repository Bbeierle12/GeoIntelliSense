### Run #256 — 2026-06-10 — Lens: Type safety
**Scope:** Eighteenth type-safety pass. Files examined: `components/charts/AQITrendChart.tsx`, `components/charts/PM25TrendChart.tsx`, `components/charts/WeatherForecastChart.tsx`, `components/charts/TemperaturePrecipitationChart.tsx`, `hooks/useDashboardData.ts`, `services/dataService.ts`, `services/WeatherService.ts`, `components/AccessibleChart.tsx`. Grep for `: any`, `as any`, `Record<string, any>`, `response.json() as`, `JSON.parse.*as` across all `.ts` and `.tsx` files. Cross-checked against Active Recommendations and archived type-safety runs #1, 16, 31, 46, 61, 76, 91, 106, 121, 136, 151, 166, 181, 196, 211, 226, 241.

**Findings:**

- OBSERVATION: `components/charts/AQITrendChart.tsx:15`, `components/charts/PM25TrendChart.tsx:15`, `components/charts/WeatherForecastChart.tsx:14`, `components/charts/TemperaturePrecipitationChart.tsx:15` — All four Recharts wrapper components in `components/charts/` declare their `data` prop as `any[]` in their props interfaces. Each component uses `<Line dataKey="…">` or `<Bar dataKey="…">` with hardcoded string literals. Because `data` is `any[]`, TypeScript cannot verify at compile time that those `dataKey` strings correspond to actual properties on the data objects. The data flowing into these charts is constructed via the `result: any[]` / `entry: any` pattern in `useDashboardData.ts` (lines 197–199, 241–243, 285–287, 330–332), which also loses all type information. The combined effect is a fully `any`-typed pipeline from data construction through to chart rendering: if a field name in the data builder is renamed (e.g., `${loc}_aqi` → `${loc}_aqiValue`), the chart silently renders an empty series at runtime with no compile-time error. PROPOSAL: Define a concrete row type for each chart (e.g., `type AQIChartRow = { month: string } & { [K: string]: number }`) and replace `data: any[]` with the concrete type in each chart's props interface; similarly replace `result: any[]` / `entry: any` in `useDashboardData.ts` with the same concrete row type — L/L effort (~20 lines across 4 chart files + `useDashboardData.ts`; enables compile-time detection of field-name mismatches between data builders and chart `dataKey` strings).

- OBSERVATION: `hooks/useDashboardData.ts:179,223,267,311` — Four parallel data-aggregation `useMemo` blocks (humidity trends, wind speed trends, AQI monthly means, temperature monthly means) each iterate `locEntry.dailyForecast.forEach((day: any) => {…})`. The `dailyForecast` property on each location entry has a structurally defined shape in the dashboard data (it comes from typed source data in `data/`), but the forEach callback parameter is explicitly typed as `any`, bypassing field-level type checking inside the entire callback. Immediately after each forEach, results are accumulated into `const result: any[]` / `const entry: any = { month }` (lines 197–199, 241–243, 285–287, 330–332) — four repetitions of the same `any`-chain pattern in one file. If `dailyForecast` items' fields are renamed (e.g., `day.humidity` → `day.relativeHumidity`), each callback silently reads `undefined` and produces NaN chart data with no compile-time warning. PROPOSAL: Look up the inferred type of `locEntry.dailyForecast[number]` (inferrable from the typed `dashboardData` structure in `data/`) and replace each `(day: any)` with the concrete inferred type; replace each `result: any[]` + `entry: any` with a typed row interface — L/L effort (~8 targeted substitutions in `useDashboardData.ts`; eliminates 8 `any` usages in one file, closes the channel through which dashboard data field renames produce silent NaN chart data).

- OBSERVATION: `services/dataService.ts:206,228` and `services/WeatherService.ts:103` — Three `response.json() as T` casts are silently unsound: `response.json()` is typed `Promise<any>` in the Fetch API's `lib.dom.d.ts`. Casting `any → ConcreteType` with `as` does not constitute type narrowing — TypeScript accepts it unconditionally regardless of actual runtime shape, because `any` is both a top and bottom type. Concretely: if the analytics service at `GET /historical-aqi` renames `aqi` to `aqiValue`, `dataService.ts:206`'s cast (`await response.json() as HistoricalAQIRecord[]`) still compiles, and all downstream code reading `.aqi` receives `undefined` silently. The same applies to `GET /historical-weather` at `dataService.ts:228` and the forecast response at `WeatherService.ts:103`. This pattern also directly amplifies the TS ↔ Python contract drift risk that prior audit runs have documented: the TypeScript side has no guard that would fire when the Python analytics response shape diverges. PROPOSAL: Treat `response.json()` as `unknown` (via `const raw: unknown = await response.json()`) and add minimal type guards or Zod/Valibot schema parse at each call site in `dataService.ts:206,228` and `WeatherService.ts:103`; throw an explicit error if validation fails — M/M effort (~15 lines across the 3 call sites plus 2–3 schema definitions; converts silent `undefined` field-access bugs into explicit boundary errors, provides a type-safety backstop for TS ↔ Python schema drift).

- OBSERVATION: `components/AccessibleChart.tsx:66,79` — The `AccessibleChart` component provides a screen-reader-friendly data table alternative for all dashboard charts. Its public props interface contains two `any`-typed entries: `format?: (value: any) => string` (line 66, the column value formatter) and `data: Record<string, any>[]` (line 79, the table rows). The `DataTableColumn` type has a `key: string` field used at runtime as `row[column.key]` inside the table renderer. Because `data` is `Record<string, any>[]` rather than a generic parameter, TypeScript does not enforce that `DataTableColumn.key` values match actual fields of the data objects. A misspelled column key (e.g., `"pm2_5"` instead of `"pm25"`) will silently render `undefined` in accessible table cells — an invisible a11y regression that sighted users testing the visual chart would never notice. Given that `AccessibleChart` is a reusable wrapper consumed by every chart in the dashboard, this gap affects the entire accessible table surface. PROPOSAL: Make `AccessibleChart` generic over its row type: `interface AccessibleChartProps<T extends Record<string, unknown>>` with `data: T[]`, `DataTableColumn<T>` typed as `{ key: keyof T & string; … }`, and `format: (value: T[keyof T]) => string` — M/L effort (~15 lines in `AccessibleChart.tsx`; constrains column keys to actual data fields at compile time, preventing silent `undefined` cells in the accessible table for every chart in the dashboard).

**Proposed actions:**

- Replace `(day: any)` + `result: any[]` + `entry: any` patterns at `useDashboardData.ts:179,197,223,241,267,285,311,330` with inferred concrete types — L/L effort (~8 changes; closes `any`-chain for all 4 dashboard data-aggregation functions)
- Add `unknown` + type-guard or Zod parse for `response.json()` in `dataService.ts:206,228` and `WeatherService.ts:103` — M/M effort (~15 lines; converts silent schema-drift bugs into explicit boundary errors)

**Findings:**

- OBSERVATION: `geointellisense-analytics/app/routes/traffic.py:16,17` and `geointellisense-analytics/app/clients/caltrans.py:15` — The endpoint `GET /api/traffic/current` serves Annual Average Daily Traffic (AADT) data from the Caltrans ArcGIS Feature Service (`Traffic_AADT/FeatureServer/0/query`). AADT is a statistical metric published once per year by Caltrans; it represents the average number of vehicles passing a point over a full calendar year and is updated annually, not in real time or even daily. The developer comment at `traffic.py:16` explicitly acknowledges the mislabeling: `TRAFFIC_TTL = 300  # 5 minutes for "current" (AADT is static but we present it as current conditions)`. The response JSON includes `"source": "caltrans_aadt"` but no `data_vintage` or `collection_year` field, so API consumers have no programmatic way to determine which year's AADT they are receiving. The `source_toggles.py:38` UI label reads `"Caltrans traffic AADT volumes"` — which correctly uses "AADT" — but the endpoint name `/api/traffic/current` and the `TRAFFIC_TTL = 300` (implying 5-minute freshness) create a false impression of near-real-time traffic data in any dashboard widget or AI tool that calls this endpoint. PROPOSAL: Rename the endpoint to `/api/traffic/aadt`; add a `data_vintage: int` field to the response payload containing the year of the AADT dataset; update `source_toggles.py:38` description to `"Caltrans Annual Average Daily Traffic (AADT) — updated yearly, not live"`; add a tooltip or footnote in any UI widget consuming this endpoint clarifying that traffic figures are annual averages — L/L effort (~10 lines across `traffic.py`, `source_toggles.py`, and response formatter; eliminates the "current conditions" mislabeling for annual-average traffic data).

- OBSERVATION: `geointellisense-analytics/app/cache.py:106-111` and `geointellisense-analytics/app/routes/airnow.py:12,28,49` — The `cache_headers(hit: bool, ttl: int)` function at `cache.py:106-111` returns `"Cache-Control": f"public, max-age={ttl}"` for **both** cache HITs and MISSes — the same `max-age` regardless of how long the data has already been sitting in Redis. For `airnow.py` (TTL=3600s) a cache HIT response instructs the browser and any intermediate CDN to cache the response for a further 3600s from the moment of receipt. Since the data in Redis may already be up to 3599s old at the time of the HIT, worst-case data age at the browser is 3599 + 3600 = 7199 seconds (≈ 2 hours) — two full AirNow update cycles. The same doubling applies to NWS forecast (`nws_forecast.py:12` TTL=3600s): worst-case browser staleness is also 2 hours for forecast data. The HTTP specification provides the `Age` response header precisely for this scenario: setting `Age: {elapsed_redis_seconds}` on a cache HIT causes browsers and CDNs to correctly subtract elapsed time from `max-age`, preventing the double-caching window. Without `Age`, the `Cache-Control: public, max-age=3600` on a HIT response looks identical to a MISS response, so the browser treats it as freshly-fetched. PROPOSAL: Extend `cache_headers()` at `cache.py:106-111` to accept an optional `age: int = 0` parameter and include `"Age": str(age)` in the returned headers; update `get_cached()` to also return the elapsed age via `r.object(key, "idletime")` or `ttl_max - r.ttl(key)`; pass this to all `cache_headers(hit, ttl, age=elapsed)` call sites — M/L effort (~20 lines across `cache.py` and 7 route files; eliminates browser double-caching, ensures displayed AirNow/NWS data age accurately matches the `max-age` window, aligns with RFC 7234).

- OBSERVATION: `components/AirQualityMapView.tsx:177` and `hooks/useRealtimeAQI.ts:249` — The city-detail tooltip popup in `AirQualityMapView` (rendered for each city marker on hover) contains a hardcoded footer: `"Real-time data from EPA monitoring station. Interpolation model uses IDW and Kriging algorithms."` at line 177. This text is unconditional — it is shown regardless of whether the data source is the live SSE stream or the mock data generator. When the SSE server is unavailable and `fallbackToMock: true` (line 203), `useRealtimeAQI` falls back to `generateMockData()` (a random-walk synthetic generator at `useRealtimeAQI.ts:76-130`) and sets `error = 'Using simulated data (server unavailable)'` at line 249. The connection error banner at `AirQualityMapView.tsx:390-392` does surface this error text when `realtimeError && !isConnected`. However, once mock data populates `realtimeCities`, the city tooltip popup still claims "Real-time data from EPA monitoring station" — an EPA-monitoring-station provenance claim that is factually false when the source is a client-side random number generator. The `isConnected` boolean is available in the component scope (destructured at line 198) but is not passed to the city popup sub-component. PROPOSAL: Pass `isConnected` prop to the city popup sub-component; replace the hardcoded attribution line with `isConnected ? "Real-time data from EPA monitoring station. Interpolation model uses IDW and Kriging algorithms." : "Simulated data (server unavailable — reconnect to restore EPA feed)"` — L/L effort (~5 line change; removes a factually false EPA provenance claim during mock-data fallback, consistent with the error banner already shown to users).

- OBSERVATION: `components/dashboard/WidgetShell.tsx:44-46` and `hooks/useLiveData.ts:81-83` — Every dashboard widget (Active Fires, Water Levels, Earthquakes, Temperature Inversion, AQI Trend, AQI Forecast) displays a `lastUpdated` timestamp via `WidgetShell`: `{lastUpdated.toLocaleTimeString()}` at line 46. This timestamp is set by `hooks/useLiveData.ts:83`: `setLastUpdated(new Date())` — which fires whenever `fetch()` returns a 200 response. Crucially, browsers honor `Cache-Control: public, max-age=N` (returned by `cache_headers()` for all analytics responses): when the browser's HTTP cache holds a still-fresh response, `fetch()` resolves immediately from the browser cache without a network round-trip, yet `setLastUpdated(new Date())` is still called with the current wall-clock time. The widget thus displays a freshly-computed timestamp (e.g., "3:47:02 PM") that the user reads as "data received moments ago", while the actual data payload may be from a Redis entry set up to 3600s earlier, further amplified by the browser's own cache window. For `NWS_TTL=3600` endpoints, a `lastUpdated` of "3:47:02 PM" may reflect data originally fetched from NWS at as early as "1:47:02 PM" (2 hours ago). No `Age` header or data-vintage field is present in any analytics response to let the frontend compute true data age. PROPOSAL: In `cache_headers()` at `cache.py:106-111` (same fix as Finding 2 above), include `Age: {elapsed_seconds}` in all HIT responses; in `hooks/useLiveData.ts:81-83`, read the `Age` header from the response (`res.headers.get('Age')`) and set `setLastUpdated(new Date(Date.now() - parseInt(age || '0') * 1000))` — this makes the displayed timestamp reflect when the data was actually generated, not when the browser cache returned it — L/M effort (~10 lines across `cache.py` + `useLiveData.ts`; makes widget freshness timestamps accurate regardless of browser or Redis caching layer, directly addresses the live-time honesty claim for all dashboard widgets).

- OBSERVATION: `components/ChatView.tsx:6-82`, `geointellisense-analytics/app/routes/chat.py:11-13`, `geointellisense-analytics/app/claude.py:CHAT_SYSTEM` — GeoIntelliSense has a single hardcoded `CHAT_SYSTEM` prompt ("expert geospatial and environmental analyst … San Joaquin Valley") and `ChatRequest` defines only `message: str` and `session_id: str | None = None` — no audience or role field. `ChatView.tsx` has no role-selector UI. The VayuBuddy user study reported that 73% of participant feedback concerned output framing rather than data accuracy — i.e., users already trusted the data but found generic analyst framing unactionable. GeoIntelliSense currently presents all responses in a single "expert analyst" frame regardless of who is asking. PROPOSAL: Add `audience: Literal["general", "policymaker", "parent", "researcher", "journalist"] = "general"` to `ChatRequest` at `chat.py:11-13`; branch the system prompt in `chat.py` to prepend a 1-2 sentence audience instruction per role (policymaker: compliance tables; parent: plain-language child risk; journalist: chart-ready summaries); add a 5-option role dropdown to `ChatView.tsx` — M/L effort (~20 line changes across `chat.py` + `ChatView.tsx`; enables differentiated output framing per user type, competitive parity with VayuBuddy's highest-valued feature).

The companion **VayuBench** benchmark (ACM IKDD 2026, 5,000 query–code pairs across 7 query categories) quantifies LLMs on air-quality analytics tasks and shows that schema-injected, code-backed responses eliminate the category of spatial column-name hallucinations (e.g., confusing `station_name` with `city`) that occur in ~22% of direct text-generation responses. GeoIntelliSense's `grounded_search.py` has a `SEARCH_SUFFIX` prompt that asks for citations but never asks Claude to show analysis code, so the hallucination class that VayuChat specifically solves remains unchecked. PROPOSAL: Add `show_code: bool = False` to `GroundedSearchRequest` at `grounded_search.py`; when `True`, append to the system prompt: "Conclude your response with a Python code block demonstrating how this analysis could be reproduced against the air_quality dataset schema: {schema_snippet}." Add a "Show analysis code" toggle to `AnalysisView.tsx` — M/M effort (~25 line changes across `grounded_search.py` + `AnalysisView.tsx`; enables analysis auditability for power users, directly matches VayuChat's core differentiating feature and reduces spatial hallucinations in structured queries).
