**Findings:**

- OBSERVATION: `rollup 4.53.2` (transitive dependency of `vite 6.4.1`, confirmed at `node_modules/rollup` in `package-lock.json`) is vulnerable to GHSA-mw96-cpmx-2vgc — "Rollup 4 has Arbitrary File Write via Path Traversal" (CWE-22, `npm audit` severity: high, range `>=4.0.0 <4.59.0`). The flaw allows path traversal in the rollup build output step: a malicious rollup plugin or crafted `output.file`/`output.entryFileNames` value containing `../` sequences can write files outside the configured `outDir`. In GeoIntelliSense's `vite.config.ts:18–29`, `manualChunks` defines four hardcoded chunk names (no traversal sequences), but the vulnerability is exploitable through supply-chain compromise of any rollup plugin — `@vitejs/plugin-react` (listed in `package.json:35`) could return adversarial `output.file` values during the `generateBundle` hook. In a CI/CD pipeline running `npm run build`, this could write files to arbitrary paths the Node.js process can access (e.g., overwriting deployment artifacts or container entrypoints). `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"rollup": ">=4.59.0"}` to `package.json` — L/L effort (~1 line; closes path traversal in the vite build pipeline without requiring a vite version bump).

- OBSERVATION: `shell-quote 1.8.3` (transitive dependency of `concurrently 9.2.1`, a direct `devDependency` at `package.json:38`) is vulnerable to GHSA-w7jw-789q-3m8p — "shell-quote quote() does not escape newlines in object .op values" (CWE-77, CWE-78, CVSS 8.1, range `>=1.1.0 <=1.8.3`). The `shell-quote` library is used by `concurrently` to assemble compound shell command strings from structured operator objects (e.g., `{op: '&&'}`). When an `.op` value contains a newline, `quote()` emits it unescaped, allowing `\n` to break out of the intended command and inject an arbitrary shell instruction. `concurrently` is installed but not referenced in any `package.json` script — however, its presence in `node_modules` means it is available to any lifecycle script run during `npm install` or any tool that imports it programmatically. Any concurrently invocation that passes arguments derived from environment variables or user input (common in CI wrapper scripts) is potentially injectable. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Upgrade `concurrently` to a version that depends on shell-quote >1.8.3, or add `"overrides": {"shell-quote": ">1.8.3"}` to `package.json` — L/L effort (~1 line; eliminates shell injection in the dev process runner).

- OBSERVATION: `picomatch 4.0.3` (transitive dependency of `vite 6.4.1`, `vitest 4.0.13`, and `tinyglobby`, confirmed in `package-lock.json`) is vulnerable to GHSA-c2c7-rcm5-vvqj — "Picomatch ReDoS vulnerability via extglob quantifiers" (CWE-1333, CVSS 7.5) and GHSA-3v7f-55p6-f55p — "Picomatch Method Injection via POSIX Character Classes" (CWE-1321, moderate), both fixed at `>=4.0.4`. For GHSA-c2c7-rcm5-vvqj: a crafted extglob pattern causes catastrophic backtracking in the regex picomatch generates, blocking the event loop. Picomatch is used by vite's chokidar file watcher and by `import.meta.glob()` calls; a file with a specially crafted name in the watched directory freezes the vite dev-server event loop. For GHSA-3v7f-55p6-f55p: POSIX character-class injection (`[:`) allows property-name injection leading to prototype pollution in picomatch's internal state, affecting subsequent glob matches during the test or build session. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"picomatch": ">=4.0.4"}` to `package.json` — L/L effort (~1 line; fixes both ReDoS and prototype pollution in glob matching used by vite's file watcher and vitest test discovery).

- OBSERVATION: `postcss 8.5.6` (transitive dependency of `vite 6.4.1`, confirmed in `package-lock.json`) is vulnerable to GHSA-qx2v-qp2m-jg93 — "PostCSS has XSS via Unescaped `</style>` in CSS Stringify Output" (CWE-79, CVSS 6.1, range `<8.5.10`). When PostCSS stringifies a CSS AST node whose value contains the literal string `</style>`, it is emitted unescaped. Vite uses PostCSS during `vite build` to process CSS and can inject processed results inline into `<style>` tags in the output `index.html`; `vite.config.ts:17` defines `build.rollupOptions` with CSS manualChunks and vite inlines critical CSS by default for small stylesheets. If any CSS in `styles/` ever contains `</style>` — in a comment, a CSS string value, or via a supply-chain-compromised CSS dependency — the built `index.html` would contain a prematurely closed `<style>` tag, allowing arbitrary HTML/script injection in the final production artifact. `npm audit --json` confirms `fixAvailable: true`. PROPOSAL: Add `"overrides": {"postcss": ">=8.5.10"}` to `package.json` — L/L effort (~1 line; prevents CSS-to-XSS via `</style>` injection in the vite-built production HTML).

- OBSERVATION: `hooks/useRealtimeAQI.ts:8` — `import type { CityData } from '../components/3d/CityMarkers'`. The type should be defined in `types.ts` and imported by both `CityMarkers.tsx` and `useRealtimeAQI.ts`, making `CityMarkers.tsx` the consumer of the shared type rather than its accidental owner. PROPOSAL: Move `CityData` interface to `types.ts`; update `CityMarkers.tsx` and `useRealtimeAQI.ts:8` to import from `'../types'` — L/L effort (~1 interface moved + 2 import-path changes; eliminates the hook→component import inversion).

- OBSERVATION: `geointellisense-analytics/app/context.py:323` imports `get_current_smoke_context` from `app.routes.fires`; `context.py:471` imports `get_current_inversion` from `app.routes.inversion`; `claude.py:103` and `claude.py:116` each independently import `get_current_smoke_context` from `app.routes.fires` (the same deferred import repeated in two separate try/except blocks in the same file). ### Run #241 — 2026-06-10 — Lens: Type safety
**Scope:** Seventeenth type-safety pass. Full reads of: `tsconfig.json` (full), `data/dashboardData.ts` (lines 193–250), `hooks/useDashboardData.ts` (lines 170–342), `components/3d/AQI3DScene.tsx` (lines 1–80), `components/charts/AQITrendChart.tsx` (full), `components/charts/PM25TrendChart.tsx` (full), `components/charts/TemperaturePrecipitationChart.tsx` (full), `components/charts/WeatherForecastChart.tsx` (full), `components/AccessibleChart.tsx` (lines 60–90), `services/aiService.ts` (full), `hooks/useLiveData.ts` (full), `hooks/useNormalizedData.ts` (full), `hooks/useRealtimeAQI.ts` (lines 1–80, 180–365), `components/AnalysisView.tsx` (lines 248–260), `contexts/UserPreferencesContext.tsx` (lines 1–65), `types.ts` (full). Cross-checked against Active Recommendations and archived type-safety runs #1, 16, 31, 46, 61, 76, 91, 106, 121, 136, 151, 166, 181, 196, 211, 226 (one-line archive summaries) and Latest Findings runs #238–240 to confirm all findings are new.

**Findings:**

- OBSERVATION: `tsconfig.json` has no `strict` flag and no individual strict-mode flags (`noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `alwaysStrict`). TypeScript strict mode has been the recommended baseline for new projects since TypeScript 2.3 (released 2017). The practical impact on this codebase is systemic: (a) Without `noImplicitAny`, untyped variables and parameters silently acquire `any` — `const forecast = []` at `data/dashboardData.ts:196` is typed as `any[]` rather than raising a compile error, and this `any[]` propagates to all 7 `dailyForecast` fields in the `dashboardData` object, then to the `day: any` callback parameters in `useDashboardData.ts:179,223,267,311`. (b) Without `strictNullChecks`, the non-null assertion operator `!` at `useDashboardData.ts:186,230,274,318` (`monthMap.get(monthKey)!`) is vacuous — the compiler already treats `Map.get()` as returning `T` (not `T | undefined`) because it does not model nullable types, making the `!` appear protective while checking nothing. (c) Without `strictFunctionTypes`, callback parameter variance is unsound: a function typed `(value: string) => void` may be silently passed where `(value: string | number) => void` is expected, as in `AccessibleChart.tsx:66`'s `format?: (value: any) => string` pattern. The effective type safety level of the whole frontend is therefore lower than it appears from reading the TypeScript syntax. PROPOSAL: Add `"strict": true` to `tsconfig.json` compilerOptions (~1 line). This will surface compile errors that require correction — primarily adding a `DailyForecastEntry` interface to `data/dashboardData.ts:195`, changing `catch (e: any)` to `catch (e: unknown)` in `AnalysisView.tsx:255`, and adding null guards where `Map.get()` results are used without `!`; the total remediation is approximately 20 targeted annotations — L/M effort total (~1 tsconfig line + ~20 annotation fixes; the highest-leverage type safety improvement possible for the entire project as it enforces all other type checks simultaneously).

- OBSERVATION: `data/dashboardData.ts:195-196` — `generateDailyForecast(location: string, days: number)` has no explicit return type annotation and initializes `const forecast = []` without a type. Without `noImplicitAny` (confirmed absent from `tsconfig.json`), this empty array literal is typed as `any[]`. The function pushes objects with at least 25 distinct fields (`date`, `temp`, `tempMin`, `tempMax`, `humidity`, `windSpeed`, `windDirection`, `windGust`, `feelsLike`, `dewPoint`, `pressure`, `uv`, `precipProb`, `precipAmount`, `precipType`, `cloudCover`, `visibility`, `evapotranspiration`, `solarRadiation`, `aqi`, `pm25`, `sunrise`, `sunset`, `dayLength`, `condition`) — all inferred but never checked. The `any[]` return propagates to all 7 `dailyForecast` entries in `dashboardData` (Valley Average, Bakersfield, Fresno, Visalia, Merced, Modesto, Stockton), which causes `useDashboardData.ts` to need the explicit `: any` annotations on the callback parameters at lines 179 (`(day: any) => { ... day.humidity }`), 223 (`day.wind.speed`), 267 (`day.uv`), and 311 (`day.evapotranspiration`, `day.solarRadiation`). A practical consequence: if any of these field names were renamed in `generateDailyForecast` (e.g., `evapotranspiration` → `et0`) the access at `useDashboardData.ts:323` (`monthData[loc].et0Sum += day.evapotranspiration`) would silently receive `undefined`, accumulating NaN into all agricultural chart data — no compile error would occur. PROPOSAL: Define a `DailyForecastEntry` interface above `generateDailyForecast` at `data/dashboardData.ts:193` with all 25+ fields; annotate the function return type as `DailyForecastEntry[]`; remove the `(day: any)` annotations from all four `forEach` callbacks in `useDashboardData.ts:179,223,267,311` and replace with the inferred `day: DailyForecastEntry` — M/L effort (~40 interface lines + 4 annotation changes; eliminates the silent rename-bug category across the entire dashboard data pipeline and makes `day.evapotranspiration`, `day.wind.speed`, etc. statically checkable).

- OBSERVATION: `components/3d/AQI3DScene.tsx:57` — `const controlsRef = useRef<any>(null)`. The `OrbitControls` component imported at line 8 from `@react-three/drei` exposes an instance type of `OrbitControls` from the `three-stdlib` package (which `@react-three/drei` re-exports). The correct ref type annotation is `useRef<import('three-stdlib').OrbitControls>(null)`. Two problems arise from `useRef<any>`: (1) `controlsRef.current.getTarget(target)` at line 70 is completely unchecked — any typo (`controlsRef.current.getTraget(target)`) or API change in `drei`/`three-stdlib` compiles silently and produces a runtime exception inside the `useFrame` callback (which runs 60 times per second, making the error difficult to diagnose from browser logs). (2) `ref={controlsRef}` at line 79 passes `React.MutableRefObject<any>` to the `OrbitControls` JSX component, which actually expects `React.Ref<OrbitControls>` in its prop types — the type mismatch is masked by `any`, preventing TypeScript from enforcing that the ref and the component type match. Note: `@react-three/drei`'s `OrbitControls` re-exports the instance type as `import type { OrbitControls } from 'three-stdlib'`, so no new package dependency is needed. PROPOSAL: Change line 57 to `const controlsRef = useRef<import('three-stdlib').OrbitControls | null>(null)` — L/L effort (~1 line; provides full type checking on all OrbitControls method calls inside the 60fps `useFrame` callback and correctly types the ref passed to the JSX element, enabling TypeScript to catch three-stdlib API changes at compile time rather than at 60fps runtime).

- OBSERVATION: `components/AccessibleChart.tsx:66,79` — Two `any` usages in the public prop interface of a component used across the dashboard: (a) `format?: (value: any) => string` in the `DataTableColumn` interface at line 66, and (b) `data: Record<string, any>[]` in the `AccessibleChartProps` interface at line 79. For (a): the `format` function is called on each table cell value (logically `format(row[column.key])`). With `value: any`, a formatter typed as `(n: number) => n.toFixed(2)` compiles even when its column actually holds `string` values — the runtime error occurs only when users toggle to the accessible table view, in an accessibility-critical code path. For (b): `data: Record<string, any>[]` means any row shape is accepted, masking key mismatches between `columns[i].key` and the actual data rows. If a `DataTableColumn` has `key: "avgAqi"` but the actual data has `key: "aqi"`, TypeScript accepts the mismatch silently — the accessible table renders `undefined` for every AQI cell, and screen-reader users receive no AQI data. The `format?: (value: unknown) => string` fix (using `unknown` instead of `any`) forces each formatter to perform type checks or casts before use, preventing wrong-typed formatters. A generic `AccessibleChart<TRow extends Record<string, unknown>>` would further constrain `columns[i].key` to `Extract<keyof TRow, string>`, catching the `"avgAqi"` vs `"aqi"` class of bug at compile time. PROPOSAL: (a) Immediately change `(value: any) => string` to `(value: unknown) => string` at `AccessibleChart.tsx:66` (~1 line; forces type-safe formatters without changing the call signature); (b) generify the component: replace `interface AccessibleChartProps` with `interface AccessibleChartProps<TRow extends Record<string, unknown>>` and update `data: TRow[]`, `columns: DataTableColumn<TRow>[]`, and `key: Extract<keyof TRow, string>` — M/L effort total (~12 lines; makes the accessible table's column key validated against actual data shape, preventing silent accessibility regressions in the one code path most critical for users relying on screen readers).

**Proposed actions:**
- Add `"strict": true` to `tsconfig.json` compilerOptions, then fix the ~20 resulting annotation errors — L/M effort (~1 config line + ~20 targeted fixes; highest-leverage type safety improvement for the entire project; references Active Recommendations row #10)
- Define `DailyForecastEntry` interface at `data/dashboardData.ts:193` with all 25+ fields; annotate `generateDailyForecast` return type as `DailyForecastEntry[]`; remove `(day: any)` in `useDashboardData.ts:179,223,267,311` — M/L effort (~44 lines; eliminates silent field-rename bugs in the dashboard data pipeline)
- Change `AQI3DScene.tsx:57` from `useRef<any>` to `useRef<import('three-stdlib').OrbitControls | null>` — L/L effort (~1 line; type-checks 60fps useFrame OrbitControls calls)
- Change `AccessibleChart.tsx:66` `(value: any)` to `(value: unknown)` and generify the component interface to constrain `key` to `keyof TRow` — M/L effort (~12 lines; prevents silent key-mismatch bugs in the accessibility-critical table view)
