### Run #275 — 2026-06-11 — Lens: Test coverage gaps
**Scope:** Nineteenth test-coverage-gaps pass. Files read: `utils/interpolation.ts`, `utils/colorScales.ts`, `geointellisense-analytics/app/ml/aqi_model.py`, `geointellisense-ingestion/src/aqi.rs`. Compared against all prior test-coverage runs (#5, 20, 35, 50, 65, 80, 95, 110, 125, 140, 155, 170, 185, 200, 215, 230, 245, 260) to identify new findings only.

**Findings:**

- OBSERVATION: `utils/interpolation.ts:228-255` — `estimateVariogramParams` (called by `interpolateKriging:139`) computes `range: maxDist / 3` where `maxDist` is the maximum pairwise Euclidean distance among `dataPoints`. When all data points share the same lat/lng (e.g., duplicate-sensor inputs, or a single-point array passed by any caller), `maxDist` remains 0 and `range = 0`. Then `variogramFunction` at line 206 evaluates `h = distance / range = distance / 0`, yielding `Infinity`. In the spherical model branch (line 211): `1.5 * Infinity - 0.5 * Infinity^3 = Infinity - Infinity = NaN`. The Kriging matrix `K` fills with NaN, causing `solveLinearSystem` to return `null`, and `interpolateKriging` falls back to IDW (line 172). The fallback is correct, but the NaN propagation path is completely opaque and untested — a regression that removes the guard at line 172-174 would cause `generateInterpolatedGrid` and `generateInterpolatedMatrix` to silently return grids of `NaN`, corrupting every 3D heatmap and map overlay texture with no error thrown. There are zero unit tests for `interpolateKriging`, `estimateVariogramParams`, or `solveLinearSystem`. PROPOSAL: Add a guard in `estimateVariogramParams`: `if (maxDist === 0) return { sill: variance || 1, range: 1, nugget: 0 };`. Add unit tests covering: fewer-than-3 points (IDW fallback), collocated points (zero maxDist), all three variogram model branches, and a case where `solveLinearSystem` returns `null` (singular matrix) — M/L effort (~30 lines of tests; prevents silent NaN propagation into texture generation).

- OBSERVATION: `utils/colorScales.ts:143-172` — `interpolateColorStops` is the leaf function driving every AQI color in the application: it is called by `getInterpolatedAQIColor` (line 177), `createGradientTexture` (line 198), `createDataTexture` (line 236), `createVolumeTexture` (line 269), and `createAQILegendGradient` (line 314). It has zero tests. The function contains two silent failure modes: (a) `hexToRgb` at line 119 returns `{ r: 0, g: 0, b: 0 }` for any hex string that fails the regex, so a single-character typo in any `AQI_GRADIENT_STOPS` color constant (e.g., `'#00e40'` instead of `'#00e400'`) silently produces black pixels across the entire 3D scene and 2D overlay with no error thrown and no visual diff test to detect it; (b) `getAQICategory` at line 27-34, which governs the discrete category label attached to every sensor reading displayed in the UI, has no boundary tests — a refactor that changes `if (aqi <= 50)` to `if (aqi < 50)` would misclassify every reading of exactly 50 as "Moderate" rather than "Good" without any test catching it. Since `interpolateColorStops` feeds the GPU texture pipeline for the 3D pollution volume, wrong colors would manifest as globally incorrect AQI shading across all views. PROPOSAL: Add unit tests for `interpolateColorStops` covering exact stop positions, between-stop interpolation, out-of-range clamping, and single-stop arrays; add boundary tests for `getAQICategory` at 0, 50, 51, 100, 101, 150, 151, 200, 201, 300, 301; add a test that detects `hexToRgb` returning black for malformed hex — L/M effort (~25 lines of tests; safeguards the entire visualization color pipeline).

- OBSERVATION: `geointellisense-analytics/app/ml/aqi_model.py:286-292` — The confidence interval in `predict_aqi` is constructed as: call `model.staged_predict(X)` to obtain 200 cumulative ensemble predictions (one per boosting round), take `np.diff(staged[-50:])` to get the last 50 per-round incremental contributions, compute `std_estimate = np.std(increments) * sqrt(50)`, then apply `CI = predicted ± 1.96 * std_estimate`. This is statistically invalid: `staged_predict` returns cumulative sums where each increment represents a learning-rate-scaled single-tree adjustment (typically < 1 AQI unit after convergence). The standard deviation of late-stage micro-corrections scaled by `sqrt(50)` is not a standard error of the mean, a prediction interval, or any recognized confidence interval construction — it is an informal approximation that produces CI widths completely divorced from the model's actual generalization error (which is captured in `meta['mae']`). The calculation has zero tests: there is no test that asserts `result['confidenceInterval']['low'] <= result['predictedAqi'] <= result['confidenceInterval']['high']`, that the CI width is plausible relative to `meta['mae']`, or that the fallback branch at line 292 (`std_estimate = max(predicted * 0.15, 5)`) fires when `len(staged) <= 50`. Users see the CI as a trust signal for the 24-hour forecast; displaying a statistically meaningless interval undermines that trust. PROPOSAL: Replace the staged-predict heuristic with a MAE-based prediction interval — `std_estimate = meta['mae']`; `CI = [max(0, round(predicted - 1.96 * mae)), round(predicted + 1.96 * mae)]` — which is both simpler and grounded in the model's measured error; add tests asserting CI monotonicity and plausible width — M/L effort (~10 lines; replaces invalid CI with a defensible one and enables regression testing).

- OBSERVATION: `geointellisense-ingestion/src/aqi.rs:88-96,138-143` — Two untested correctness issues. First, `aqi_category` at line 88 has no Rust `#[cfg(test)]` block. The same AQI category boundaries (0/50, 51/100, 101/150, 151/200, 201/300) are independently encoded in three separate codebases: `aqi.rs:89-96`, `utils/colorScales.ts:27-34` (TypeScript), and `app/ml/aqi_model.py:371-382` (Python). Boundary drift between these three would cause inconsistent category labels between the ingestion API, frontend, and analytics API with no compile-time or test-time detection. Second, `generate_history` at line 143 selects a station's base AQI via `station_id.contains("0002")` — a string substring match on the station's UUID. The Bakersfield-California station UUID is `a1b2c3d4-0001-4000-8000-000000000002`. Any future station whose UUID contains `"0002"` in a different segment (e.g., `a1b2c3d4-0002-4000-8000-000000000099`) would be silently misidentified as the Bakersfield station, receiving a base AQI of 85 instead of the intended default 60. Both bugs are untested because `aqi.rs` has no test module. PROPOSAL: Add a `#[cfg(test)]` module in `aqi.rs` with tests for `aqi_category` boundary values (0, 50, 51, 100, 101, 150, 151, 200, 201, 300, 301, 500); replace `station_id.contains("0002")` in `generate_history:143` with a proper UUID equality check against the known Bakersfield station UUID constant — L/L effort (~20 lines; prevents cross-codebase boundary drift and fragile UUID substring matching).

### Run #274 — 2026-06-11 — Lens: Perf hot paths

**Findings:**

- OBSERVATION: `components/3d/AQI3DScene.tsx:69` — `CameraController` allocates `const target = new THREE.Vector3()` inside the `useFrame` callback. `useFrame` fires on every animation frame (up to 60 fps). When the `onCameraMove` prop is provided, this executes the allocation path on every frame, creating 60 short-lived `THREE.Vector3` heap objects per second. In a WebGL context the GC cost of frequent small allocations is amplified because the JS garbage collector must pause the main thread while the GPU is mid-frame, causing dropped frames and visual jitter. The `OrbitControls.getTarget(target)` API mutates its argument in place, so the correct approach is to allocate once via `const targetRef = useRef(new THREE.Vector3())` outside `useFrame` and pass `targetRef.current` to `getTarget` — zero heap allocation per frame. PROPOSAL: Replace the per-frame `new THREE.Vector3()` allocation in `AQI3DScene.tsx:69` with a `useRef`-held instance initialized once — L/L effort (~3 lines; eliminates 60 per-second GC-triggering allocations in the 3D scene hot path).

- OBSERVATION: `components/Dashboard.tsx:145–329` — Seven `useMemo` blocks (`mergedHistoricalAqi` at :145, `mergedHistoricalPm25` at :171, `mergedHistoricalWeather` at :197, `mergedHumidityData` at :225, `mergedWindData` at :251, `mergedUVData` at :277, `mergedAgriculturalData` at :303) all iterate `historicalAqi` or `historicalWeather` and independently call `new Date(Date.parse(record.month + " 1, 2012"))` on every element to convert the `"Jan '22"` month string to a `Date` for range comparison. When `historicalWeather` contains R rows, each of the 5 weather memos performs R independent `Date.parse()` calls — a string-tokenisation and timezone-lookup operation — on every memo invalidation triggered by `startDate`, `endDate`, or `selectedLocations` changes. With 5 weather memos and R rows, a single date-filter change causes 5×R date-parse operations. A single upstream `useMemo` that pre-processes both `historicalAqi` and `historicalWeather` into arrays of `{rDate: Date, record}` objects would reduce this to 1×R date-parse calls shared across all 7 downstream memos. PROPOSAL: Extract a shared `const parsedHistoricalWeather = useMemo(() => historicalWeather.map(r => ({ rDate: parseMonthToDate(r), record: r })), [historicalWeather])` and replace the inline `Date.parse` calls in the 5 weather memos — M/M effort (~25 lines; reduces date-parse work from 5×R to 1×R per filter interaction and standardises the month-parse logic in one place).

- OBSERVATION: `geointellisense-analytics/app/http_client.py:32–33` — every call to `fetch()` opens `async with httpx.AsyncClient(timeout=timeout) as client:` inside the retry loop. Creating an `httpx.AsyncClient` instantiates a new connection pool, and destroying it at the end of `async with` closes the pool — including any open TCP connections. Routes that call `fetch()` multiple times in a single request handler pay a full TCP handshake per call rather than reusing the pool's keep-alive connections. The most impactful consumer is `app/clients/airnow.py`, which calls `fetch()` once per SJV city (8 cities), paying 8 sequential TCP handshakes to the same `api.airnow.gov` host. The fix is a module-level singleton `AsyncClient` (or a per-host client stored in `AppState`) with a connection pool shared across all requests, using `httpx.AsyncClient(limits=httpx.Limits(max_connections=20))`. For AirNow, this reduces 8 TCP handshakes to 1 on the first request and 0 thereafter for the process lifetime. PROPOSAL: Replace the per-call `async with httpx.AsyncClient()` in `http_client.py:32–33` with a lazily-initialized module-level `_shared_client: httpx.AsyncClient` reused across calls, with graceful shutdown via a `lifespan` hook in `main.py` — M/L effort (~15 lines; eliminates per-call connection setup overhead across all 15+ API client modules).

- OBSERVATION: `hooks/useRealtimeAQI.ts:165–177` — the `addToHistory` callback performs a full array spread `[...prev, snapshot]` on every call, which copies all references in `history` (up to `maxHistorySize = 288` elements) into a new array. This runs every 5 seconds (the SSE `aqi-update` cadence). At steady state (history at capacity), each call triggers `[...prev, snapshot]` (288-element copy) followed immediately by `.slice(-288)` (another 288-element copy = 576 reference copies per 5 s, or ~115 copies/second). Each copy triggers a React state update → re-render of any component that reads `history` or `timeRange` (the `timeRange` `useMemo` at :201 depends directly on `history`). For 3D visualization components consuming `useRealtimeAQI`, this means up to 12 re-renders per minute driven by history bookkeeping rather than actual displayed-data changes. The fix is to store history in a `useRef`-held circular buffer and only update React state for values actually displayed (i.e., `timeRange` updates once per minute rather than every 5 s). PROPOSAL: Replace the `useState<HistoricalSnapshot[]>` history with a `useRef`-held circular buffer indexed by a write-pointer mod `maxHistorySize`; expose `getDataAtTime` and `timeRange` without triggering component re-renders on every append — M/M effort (~20 lines; reduces history-driven re-renders from 12/min to ~1/min and eliminates the 576-copy-per-5s allocation pattern).

**Proposed actions:**

**Findings:**

- OBSERVATION: `package.json:16` declares `"@googlemaps/markerclusterer": "latest"` — the only direct dependency that uses the `"latest"` dist-tag rather than a semver range constraint. Every other dependency (18 total) uses `^`, `~`, or a version range. The `"latest"` tag is resolved at `npm install` time to whatever the registry considers current (currently 2.6.2 per `package-lock.json`). The risk is that `package-lock.json` regeneration — triggered by any `npm install <package>`, `npm update`, or CI cache invalidation — will silently upgrade `@googlemaps/markerclusterer` to whatever is newest at that moment without any semver constraint filter. A major bump (e.g., 3.x) could silently replace the `MarkerClusterer` class interface that `AirQualityMapView.tsx` depends on, manifesting as a runtime JavaScript error rather than a compile-time or lock-file conflict. PROPOSAL: Change `package.json:16` from `"latest"` to `"^2.6.2"` (the currently resolved version) to apply the same reproducibility guarantee as all other dependencies — L/L effort (1 line; closes the floating version hole).

- OBSERVATION: `geointellisense-analytics/requirements.txt:15-18` contains four tight upper-bound constraints: `numpy>=1.26,<2.1`, `scipy>=1.13,<1.15`, `scikit-learn>=1.5,<1.7`, `joblib>=1.4,<1.5`. As of mid-2026 these packages have released versions at or beyond the specified ceilings (`numpy 2.1.x` has been superseded by `2.2+`, `scipy 1.15` was released in early 2026, `scikit-learn 1.7` is in active development). When any of these packages crosses its stated upper bound in the default pip index, a fresh `pip install -r requirements.txt` in any new environment (CI, Docker build, developer onboarding) will produce a `ResolutionImpossible` error, breaking all three environments simultaneously. The ML dependencies are consumed by `routes/predictive_analysis.py` for lightweight gradient-boosted models; the APIs used (`Pipeline`, `GradientBoostingRegressor`, `StandardScaler`) are stable and unlikely to have breaking changes in minor/patch releases. PROPOSAL: Relax the four upper bounds in `requirements.txt:15-18` to allow the current stable release family (e.g., `numpy>=1.26,<3`, `scipy>=1.13,<2`, `scikit-learn>=1.5,<2`, `joblib>=1.4,<2`) — L/L effort (~4 lines; eliminates the future `ResolutionImpossible` time-bomb while preserving intentional major-version guards).

- OBSERVATION: `geointellisense-ingestion/Cargo.toml:23` declares `rand = "0.8"` (resolved to 0.8.5 in `Cargo.lock`). The `rand` 0.9 generation was released in late 2024 and is now the actively-maintained crate line; rand 0.8.x has received no updates since. Cargo's dependency resolver will attempt to simultaneously vendor both rand 0.8 and rand 0.9 if any future crate dependency requires 0.9, increasing binary size and potentially creating duplicate `SmallRng`/`StdRng` type imports that confuse the compiler. The ingestion crate's rand usage is confined to `aqi.rs` (mock reading generation): `use rand::Rng; let mut rng = rand::thread_rng();` — the `rand::thread_rng()` API was replaced by `rand::rng()` in 0.9 while `gen_range()` remains available via the `Rng` trait. The migration is mechanical. PROPOSAL: Bump `Cargo.toml:23` to `rand = "0.9"` and update the one call site in `aqi.rs` from `rand::thread_rng()` to `rand::rng()` — L/L effort (~2 lines; keeps the ingestion crate on the maintained rand generation and prevents future dual-vendor conflicts).

- OBSERVATION: `geointellisense-analytics/requirements.txt:9` pins `anthropic==0.49.*`. The `==0.49.*` constraint (pip PEP 440 compatible-release on minor) allows only `0.49.x` patch releases and blocks all `0.50+` minor releases including any that add new API features, fix client bugs, or deprecate old patterns. The analytics server uses the Anthropic SDK across at least six route modules (`claude.py`, `chat.py`, `deep_analysis.py`, `grounded_search.py`, `low_latency.py`, `predictive_analysis.py`, `weather_forecast.py`). With `==0.49.*`, dependency conflict errors will occur if any future Python package in the analytics environment directly or transitively requires `anthropic>=0.50`. The appropriate constraint for an actively-developed SDK is `anthropic>=0.49,<1.0` (semver-conservative) or `~=0.49` (tilde-range, same as `>=0.49,<0.50`) — the current exact-minor pin is unnecessarily restrictive. PROPOSAL: Change `requirements.txt:9` from `anthropic==0.49.*` to `anthropic>=0.49,<1.0` to allow patch and minor upgrades while protecting against hypothetical major-version breaks — L/L effort (1 line; unblocks Anthropic SDK minor releases and eliminates transitive-conflict risk).
