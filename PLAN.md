**Scope:** Eighteenth observability pass. Cross-checked against Active Recommendations and archived observability runs #10, 25, 40, 55, 70, 85, 100, 115, 130, 145, 160, 175, 190, 205, 220, 235, 250.

**Findings:**

- OBSERVATION: `main.py:1-117` — Python logging is never configured; all `logger.info()` calls throughout the analytics service are silently discarded at runtime. `main.py` creates the FastAPI app without calling `logging.basicConfig()`, `logging.config.dictConfig()`, or passing `log_config` to `uvicorn.run()` at line 117. Uvicorn's default `LOGGING_CONFIG` configures only the `uvicorn`, `uvicorn.access`, and `uvicorn.error` loggers and leaves the root logger with no handlers at WARNING level. Module loggers created with `logging.getLogger(__name__)` propagate to the root logger, so all INFO-level events are unreachable: `cache.py:70,72` (`cache HIT/MISS` per request), `predict.py:33,45` (`retrain scheduler started`, `Weekly AQI model retrain complete: R²=…`), `fires.py:38,54,59` (`fire polling started`, `FIRMS poll: N detections, N new`, `Smoke context updated`), `inversion.py:31,50-55` (`Inversion detection polling started`, per-30-min-cycle inversion check). WARNING-level messages do appear via Python's lastResort handler but with no timestamp, no logger name, and no structured format — unindexable by log aggregation tools. Contrast: the Rust ingestion service explicitly calls `tracing_subscriber::fmt()...init()` at `main.rs:23-25`, producing timestamped structured output for every event. PROPOSAL: Add `logging.basicConfig(level=logging.INFO, format="%(asctime)s %(name)s %(levelname)s %(message)s")` to `main.py` before the `FastAPI(...)` call at line 60 — L/L effort (~1 line; activates all existing `logger.info()` calls throughout the analytics service — cache hit/miss, poll cycle confirmations, retrain lifecycle, and Redis retry events are immediately visible in service output).

- OBSERVATION: `middleware.py:64-75` — Rate-limit enforcement events are never logged; successful throttling and abuse patterns are invisible. When `check_rate_limit()` determines a request exceeds the tier limit (`count > max_requests` at line 64), it returns a HTTP 429 JSONResponse with `Retry-After` headers but emits no log record. The error path at line 76-78 correctly calls `logger.warning("Rate limit check failed (allowing request): %s", e)` when Redis itself fails. The result is an asymmetry: Redis outages (a recoverable infra event) are logged, but rate-limit enforcement (an intentional security control firing as designed) is invisible. An attacker sustaining 100+ req/s against `POST /api/deep-analysis` (5 req/min limit) would generate hundreds of 429 responses with zero signal in any log aggregator. A defender cannot distinguish "rate limiting is working" from "rate limiting middleware is misconfigured" from log output alone. Uvicorn's access log records HTTP status but not the rate-limit tier, the anonymized client ID (computed at `middleware.py:36-40`), or the request count — all of which are available inside `check_rate_limit` but currently discarded. PROPOSAL: Add `logger.warning("Rate limit enforced: tier=%s client=%s count=%d limit=%d", tier, client, count, max_requests)` before the `return JSONResponse(429, ...)` at `middleware.py:66` — L/L effort (~1 line; makes every rate-limit enforcement event observable, enables real-time abuse detection, and confirms the control is active during load tests or attack scenarios).

- OBSERVATION: `broadcast.rs:97-131` — The AQI broadcast ticker runs completely silently in mock-data mode and discards the SSE receiver count on every cycle. When `pa_client` is `None` (no `PURPLEAIR_API_KEY`), the PurpleAir poll task is never spawned (line 49: `if let Some(client) = pa_client`), so the PurpleAir fetch log lines at lines 87/90/91 are never reached. The broadcast ticker at lines 97-131 calls `aqi::generate_readings(&stations)` for mock data, `persist::write_readings()`, and `tx.send()` — but emits zero log output per cycle. In production, if the service is running with mock data (misconfigured key or intentional dev mode), the ticker loop is completely silent: no confirmation that ticks are firing, no confirmation that readings are being persisted, and no confirmation that SSE clients are receiving data. Additionally, `tx.send(Arc::new(readings))` at line 128 returns `Result<usize, SendError<T>>` — where `usize` is the count of SSE receivers that received the message, and `Err(SendError)` is returned when there are no active receivers — but `let _ = tx.send(...)` explicitly discards both the receiver count and the error. The `sse.rs` handler tracks `CLIENT_COUNT` atomically (line 13) and logs individual connect/disconnect events, but there is no observable aggregate receiver count per broadcast cycle. PROPOSAL: Replace `let _ = tx.send(Arc::new(readings))` with `let recv = tx.receiver_count(); if let Err(_) = tx.send(Arc::new(readings)) { tracing::debug!("No active SSE receivers"); } else { tracing::info!(readings = readings.len(), receivers = recv, "AQI broadcast tick complete"); }` at `broadcast.rs:128` — L/L effort (~4 lines; provides per-cycle confirmation that the ticker is running, exposes SSE subscriber count for capacity planning, and surfaces the case where broadcasts are occurring but no clients are connected).

- OBSERVATION: `chat.py:87-92`, `deep_analysis.py:86-94`, `grounded_search.py`, `predictive_analysis.py:98-106` — Anthropic API token usage is never logged and exceptions are reported to stderr rather than the Python logging hierarchy, making Claude API cost and failure events invisible. Every `client.messages.create()` call returns a `Message` object with `resp.usage` (`Usage(input_tokens=N, output_tokens=M)`), but no call site logs token counts. This affects six endpoints: `chat.py` (Sonnet, tool-use loop up to 5 rounds), `deep_analysis.py` (Opus + 32768-token thinking budget, up to 3 rounds), `grounded_search.py` (Sonnet, tool-use loop), `grounded_maps.py`, `predictive_analysis.py` (Sonnet), and `weather_forecast.py`. For `deep_analysis.py`, a single 3-round tool-use call with full thinking budget can consume 100K+ tokens with zero observable signal. Beyond usage, all five route except blocks use `traceback.print_exc()` (writes to Python stderr, mixed with uvicorn access logs) rather than `logger.exception(...)` (writes to Python logging hierarchy with traceback included). The consequence: an Anthropic API `OverloadedError` or `RateLimitError` during peak load appears only as raw stderr text — invisible to any structured log aggregator, unalertable, and not correlated with the request that triggered it. Contrast: `predict.py:49` correctly uses `logger.error("Weekly retrain failed: %s", e)` for background tasks. PROPOSAL: (1) After each `client.messages.create()` call, add `logger.info("anthropic usage model=%s input=%d output=%d", model_name, resp.usage.input_tokens, resp.usage.output_tokens)` — L/L effort (~1-2 lines per call site across 6 files; exposes per-request token consumption for cost attribution and anomaly detection). (2) Replace `traceback.print_exc()` with `logger.exception("…")` in the five AI route except blocks — L/L effort (~5 lines; routes AI endpoint exceptions into the structured logging system where they are timestamped, correlated, and alertable).

### Run #264 — 2026-06-11 — Lens: Security
**Scope:** Twenty-first security pass. Files examined: `geointellisense-analytics/app/main.py`, `geointellisense-analytics/app/middleware.py`, `geointellisense-analytics/app/routes/admin.py`, `geointellisense-analytics/app/routes/chat.py`, `geointellisense-analytics/app/routes/predict.py`, `geointellisense-analytics/app/routes/explore.py`, `geointellisense-analytics/app/routes/deep_analysis.py`, `geointellisense-analytics/app/routes/grounded_search.py`, `geointellisense-analytics/app/config.py`, `geointellisense-analytics/app/claude.py`, `geointellisense-ingestion/src/routes/admin.rs`, `.env.local.example`. Cross-checked against Active Recommendations and archived security runs #9, 24, 39, 54, 69, 84, 99, 114, 129, 144, 159, 174, 189, 204, 219, 234, 249.

**Findings:**

- OBSERVATION: `middleware.py:106` and `admin.py:14` and `admin.rs:28` — `check_ai_auth` compares `api_key == settings.admin_token` and `_check_admin` compares `token != settings.admin_token` using Python's default `==`/`!=` operators, which short-circuit on the first differing byte and return immediately. The same issue exists in the Rust ingestion service at `admin.rs:28` where `if provided != token` uses Rust's default `PartialEq` on `&str`, also non-constant-time. A remote attacker making many requests with incrementally varying API key prefixes can measure sub-millisecond response-time differences to recover the admin token byte-by-byte (timing oracle). While network jitter makes this unreliable over the public internet, it is practical in co-located or container-to-container environments (e.g. Kubernetes pod traffic). PROPOSAL: Replace `api_key == settings.admin_token` with `hmac.compare_digest(api_key, settings.admin_token)` (Python stdlib `hmac` module, no new deps) at `middleware.py:106` and `admin.py:14`; use `subtle::ConstantTimeEq` (or compare via `ring`) at `admin.rs:28` — L/L effort (~3 lines Python + ~3 lines Rust; eliminates timing oracle on secret comparisons in both services).

- OBSERVATION: `chat.py:95-108` — `POST /api/chat/reset` (lines 95–102) and `POST /api/chat/session` (lines 105–108) have neither `check_ai_auth` nor `check_rate_limit` calls, unlike every other endpoint in the same file. `create_session()` at `claude.py:33-42` maintains `MAX_SESSIONS = 100` via LRU eviction: when the 101st session is created, the oldest entry is popped from `_session_order` and deleted from `_sessions`. An unauthenticated attacker can POST to `/api/chat/session` 100 times in rapid succession (no rate-limiting consulted) to fill the 100-slot LRU and silently evict all active legitimate sessions; any ongoing conversation then starts fresh with empty history. `POST /api/chat/reset` is additionally unprotected: while UUIDv4 session IDs (128-bit random, `claude.py:35`) are not brute-forceable, a session ID leaked via an XSS vector (see Active Recommendation #1, `AnalysisView.tsx:450`) or server logs can be used to terminate a legitimate session without any authentication or authorization. PROPOSAL: Add `request: Request` parameter and `await check_rate_limit(request, "data_default")` to `new_session` at `chat.py:105`; add `check_ai_auth(request)` and `await check_rate_limit(request, "ai_chat")` to `chat_reset` at `chat.py:95` — L/L effort (~6 lines; closes unauthenticated session-flood DoS and prevents unauthorized session teardown, aligning both management endpoints with the auth+rate-limit pattern used by every other chat endpoint in the same file).

- OBSERVATION: `explore.py:41` — `bucket: str = Query("1 day", description="Time bucket: 1 hour, 6 hours, 1 day")` accepts any PostgreSQL interval string with no code-level allowlist validation. The value is forwarded as `$1` to `time_bucket($1::interval, ...)` in all five source-specific queries inside `_query_source` (lines 152–217). A bucket of `"1 microsecond"` over `?days=365` asks TimescaleDB to compute approximately 3.15 × 10^13 time buckets across five concurrent queries, which will exhaust the PostgreSQL connection pool and OOM the analytics container. The raw `bucket` string is also included verbatim in the Redis cache key at `explore.py:48` (`{"src": sources, "days": days, "bucket": bucket}`); flooding the endpoint with unique bucket strings generates a unique Redis entry per request, exhausting Redis memory. Neither `GET /api/analysis/explore` nor `GET /api/analysis/explore/csv` call `check_ai_auth` or `check_rate_limit`, so any anonymous caller can trigger this at full request rate. PROPOSAL: Add `VALID_BUCKETS = frozenset({"1 hour", "6 hours", "1 day", "7 days", "30 days"})` and return HTTP 400 if `bucket not in VALID_BUCKETS` at `explore.py:43` — L/L effort (~4 lines; eliminates DoS via adversarial interval strings, bounds Redis cache cardinality, and makes the three documented valid values enforceable in code rather than just in a description string).

- OBSERVATION: `explore.py:37` and `explore.py:92` — `GET /api/analysis/explore` and `GET /api/analysis/explore/csv` have no `check_rate_limit` call and no `check_ai_auth` call, while executing 3–9 concurrent TimescaleDB queries (one per selected source) plus an O(n²) Pearson correlation computation in pure Python at `explore.py:222-268`. With `sources=aqi,pm25,temperature,humidity,wind_speed,fires,fire_frp,earthquakes,inversion` (all 9 sources) and `days=365&bucket=1+hour`, each request produces ~8760 data points × 36 source pairs = ~315K multiply-accumulate operations in Python, plus 9 concurrent DB queries. The CSV export endpoint at `explore.py:92` skips even the in-memory cache (no `get_cached` call), meaning every CSV request repeats the full DB+CPU work regardless of prior requests. Without rate limiting, an attacker can saturate both the PostgreSQL connection pool and Python event loop with a sustained burst of requests. PROPOSAL: Add `request: Request` parameter and `await check_rate_limit(request, "data_default")` to both endpoint handlers at `explore.py:38` and `explore.py:93` — L/L effort (~4 lines; applies the standard 60 req/min Redis-backed rate limit to the most computationally expensive endpoint chain in the analytics service).

**Proposed actions:**
- Replace `==`/`!=` admin token comparisons with `hmac.compare_digest` at `middleware.py:106` and `admin.py:14`; use constant-time compare at `admin.rs:28` — L/L effort (~6 lines; eliminates timing oracle across both services)
- Add auth + rate-limit to `POST /api/chat/reset` and `POST /api/chat/session` at `chat.py:95-108` — L/L effort (~6 lines; closes unauthenticated session-flood DoS that evicts all 100 active sessions)
- Validate `bucket` against `VALID_BUCKETS` allowlist at `explore.py:43` — L/L effort (~4 lines; prevents trillion-bucket TimescaleDB DoS and Redis cache flooding)
- Add `check_rate_limit(request, "data_default")` to both explore endpoints at `explore.py:38,93` — L/L effort (~4 lines; closes unthrottled DB+CPU path on the most expensive public endpoint)
