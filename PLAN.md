### Run #264 — 2026-06-11 — Lens: Security
**Scope:** Twenty-first security pass. Files examined: `geointellisense-analytics/app/main.py`, `geointellisense-analytics/app/middleware.py`, `geointellisense-analytics/app/routes/admin.py`, `geointellisense-analytics/app/routes/chat.py`, `geointellisense-analytics/app/routes/predict.py`, `geointellisense-analytics/app/routes/explore.py`, `geointellisense-analytics/app/routes/deep_analysis.py`, `geointellisense-analytics/app/routes/grounded_search.py`, `geointellisense-analytics/app/config.py`, `geointellisense-analytics/app/claude.py`, `geointellisense-ingestion/src/routes/admin.rs`, `.env.local.example`. Cross-checked against Active Recommendations and archived security runs #9, 24, 39, 54, 69, 84, 99, 114, 129, 144, 159, 174, 189, 204, 219, 234, 249.

**Findings:**

- OBSERVATION: `middleware.py:106` and `admin.py:14` and `admin.rs:28` — `check_ai_auth` compares `api_key == settings.admin_token` and `_check_admin` compares `token != settings.admin_token` using Python's default `==`/`!=` operators, which short-circuit on the first differing byte and return immediately. The same issue exists in the Rust ingestion service at `admin.rs:28` where `if provided != token` uses Rust's default `PartialEq` on `&str`, also non-constant-time. A remote attacker making many requests with incrementally varying API key prefixes can measure sub-millisecond response-time differences to recover the admin token byte-by-byte (timing oracle). While network jitter makes this unreliable over the public internet, it is practical in co-located or container-to-container environments (e.g. Kubernetes pod traffic). PROPOSAL: Replace `api_key == settings.admin_token` with `hmac.compare_digest(api_key, settings.admin_token)` (Python stdlib `hmac` module, no new deps) at `middleware.py:106` and `admin.py:14`; use `subtle::ConstantTimeEq` (or compare via `ring`) at `admin.rs:28` — L/L effort (~3 lines Python + ~3 lines Rust; eliminates timing oracle on secret comparisons in both services).

- OBSERVATION: `chat.py:95-108` — `POST /api/chat/reset` (lines 95–102) and `POST /api/chat/session` (lines 105–108) have neither `check_ai_auth` nor `check_rate_limit` calls, unlike every other endpoint in the same file. `create_session()` at `claude.py:33-42` maintains `MAX_SESSIONS = 100` via LRU eviction: when the 101st session is created, the oldest entry is popped from `_session_order` and deleted from `_sessions`. An unauthenticated attacker can POST to `/api/chat/session` 100 times in rapid succession (no rate-limiting consulted) to fill the 100-slot LRU and silently evict all active legitimate sessions; any ongoing conversation then starts fresh with empty history. `POST /api/chat/reset` is additionally unprotected: while UUIDv4 session IDs (128-bit random, `claude.py:35`) are not brute-forceable, a session ID leaked via an XSS vector (see Active Recommendation #1, `AnalysisView.tsx:450`) or server logs can be used to terminate a legitimate session without any authentication or authorization. PROPOSAL: Add `request: Request` parameter and `await check_rate_limit(request, "data_default")` to `new_session` at `chat.py:105`; add `check_ai_auth(request)` and `await check_rate_limit(request, "ai_chat")` to `chat_reset` at `chat.py:95` — L/L effort (~6 lines; closes unauthenticated session-flood DoS and prevents unauthorized session teardown, aligning both management endpoints with the auth+rate-limit pattern used by every other chat endpoint in the same file).

- OBSERVATION: `explore.py:41` — `bucket: str = Query("1 day", description="Time bucket: 1 hour, 6 hours, 1 day")` accepts any PostgreSQL interval string with no code-level allowlist validation. The value is forwarded as `$1` to `time_bucket($1::interval, ...)` in all five source-specific queries inside `_query_source` (lines 152–217). A bucket of `"1 microsecond"` over `?days=365` asks TimescaleDB to compute approximately 3.15 × 10^13 time buckets across five concurrent queries, which will exhaust the PostgreSQL connection pool and OOM the analytics container. The raw `bucket` string is also included verbatim in the Redis cache key at `explore.py:48` (`{"src": sources, "days": days, "bucket": bucket}`); flooding the endpoint with unique bucket strings generates a unique Redis entry per request, exhausting Redis memory. Neither `GET /api/analysis/explore` nor `GET /api/analysis/explore/csv` call `check_ai_auth` or `check_rate_limit`, so any anonymous caller can trigger this at full request rate. PROPOSAL: Add `VALID_BUCKETS = frozenset({"1 hour", "6 hours", "1 day", "7 days", "30 days"})` and return HTTP 400 if `bucket not in VALID_BUCKETS` at `explore.py:43` — L/L effort (~4 lines; eliminates DoS via adversarial interval strings, bounds Redis cache cardinality, and makes the three documented valid values enforceable in code rather than just in a description string).

- OBSERVATION: `explore.py:37` and `explore.py:92` — `GET /api/analysis/explore` and `GET /api/analysis/explore/csv` have no `check_rate_limit` call and no `check_ai_auth` call, while executing 3–9 concurrent TimescaleDB queries (one per selected source) plus an O(n²) Pearson correlation computation in pure Python at `explore.py:222-268`. With `sources=aqi,pm25,temperature,humidity,wind_speed,fires,fire_frp,earthquakes,inversion` (all 9 sources) and `days=365&bucket=1+hour`, each request produces ~8760 data points × 36 source pairs = ~315K multiply-accumulate operations in Python, plus 9 concurrent DB queries. The CSV export endpoint at `explore.py:92` skips even the in-memory cache (no `get_cached` call), meaning every CSV request repeats the full DB+CPU work regardless of prior requests. Without rate limiting, an attacker can saturate both the PostgreSQL connection pool and Python event loop with a sustained burst of requests. PROPOSAL: Add `request: Request` parameter and `await check_rate_limit(request, "data_default")` to both endpoint handlers at `explore.py:38` and `explore.py:93` — L/L effort (~4 lines; applies the standard 60 req/min Redis-backed rate limit to the most computationally expensive endpoint chain in the analytics service).

**Proposed actions:**
- Replace `==`/`!=` admin token comparisons with `hmac.compare_digest` at `middleware.py:106` and `admin.py:14`; use constant-time compare at `admin.rs:28` — L/L effort (~6 lines; eliminates timing oracle across both services)
- Add auth + rate-limit to `POST /api/chat/reset` and `POST /api/chat/session` at `chat.py:95-108` — L/L effort (~6 lines; closes unauthenticated session-flood DoS that evicts all 100 active sessions)
- Validate `bucket` against `VALID_BUCKETS` allowlist at `explore.py:43` — L/L effort (~4 lines; prevents trillion-bucket TimescaleDB DoS and Redis cache flooding)
- Add `check_rate_limit(request, "data_default")` to both explore endpoints at `explore.py:38,93` — L/L effort (~4 lines; closes unthrottled DB+CPU path on the most expensive public endpoint)

### Run #263 — 2026-06-11 — Lens: Data pipeline integrity
**Scope:** Twentieth data pipeline integrity pass. Files examined: `geointellisense-ingestion/src/db/persist.rs`, `geointellisense-ingestion/src/usgs.rs`, `geointellisense-ingestion/src/purpleair.rs`, `geointellisense-ingestion/src/broadcast.rs`, `geointellisense-ingestion/src/redis_cache.rs`, `geointellisense-ingestion/src/aqi.rs`, `geointellisense-ingestion/src/routes/aqi.rs`, `geointellisense-ingestion/src/routes/sse.rs`, `geointellisense-analytics/app/clients/airnow.py`, `geointellisense-analytics/app/clients/epa_aqs.py`, `geointellisense-analytics/app/clients/nasa_firms.py`, `geointellisense-analytics/app/clients/usgs_water.py`, `geointellisense-analytics/app/http_client.py`, `geointellisense-analytics/app/routes/epa_aqi.py`, `geointellisense-analytics/app/routes/airnow.py`, `geointellisense-analytics/app/context.py`. Cross-checked against Active Recommendations and archived data-pipeline runs #8, 23, 38, 53, 68, 83, 98, 113, 128, 143, 158, 173, 188, 203, 218, 233, 248.

**Findings:**

- OBSERVATION: `db/persist.rs:6-34` — `write_readings` inserts each of the 6 station readings in an individual `sqlx::query().execute()` loop with no wrapping transaction and no `ON CONFLICT` clause. Three failure modes result: (1) If the PostgreSQL connection drops mid-loop, readings 1–k succeed and k+1–6 are silently dropped — the partial dataset for that broadcast timestamp is indistinguishable from a complete one, producing apparent data gaps in historical charts without any error record; (2) Because `broadcast.rs:106` stamps each reading with `Utc::now()` inside the loop, timestamps across the 6 readings within a single broadcast can diverge by several milliseconds, potentially colliding with `(time, location_id)` unique-key constraints if microsecond rounding places two tick intervals within the same stored precision; (3) The USGS earthquake persist at `usgs.rs:170` correctly uses `ON CONFLICT (event_id, time) DO NOTHING` for idempotent replay after restarts, but no equivalent protection exists for sensor readings — a service restart that triggers two writes within the same timestamp window would cause constraint-violation errors logged at `tracing::error!` with no recovery path. PROPOSAL: Wrap the `write_readings` loop in a single `BEGIN` / `COMMIT` transaction via `sqlx::Transaction` and add `ON CONFLICT (time, location_id) DO NOTHING` to the INSERT in `persist.rs:7` — L/M effort (~5 lines; makes sensor ingestion idempotent on replay and prevents partial writes on connection interruptions, consistent with the USGS pattern already in the same codebase).

- OBSERVATION: `usgs.rs:107` — `fetch_recent` (called every `earthquake_interval_secs` via `broadcast.rs:154`) creates `let client = reqwest::Client::new()` on every invocation. `reqwest::Client` internally manages a TCP connection pool with keep-alive and TLS session resumption; creating a new instance on every poll cycle discards the pool, forcing a fresh DNS lookup, TCP three-way handshake, and full TLS handshake (~40–80 ms to USGS servers at each poll). At a 60 s poll interval this adds ~0.1–0.3 % overhead per cycle; at shorter intervals the overhead compounds further. The USGS endpoint is a government API with no SLA — TLS setup failure also maps to no retry (the `reqwest::Client::new()` call itself is infallible, but the subsequent `.send()` at line 122 has no retry logic in this path). Contrast with `purpleair.rs:41-47` which correctly stores `http: reqwest::Client` as a struct field and reuses it across all calls. PROPOSAL: Introduce a `UsgsClient` struct with a stored `reqwest::Client` field (mirroring `PurpleAirClient`'s layout), construct it once in `main.rs` alongside the PurpleAir client, pass it into `spawn_earthquake_poller`, and call `client.fetch_recent(bbox)` — L/M effort (~20 lines; eliminates per-poll TLS setup overhead and aligns the USGS client pattern with the existing PurpleAir implementation in the same crate).

- OBSERVATION: `airnow.py:48` — `AirNowClient.__init__` creates its own `self._http = httpx.AsyncClient(timeout=15.0)` and calls `resp.raise_for_status()` directly in `get_current_observations:65` and `get_forecast:80`, with no retry on 429 or 5xx. The shared `app.http_client.fetch()` function (used by `nasa_firms.py:17` via `from app.http_client import fetch as http_fetch` and by `usgs_water.py:13` the same way) implements Retry-After-aware 429 handling, 5xx exponential backoff (1s/2s/4s, up to 3 retries), and timeout retry — AirNow is the only analytics API client that does not use it. Per-city failures are caught in the `except Exception` block at `get_all_sjv_current:99`, but only after the single failed attempt. A transient 5xx or AirNow rate-limit event during a cache-miss sweep (6 cities × current + forecast = 12 requests) silently drops the affected city's readings for the full 1-hour cache TTL (`AIRNOW_TTL = 3600` in `routes/airnow.py:12`). This is particularly problematic because AirNow is the primary EPA-grade data source for the UI's "AirNow" source toggle. PROPOSAL: Replace the `self._http.get(url, params=params)` calls in `get_current_observations:64` and `get_forecast:79` with `await http_fetch(url, params=params, timeout=15.0)` using the shared client (adding `from app.http_client import fetch as http_fetch` at line 17 of `airnow.py`) — L/L effort (~6 lines; adds 429/5xx retry to AirNow API calls, consistent with all other clients in the analytics service, without changing the per-city catch-and-continue error-handling pattern).

- OBSERVATION: `epa_aqs.py:64-75` combined with `epa_aqi.py:48` — A fresh `EpaAqsClient` is instantiated on every HTTP request to `GET /api/epa-aqi` (line 48: `client = EpaAqsClient(settings.epa_aqs_email, settings.epa_aqs_key)`). The rate-limit throttle in `_throttled_get` (lines 70-75) checks `elapsed = now - self._last_request`; on a new instance `self._last_request = 0.0` and `asyncio.get_event_loop().time()` returns process uptime (always ≫ `REQUEST_PAUSE_SECS = 6.0`), so the `await asyncio.sleep()` branch is never triggered for the first call on any fresh instance. Consequently, two concurrent `GET /api/epa-aqi` requests — one for county 019 (Fresno) and one for county 029 (Kern) — each create a separate `EpaAqsClient` and both issue their EPA AQS HTTP calls simultaneously with zero delay between them, bypassing the intended 10 req/min (6 s pacing) completely. The throttle only functions correctly inside `_run_backfill` (which reuses one long-lived client across all calls). On a server restart (when the in-memory `get_cached` store is empty), multiple simultaneous frontend requests can trigger concurrent `GET /api/epa-aqi` calls, each firing immediately to EPA AQS and potentially exhausting the 10 req/min cap within seconds, causing subsequent calls to receive 429 responses that are returned as `502 Bad Gateway` to the frontend. PROPOSAL: Promote `_last_request` to a module-level `asyncio.Lock`-guarded class variable on `EpaAqsClient`, or add a `baseurl`-keyed rate-limit semaphore in `http_client.py`, so that all concurrent request handlers share the same 6 s pacing state — M/M effort (~15 lines; makes the 6 s rate-limit throttle effective across concurrent request handlers, not just within a single backfill session).

**Proposed actions:**
- Wrap `write_readings` in a transaction; add `ON CONFLICT (time, location_id) DO NOTHING` at `persist.rs:7` — L/M effort (~5 lines; makes sensor ingestion idempotent on replay and prevents partial-write data gaps)
- Introduce `UsgsClient` struct with stored `reqwest::Client`; refactor `usgs.rs:107` to reuse it — L/M effort (~20 lines; eliminates per-poll TLS handshake overhead and aligns USGS with PurpleAir client pattern)
- Replace `self._http.get(...)` in `airnow.py:64` and `airnow.py:79` with `http_fetch(...)` from shared `app.http_client` — L/L effort (~6 lines; adds 429/5xx retry to AirNow, the one client that currently bypasses the shared retry infrastructure)
- Promote `EpaAqsClient._last_request` to a class-level rate-limit guard in `epa_aqs.py:65` — M/M effort (~15 lines; makes the 6 s EPA AQS throttle effective across concurrent request handlers on server restart)

### Run #262 — 2026-06-11 — Lens: UX / UI flaws
**Scope:** Nineteenth UX / UI flaws pass. Files examined: `components/AnalysisView.tsx`, `components/ChatView.tsx`, `components/DataExplorer.tsx`, `components/Dashboard.tsx`, `components/Header.tsx`, `components/Sidebar.tsx`, `components/MapView.tsx` (first 100 lines), `components/dashboard/WidgetShell.tsx`, `components/dashboard/LiveDashboard.tsx`, `components/dashboard/widgets/AqiGaugeWidget.tsx`, `components/dashboard/widgets/AqiTrendWidget.tsx`, `components/dashboard/widgets/InversionWidget.tsx`, `components/LoadingStates.tsx`, `App.tsx`. Cross-checked against Active Recommendations and archived UX/UI runs #7, 22, 37, 52, 67, 82, 97, 112, 127, 142, 157, 172, 187, 202, 217, 232, 247.

**Findings:**

- OBSERVATION: `components/DataExplorer.tsx:393` — `dangerouslySetInnerHTML={{ __html: claudeResult.replace(/\n/g, '<br />') }}` renders the raw string returned by `getDeepAnalysisResponse(prompt)` at line 143 directly into the DOM with no sanitization. This is the same vulnerability class as Active Recommendation #1 (which covers `AnalysisView.tsx:450`) but is a separate, independent occurrence in a different user-facing view. The `prompt` sent to Claude at `DataExplorer.tsx:122-140` is constructed from user-controlled `selected`, `days`, and `bucket` state values plus live API data (`corrMatrix`, `sample`). If the analytics backend or correlation data is compromised (e.g., by injected field names from external data), Claude's response could contain `<script>` or `<img onerror=...>` payloads that would execute in the user's browser via this unsanitized render path. The `.replace(/\n/g, '<br />')` transform converts plain text to HTML before React's XSS protection runs, bypassing React's default escaping. PROPOSAL: Add `import DOMPurify from 'dompurify'` to `DataExplorer.tsx` and wrap the render value: `{ __html: DOMPurify.sanitize(claudeResult.replace(/\n/g, '<br />')) }` at line 393 — L/L effort (~2 lines; closes XSS in `DataExplorer` parallel to the same fix needed in `AnalysisView.tsx:450`, both of which currently pass unsanitized AI output directly to `dangerouslySetInnerHTML`).

- OBSERVATION: `components/ChatView.tsx:84` — `onKeyPress={(e) => e.key === 'Enter' && handleSend()}` uses the deprecated `keypress` DOM event via React's `onKeyPress` synthetic handler. The `keypress` event was deprecated in the HTML spec (superseded by `keydown`/`keyup`) and React 18 emits a console warning for `onKeyPress`. While browsers maintain backwards compatibility today, `keypress` has historically been unreliable for non-printable keys and some special characters — Enter key behavior in particular varies by browser engine and composition context (e.g., IME input on CJK keyboards). The rest of the codebase exclusively uses `keydown`: `App.tsx:88` calls `useKeyboardShortcuts` which attaches `document.addEventListener('keydown', ...)`, and `utils/accessibility.tsx` hooks are all `keydown`-based. `ChatView.tsx` is the sole file using `onKeyPress`, creating an inconsistency that makes the Enter-to-send path the only keyboard interaction not aligned with the spec. PROPOSAL: Change `onKeyPress` to `onKeyDown` at `ChatView.tsx:84` — L/L effort (~1 line; aligns with the HTML spec, removes the React 18 deprecation warning, and matches the `keydown`-only convention used everywhere else in the codebase).

- OBSERVATION: `components/DataExplorer.tsx:169-183` — The nine source toggle buttons (AQI, PM2.5, Temperature, Humidity, Wind Speed, Fires, Fire Intensity, Earthquakes, Inversion) convey their active/inactive state only through CSS `backgroundColor` and border styles. The `<button>` elements at line 170 have no `aria-pressed` attribute, so screen readers announce them as plain buttons with no state information. WCAG 2.1 SC 4.1.2 (Name, Role, Value) requires that for all UI components, the value (state) can be programmatically determined. A screen reader user operating the Data Explorer cannot determine which of the 9 sources are currently overlaid on the chart without visual inspection of the rendered colors. The chart description (`TimeSeriesOverlay` title) also has no associated `aria-describedby` linking the selected-source list to the chart. PROPOSAL: Add `aria-pressed={selected.includes(key)}` to the `<button>` element at `DataExplorer.tsx:172` — L/L effort (~1 line; makes each toggle's active/inactive state programmatically determinable by assistive technologies without changing the visual design).

- OBSERVATION: `components/dashboard/widgets/InversionWidget.tsx:33-37` — The widget displays surface temperature as `${data.surfaceTempF}°F` at line 33 and 850 mb temperature as `${data.temp850mbC}°C` at line 37, using two different temperature scales side by side in the same widget. The `tempDiffC` differential at line 26 is also °C. A user assessing inversion severity from the numeric values (e.g., "Surface: 72°F, 850mb: 15°C, Δ: +7.2°C") must mentally convert between Fahrenheit and Celsius to make sense of the numbers — the expected relationship between surface and aloft temperature is not immediately readable. Furthermore, `UserPreferencesContext` exposes a `temperatureUnit` preference (`TemperatureUnit` type in `types.ts`) and `SettingsView.tsx` renders a temperature unit selector, but `InversionWidget.tsx` never calls `useUserPreferences()` and ignores this setting. All other weather-facing widgets that display temperature (e.g., `WeatherWidget.tsx`) similarly need to honor the user's temperature preference. The hardcoded °F for surface temp reflects the source data unit (`surfaceTempF` field name) rather than a UX choice, but surfacing it verbatim creates the mixed-unit display. PROPOSAL: Import `useUserPreferences` in `InversionWidget.tsx`; convert `surfaceTempF` from °F to the user's preferred unit (already converted from Celsius) and convert `temp850mbC`/`tempDiffC` from °C to the same preferred unit before display; display a single consistent unit symbol — M/M effort (~15 lines; eliminates mixed-unit display, honors the user's temperature preference that is currently ignored by this widget, and makes the inversion differential immediately interpretable without mental unit conversion).

**Proposed actions:**
- Add `DOMPurify.sanitize(...)` wrapper at `DataExplorer.tsx:393` alongside the existing fix needed at `AnalysisView.tsx:450` — L/L effort (~2 lines; closes XSS from unsanitized AI output in the Data Explorer view)
- Change `onKeyPress` to `onKeyDown` at `ChatView.tsx:84` — L/L effort (~1 line; removes deprecated API usage and aligns with codebase-wide `keydown` convention)
- Add `aria-pressed={selected.includes(key)}` to source toggle buttons at `DataExplorer.tsx:172` — L/L effort (~1 line; makes toggle state programmatically determinable per WCAG 2.1 SC 4.1.2)
- Import `useUserPreferences` in `InversionWidget.tsx`; convert all temperatures to user-preferred unit — M/M effort (~15 lines; eliminates mixed °F/°C display and honors the existing temperature preference setting)
