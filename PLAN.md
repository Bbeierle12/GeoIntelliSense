- OBSERVATION: `geointellisense-analytics/app/routes/traffic.py:16,17` and `geointellisense-analytics/app/clients/caltrans.py:15` — The endpoint `GET /api/traffic/current` serves Annual Average Daily Traffic (AADT) data from the Caltrans ArcGIS Feature Service (`Traffic_AADT/FeatureServer/0/query`). AADT is a statistical metric published once per year by Caltrans; it represents the average number of vehicles passing a point over a full calendar year and is updated annually, not in real time or even daily. The developer comment at `traffic.py:16` explicitly acknowledges the mislabeling: `TRAFFIC_TTL = 300  # 5 minutes for "current" (AADT is static but we present it as current conditions)`. The response JSON includes `"source": "caltrans_aadt"` but no `data_vintage` or `collection_year` field, so API consumers have no programmatic way to determine which year's AADT they are receiving. The `source_toggles.py:38` UI label reads `"Caltrans traffic AADT volumes"` — which correctly uses "AADT" — but the endpoint name `/api/traffic/current` and the `TRAFFIC_TTL = 300` (implying 5-minute freshness) create a false impression of near-real-time traffic data in any dashboard widget or AI tool that calls this endpoint. PROPOSAL: Rename the endpoint to `/api/traffic/aadt`; add a `data_vintage: int` field to the response payload containing the year of the AADT dataset; update `source_toggles.py:38` description to `"Caltrans Annual Average Daily Traffic (AADT) — updated yearly, not live"`; add a tooltip or footnote in any UI widget consuming this endpoint clarifying that traffic figures are annual averages — L/L effort (~10 lines across `traffic.py`, `source_toggles.py`, and response formatter; eliminates the "current conditions" mislabeling for annual-average traffic data).

- OBSERVATION: `geointellisense-analytics/app/cache.py:106-111` and `geointellisense-analytics/app/routes/airnow.py:12,28,49` — The `cache_headers(hit: bool, ttl: int)` function at `cache.py:106-111` returns `"Cache-Control": f"public, max-age={ttl}"` for **both** cache HITs and MISSes — the same `max-age` regardless of how long the data has already been sitting in Redis. For `airnow.py` (TTL=3600s) a cache HIT response instructs the browser and any intermediate CDN to cache the response for a further 3600s from the moment of receipt. Since the data in Redis may already be up to 3599s old at the time of the HIT, worst-case data age at the browser is 3599 + 3600 = 7199 seconds (≈ 2 hours) — two full AirNow update cycles. The same doubling applies to NWS forecast (`nws_forecast.py:12` TTL=3600s): worst-case browser staleness is also 2 hours for forecast data. The HTTP specification provides the `Age` response header precisely for this scenario: setting `Age: {elapsed_redis_seconds}` on a cache HIT causes browsers and CDNs to correctly subtract elapsed time from `max-age`, preventing the double-caching window. Without `Age`, the `Cache-Control: public, max-age=3600` on a HIT response looks identical to a MISS response, so the browser treats it as freshly-fetched. PROPOSAL: Extend `cache_headers()` at `cache.py:106-111` to accept an optional `age: int = 0` parameter and include `"Age": str(age)` in the returned headers; update `get_cached()` to also return the elapsed age via `r.object(key, "idletime")` or `ttl_max - r.ttl(key)`; pass this to all `cache_headers(hit, ttl, age=elapsed)` call sites — M/L effort (~20 lines across `cache.py` and 7 route files; eliminates browser double-caching, ensures displayed AirNow/NWS data age accurately matches the `max-age` window, aligns with RFC 7234).

- OBSERVATION: `components/dashboard/WidgetShell.tsx:44-46` and `hooks/useLiveData.ts:81-83` — Every dashboard widget (Active Fires, Water Levels, Earthquakes, Temperature Inversion, AQI Trend, AQI Forecast) displays a `lastUpdated` timestamp via `WidgetShell`: `{lastUpdated.toLocaleTimeString()}` at line 46. Crucially, browsers honor `Cache-Control: public, max-age=N` (returned by `cache_headers()` for all analytics responses): when the browser's HTTP cache holds a still-fresh response, `fetch()` resolves immediately from the browser cache without a network round-trip, yet `setLastUpdated(new Date())` is still called with the current wall-clock time. **Findings:**

- OBSERVATION: `claude.py:74-75` — `get_client()` returns `anthropic.Anthropic(api_key=settings.anthropic_api_key)`. `anthropic.Anthropic` is the **synchronous** Anthropic SDK client; it uses `httpx.Client` internally. Every route that calls `client.messages.create()` (via `client = get_client()` or inline) executes a blocking synchronous HTTP request from within an `async def` FastAPI handler. The affected call sites are: `chat.py:43,70` (model `claude-sonnet-4-20250514`, up to 5 tool-use rounds), `deep_analysis.py:33,61` (model `claude-opus-4-6`, extended thinking, up to 3 tool-use rounds — calls can take 10–60+ seconds), `low_latency.py:31` (Haiku, typically 1–3 s), `grounded_search.py:39,62`, `grounded_maps.py:46,69`, `predictive_analysis.py:91`, `weather_forecast.py:75` — 11 call sites across 7 files, none of which use `await`. Because Uvicorn runs all async coroutines on a single event-loop thread, a blocking synchronous call freezes that thread for its entire duration: no other `async def` handler, health check, rate-limit check, or DB query can run while any LLM call is in progress. A single `POST /api/deep-analysis` triggering three tool-use rounds with extended thinking can monopolize the event loop for 60–120 seconds, making the entire analytics service unresponsive. The Anthropic SDK provides `anthropic.AsyncAnthropic` with `await client.messages.create()` for exactly this use case. PROPOSAL: Replace `anthropic.Anthropic` with `anthropic.AsyncAnthropic` in `get_client()` at `claude.py:74-75`, update the return type annotation, and add `await` to all 11 `messages.create()` call sites — H/L effort (~15 targeted line changes across 7 files; unblocks the event loop during all LLM API calls, enables concurrent request handling during multi-second Anthropic responses, prerequisite for any meaningful concurrency under load).

- OBSERVATION: `deep_analysis.py:51-76`, `grounded_search.py:51-72`, `grounded_maps.py:58-79` — All three multi-round tool use loops overwrite the accumulated message history on each iteration. In `deep_analysis.py:51`, the loop opens with `assistant_content = resp.content`, which re-binds to the CURRENT round's response on each pass; the continuation call at `deep_analysis.py:61-76` is then constructed as `messages=[{"role":"user","content":req.prompt}, {"role":"assistant","content":assistant_content}, {"role":"user","content":tool_results}]` — a flat 3-message history that discards all prior rounds. On iteration 2, round-1's assistant turn and tool results are completely absent; the model is presented with a history identical in structure to a first round, losing all knowledge of what tools it already called and what they returned. The correct pattern accumulates the full interleaved history across rounds. For `deep_analysis.py` specifically, this also violates the Anthropic extended-thinking API contract: per Anthropic's API documentation, when `thinking` blocks are present in an assistant response (which they always are when `thinking:{"type":"enabled","budget_tokens":32768}` is active at `deep_analysis.py:38-41`), those thinking blocks **must** be included verbatim in the `assistant` content of all subsequent turns — omitting them is an API error condition that causes a 400 response. On round 2, `assistant_content` contains the round-2 response (no round-1 thinking blocks), creating a malformed API call that the Anthropic API will reject. The same structural bug exists in `grounded_search.py:51-72` and `grounded_maps.py:58-79` (Sonnet, no extended thinking — loses tool history but does not violate the thinking-block contract). PROPOSAL: Refactor all three tool use loops to maintain an explicit `messages: list` that is `extend()`ed with each round's `[{"role":"assistant","content":assistant_content}, {"role":"user","content":tool_results}]` pair; initialize with `[{"role":"user","content":req.prompt}]` before the loop — L/M effort (~20-line refactor across 3 files; eliminates the extended-thinking API contract violation in `deep_analysis.py` that causes 400 errors on 2nd tool-use round, restores correct multi-round tool context in all three endpoints).

- OBSERVATION: `predictive_analysis.py:34` and `weather_forecast.py:27` — Both request models define `customFactors: str` with no Pydantic `Field(max_length=...)` constraint. The string is embedded directly into the Claude prompt at `predictive_analysis.py:52-57` and `weather_forecast.py:40-45` inside a markdown code fence. Both endpoints lack `check_ai_auth` and `check_rate_limit` (Active Rec #4 is open).
