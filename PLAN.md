Cross-checked against Active Recommendations and archived UX/UI runs #7, 22, 37, 52, 67, 82, 97, 112, 127, 142, 157, 172, 187, 202, 217, 232, 247.

**Findings:**

- OBSERVATION: `components/DataExplorer.tsx:393` — `dangerouslySetInnerHTML={{ __html: claudeResult.replace(/\n/g, '<br />') }}` renders the raw string returned by `getDeepAnalysisResponse(prompt)` at line 143 directly into the DOM with no sanitization. This is the same vulnerability class as Active Recommendation #1 (which covers `AnalysisView.tsx:450`) but is a separate, independent occurrence in a different user-facing view. The `prompt` sent to Claude at `DataExplorer.tsx:122-140` is constructed from user-controlled `selected`, `days`, and `bucket` state values plus live API data (`corrMatrix`, `sample`). If the analytics backend or correlation data is compromised (e.g., by injected field names from external data), Claude's response could contain `<script>` or `<img onerror=...>` payloads that would execute in the user's browser via this unsanitized render path. The `.replace(/\n/g, '<br />')` transform converts plain text to HTML before React's XSS protection runs, bypassing React's default escaping. PROPOSAL: Add `import DOMPurify from 'dompurify'` to `DataExplorer.tsx` and wrap the render value: `{ __html: DOMPurify.sanitize(claudeResult.replace(/\n/g, '<br />')) }` at line 393 — L/L effort (~2 lines; closes XSS in `DataExplorer` parallel to the same fix needed in `AnalysisView.tsx:450`, both of which currently pass unsanitized AI output directly to `dangerouslySetInnerHTML`).

- OBSERVATION: `components/ChatView.tsx:84` — `onKeyPress={(e) => e.key === 'Enter' && handleSend()}` uses the deprecated `keypress` DOM event via React's `onKeyPress` synthetic handler. The `keypress` event was deprecated in the HTML spec (superseded by `keydown`/`keyup`) and React 18 emits a console warning for `onKeyPress`. While browsers maintain backwards compatibility today, `keypress` has historically been unreliable for non-printable keys and some special characters — Enter key behavior in particular varies by browser engine and composition context (e.g., IME input on CJK keyboards). The rest of the codebase exclusively uses `keydown`: `App.tsx:88` calls `useKeyboardShortcuts` which attaches `document.addEventListener('keydown', ...)`, and `utils/accessibility.tsx` hooks are all `keydown`-based. `ChatView.tsx` is the sole file using `onKeyPress`, creating an inconsistency that makes the Enter-to-send path the only keyboard interaction not aligned with the spec. PROPOSAL: Change `onKeyPress` to `onKeyDown` at `ChatView.tsx:84` — L/L effort (~1 line; aligns with the HTML spec, removes the React 18 deprecation warning, and matches the `keydown`-only convention used everywhere else in the codebase).

- OBSERVATION: `components/DataExplorer.tsx:169-183` — The nine source toggle buttons (AQI, PM2.5, Temperature, Humidity, Wind Speed, Fires, Fire Intensity, Earthquakes, Inversion) convey their active/inactive state only through CSS `backgroundColor` and border styles. The `<button>` elements at line 170 have no `aria-pressed` attribute, so screen readers announce them as plain buttons with no state information. WCAG 2.1 SC 4.1.2 (Name, Role, Value) requires that for all UI components, the value (state) can be programmatically determined. A screen reader user operating the Data Explorer cannot determine which of the 9 sources are currently overlaid on the chart without visual inspection of the rendered colors. The chart description (`TimeSeriesOverlay` title) also has no associated `aria-describedby` linking the selected-source list to the chart. PROPOSAL: Add `aria-pressed={selected.includes(key)}` to the `<button>` element at `DataExplorer.tsx:172` — L/L effort (~1 line; makes each toggle's active/inactive state programmatically determinable by assistive technologies without changing the visual design).

- OBSERVATION: `components/dashboard/widgets/InversionWidget.tsx:33-37` — The widget displays surface temperature as `${data.surfaceTempF}°F` at line 33 and 850 mb temperature as `${data.temp850mbC}°C` at line 37, using two different temperature scales side by side in the same widget. The `tempDiffC` differential at line 26 is also °C. A user assessing inversion severity from the numeric values (e.g., "Surface: 72°F, 850mb: 15°C, Δ: +7.2°C") must mentally convert between Fahrenheit and Celsius to make sense of the numbers — the expected relationship between surface and aloft temperature is not immediately readable. Furthermore, `UserPreferencesContext` exposes a `temperatureUnit` preference (`TemperatureUnit` type in `types.ts`) and `SettingsView.tsx` renders a temperature unit selector, but `InversionWidget.tsx` never calls `useUserPreferences()` and ignores this setting. All other weather-facing widgets that display temperature (e.g., `WeatherWidget.tsx`) similarly need to honor the user's temperature preference. The hardcoded °F for surface temp reflects the source data unit (`surfaceTempF` field name) rather than a UX choice, but surfacing it verbatim creates the mixed-unit display. PROPOSAL: Import `useUserPreferences` in `InversionWidget.tsx`; convert `surfaceTempF` from °F to the user's preferred unit (already converted from Celsius) and convert `temp850mbC`/`tempDiffC` from °C to the same preferred unit before display; display a single consistent unit symbol — M/M effort (~15 lines; eliminates mixed-unit display, honors the user's temperature preference that is currently ignored by this widget, and makes the inversion differential immediately interpretable without mental unit conversion).

**Proposed actions:**
- Add `DOMPurify.sanitize(...)` wrapper at `DataExplorer.tsx:393` alongside the existing fix needed at `AnalysisView.tsx:450` — L/L effort (~2 lines; closes XSS from unsanitized AI output in the Data Explorer view)
- Change `onKeyPress` to `onKeyDown` at `ChatView.tsx:84` — L/L effort (~1 line; removes deprecated API usage and aligns with codebase-wide `keydown` convention)

**Findings:**

- OBSERVATION: `historical_aqi.py:46` and `historical_weather.py:42` — Both Python routes cast the incoming `location_ids` query parameter directly to `uuid[]` in the SQL WHERE clause: `query += f" AND sr.location_id = ANY(${idx}::uuid[])"`. The TypeScript caller at `dataService.ts:279` constructs location IDs as slugified city names: `id: name.toLowerCase().replace(/\s+/g, '_')`, producing values such as `"fresno"`, `"bakersfield"`, `"valley_average"`. When `dataService.getHistoricalAQI(["fresno"])` is called, it sends `?location_ids=fresno` to the analytics backend. PostgreSQL's `'fresno'::uuid` cast raises `ERROR: invalid input syntax for type uuid: "fresno"`, which propagates as an unhandled 500 from FastAPI. The TS caller at `dataService.ts:207` catches the error and silently falls back to mock data — meaning the real DB is **never** queried when any `location_ids` filter is applied from the TS frontend. `historical_weather.py:42` has the identical `::uuid[]` cast and the same silent failure path. PROPOSAL: In both routes, replace the `::uuid[]` cast with a `location_name ILIKE ANY($idx::text[])` filter joined against the `locations` table, and update `dataService.ts` to pass `location_names` (city name strings) rather than slugified IDs for the analytics API endpoints — M/L effort (~12 lines across two Python routes + one TS client change; restores the ability to query real DB data for specific cities instead of silently falling back to mock).

- OBSERVATION: `aiService.ts:14` and `chat.py:17-19` — `ChatRequest` in Python accepts `session_id: str | None = None` and implements server-side multi-turn history: `session_id = req.session_id or create_session(); append_to_session(session_id, "user", req.message)`. The response at `chat.py:86` returns `{"text": text, "sessionId": session_id}`. However, `aiService.ts:getChatResponse:14` sends only `body: JSON.stringify({ message })` — no `session_id` field — and `aiService.ts:24` reads only `data.text`, discarding the returned `sessionId`. Consequently: (a) every `getChatResponse` call creates a brand-new server session, so the server never accumulates conversation history; (b) `ChatView.tsx:41` maintains a visible message history in React state, creating the illusion of multi-turn chat, but each call sends only the current user message — the server's Claude call has no knowledge of prior turns; (c) server sessions are created and abandoned on every request, wasting session storage. PROPOSAL: Extend `getChatResponse` in `aiService.ts` to accept an optional `sessionId` and return `{ text, sessionId }` from the response; update `ChatView.tsx` to store the `sessionId` in a `useRef` after the first message and pass it on subsequent calls — M/M effort (~20 lines across `aiService.ts` + `ChatView.tsx`; enables true server-side multi-turn conversation with Claude rather than single-turn calls wrapped in a fake history UI).

- OBSERVATION: `aqi.rs:123-126` vs `airnow.py:154` vs `useRealtimeAQI.ts:115` — Three data sources use the same JSON field name `o3` (and `no2`, `so2`, `co`) but different physical units: (1) The Rust `generate_readings()` fills `o3: round2(rng.gen_range(0.02..0.08))` — ambient ppm (typical outdoor O₃ range); `no2: round2(rng.gen_range(0.01..0.06))` ppm; `so2: round2(rng.gen_range(0.001..0.015))` ppm; `co: round2(rng.gen_range(0.1..1.5))` ppm. (2) `airnow.py:154` normalizes AirNow API data as `o3 = obs_aqi` where `obs_aqi = obs.get("AQI", 0)` — EPA AQI index (0–500 scale). (3) `useRealtimeAQI.ts:115` mock generates `o3: Math.round(20 + Math.random() * 40)` — AQI index scale (20–60). All three serialize to the same field name, but Rust emits ~0.05 while AirNow and mock emit ~30–60 — a factor of ~600× difference. Any code that displays `o3` alongside `aqi` or `pm25` (which are consistently on the AQI/µg scale) will show wildly inconsistent values depending on which data source is active. `useLiveData.ts:111` declares `o3: number` with no units; the `useRealtimeAQI.ts:299` inline type has the same. PROPOSAL: Standardize all three sources on AQI index units for `o3` by adding an O₃-to-AQI breakpoint conversion in `aqi.rs` (parallel to the existing `pm25_to_aqi` at `purpleair.rs:202`) and adding a JSDoc `@unit AQI (0–500)` annotation to `o3`, `no2`, `so2`, `co` in `useLiveData.ts:110-113` — L/M effort (~25 lines in Rust + 4 annotation lines; eliminates a factor-of-600 unit inconsistency in o3 display when switching between Rust and AirNow/mock sources).

- OBSERVATION: `useLiveData.ts:102-119` `AqiReading` interface vs Rust `AqiReading` struct (`aqi.rs:17-41`) — The TypeScript `AqiReading` interface declares 16 fields but the Rust struct, serialized with `#[serde(rename_all = "camelCase")]`, emits up to 20 fields in every payload: `no2`, `so2`, `co`, `color` (the category hex string), and optionally `rawSensorCount` are present in every Rust response but absent from the TS type. As a result: (a) `useAqiSnapshot()` consumers casting to `AqiSnapshot` silently drop `no2`/`so2`/`co`/`color`/`rawSensorCount` at the type level even though they are present at runtime; (b) any future widget that adds `reading.no2` receives a TypeScript compile error even though the value exists at runtime; (c) `useRealtimeAQI.ts:288-306` also declares the SSE payload inline without `color` or `rawSensorCount`. The same structural gap applies: `AirQualityMapView.tsx` shows PM2.5 and O₃ in tooltips but cannot access NO₂ without an unsafe cast. PROPOSAL: Add `no2: number; so2: number; co: number; color: string; rawSensorCount?: number` to `AqiReading` in `useLiveData.ts:119` and add `color: string; rawSensorCount?: number` to the inline type in `useRealtimeAQI.ts:306` — L/L effort (~7 lines; makes the full Rust payload visible to TypeScript and enables future widgets to display NO₂/SO₂/CO without unsafe casts).

**Findings:**

- OBSERVATION: `vite.config.ts:35-40` — The `test` block declares `globals: true`, `environment: 'jsdom'`, `setupFiles`, and `css: true` but has no `coverage` sub-object. The `package.json:13` script `"test:coverage": "vitest --coverage"` runs without error but with default Vitest coverage settings: no `thresholds` (so 0% line/branch/function coverage on any file silently passes), no `include` pattern (so test files themselves and config files may be included in coverage totals, inflating numbers), and no `reporter` override (default `text` only, no `lcov` for CI upload). The `test:run` script at `package.json:12` runs `vitest run` with no `--coverage`, meaning CI never generates coverage data unless `test:coverage` is explicitly run — and even then it cannot fail the build. Files with genuinely zero test coverage — `utils/interpolation.ts`, `utils/colorScales.ts`, `utils/weatherUtils.ts`, `utils/geo3d.ts`, `services/AirQualityService.ts`, `services/WeatherService.ts`, `services/aiService.ts`, `services/dataService.ts`, `hooks/useLiveData.ts`, `hooks/useRealtimeAQI.ts`, `hooks/useNormalizedData.ts`, `hooks/useViewport.ts`, `hooks/useDashboardData.ts`, all `components/3d/*` — are invisible to CI. PROPOSAL: Add a `coverage` key to the `test` block in `vite.config.ts`: `{ reporter: ['text', 'lcov'], include: ['hooks/**', 'services/**', 'utils/**', 'contexts/**'], thresholds: { lines: 60, functions: 60 } }`; change `test:run` to `vitest run --coverage` so CI generates and enforces minimum coverage on each push — M/L effort (~8 lines in `vite.config.ts`; makes zero-coverage modules visible and enforceable in CI).

- OBSERVATION: `utils/interpolation.ts:356-370` — `generateInterpolatedMatrix` computes grid coordinates as `lat = bounds.south + (y / (height - 1)) * latRange` and `lng = bounds.west + (x / (width - 1)) * lngRange`. When `height === 1`, `height - 1 === 0`, producing `y / 0 = NaN` for the latitude of every pixel; similarly for `width === 1`. The `NaN` propagates through `interpolateIDW` (which computes distances as `Math.sqrt(Math.pow(NaN - target, 2) + ...)`, yielding `NaN` distance and weights of `1 / NaN = NaN`), resulting in a `Float32Array` filled entirely with `NaN`. The GPU texture generated from this array (`createDataTexture` in `colorScales.ts`) would render as all-black (the `hexToRgb` fallback for NaN-positioned color lookups returns `{r:0,g:0,b:0}`). The current sole caller `TerrainMesh.tsx:239` passes `128, 128`, so the bug is latent — but the function signature accepts arbitrary dimensions with no guard, and there are zero unit tests for `generateInterpolatedMatrix`. PROPOSAL: Add a guard at `interpolation.ts:354` — `if (height < 2 || width < 2) throw new Error('generateInterpolatedMatrix requires width and height ≥ 2')` — and add unit tests covering the `width=128, height=128` normal path plus the `height=1` and `width=1` edge cases — L/L effort (~5 lines guard + 6 test assertions; prevents silent NaN textures if the function is ever called from a new codepath with a single-row/column dimension).

- OBSERVATION: `utils/weatherUtils.ts:36-55` — `calculateSunTimes` calls `Math.acos(-Math.tan(latRad) * Math.tan(declinationRad))` without guarding the argument. `Math.acos` returns `NaN` when its argument is outside `[-1, 1]`: at polar latitudes (>66.5°) during solstice, `tan(lat) * tan(±23.45°)` exceeds 1 (polar night/midnight sun). The NaN propagates through `hourAngleDeg`, `sunriseHour`, `sunsetHour`, and into `formatTime` — which produces `"NaN:aN undefined"` (since `Math.floor(NaN) = NaN`, `NaN % 12 = NaN`, `NaN >= 12` is false). The San Joaquin Valley (lat 34.8–38.5°) is safely below the critical angle, but the function is exported without a documented valid-latitude contract, and any caller with a different study region or a programmatic error in latitude input would silently receive malformed time strings. Additionally, `calculateET0` uses `solarRadiation * 0.0864` to convert W/m² to MJ/m²/day — correct for a daily timestep — but the parameter is unnamed (`solarRadiation: number`) with no unit annotation; a caller passing instantaneous W/m² directly (without multiplying by seconds per day) would get ET₀ values 10⁴× too small, silently. Zero tests for any function in `weatherUtils.ts`. PROPOSAL: Add an input guard in `calculateSunTimes` before `Math.acos` (`const arg = -Math.tan(latRad) * Math.tan(declinationRad); if (arg >= 1) return { sunrise: 'Polar night', sunset: 'Polar night', dayLength: 0 }; if (arg <= -1) return ...midnight sun...`) and add a `tests/weatherUtils.test.ts` covering all four exported functions, including the polar edge cases and the heat-index/wind-chill transition boundaries in `calculateFeelsLike` — L/L effort (~15 lines tests + 4-line guard; prevents silent malformed output for any latitude outside SJV).

- OBSERVATION: `services/AirQualityService.ts:30-35` and `services/WeatherService.ts:44-49` — Both services implement the Singleton pattern via `private static instance: AirQualityService` / `private static instance: WeatherService` stored directly on the class. Vitest runs test files in the same Node.js worker process and reuses the module registry across files by default (unless `isolate: true` is set, which is not configured in `vite.config.ts`). This means: once any test file calls `AirQualityService.getInstance()`, the singleton `instance` is set; all subsequent test files in the same worker share the same cached instance — including its `cachedReadings` and `cacheTimestamp` fields. A test that expects cold-cache behavior (first fetch) would silently pass a warm-cache guard (`(now - this.cacheTimestamp) < 4000`) if a previous test set the cache within 4 seconds of wall-clock time. Neither class exposes a `resetForTesting()` method, `clearCache()`, or any way to reset the instance, and neither class is injected as a dependency anywhere — both are imported and used via `getInstance()` throughout `AirQualityMapView.tsx` and `Dashboard.tsx`. Without test isolation, any future test suite for these services will experience order-dependent failures that are difficult to debug. PROPOSAL: Add `static resetForTesting(): void { AirQualityService.instance = undefined as any; }` to both classes; call it in `afterEach` in any service test file; add a `tests/services.test.ts` with at minimum: cache-hit path (second call within TTL returns same data without fetch), cache-miss path (call after TTL re-fetches), and error-propagation path (fetch failure throws) — M/L effort (~6 lines across 2 service files + 15-line test; prevents hidden test pollution once service tests are written and documents the cache boundary behavior).

**Proposed actions:**
