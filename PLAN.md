**Findings:**

- OBSERVATION: `chat.py:88`, `deep_analysis.py:87`, `low_latency.py:39`, `predict.py:93`, `predict.py:192`, `predictive_analysis.py:99` — Six error-handling `except` blocks across the AI route handlers call `traceback.print_exc()` to report exceptions. `traceback.print_exc()` writes the formatted traceback directly to the Python process's `sys.stderr` as unformatted plaintext. When Uvicorn runs inside Docker, this stderr output is captured by the container runtime and forwarded to its logging pipeline — but it arrives as raw multiline text with no log level field, no timestamp, no logger name, and no structured JSON keys. Consequently: (a) log aggregators (Loki, Fluentd, Elastic, CloudWatch) cannot parse these error events as structured records or filter them by level; (b) it is impossible to compute a per-endpoint error rate in a log query (e.g., "how many 500s did `/api/deep-analysis` emit in the last hour?"); (c) the output is inconsistent with the structured `logger.info()` / `logger.warning()` calls made elsewhere in the same codebase (`cache.py:70,72`, `middleware.py:77`, `predict.py:45,47,49`), which go through the standard logging system. The correct replacement is `logger.exception("Failed to get chat response")` — `logging.Logger.exception()` automatically attaches the current exception and its traceback to the log record via `exc_info=True`, routes through all configured handlers, and is emittable as structured JSON when `python-json-logger` or similar is added. PROPOSAL: Replace `traceback.print_exc()` at `chat.py:88`, `deep_analysis.py:87`, `low_latency.py:39`, `predict.py:93,192`, `predictive_analysis.py:99` with `logger = logging.getLogger(__name__)` at module level and `logger.exception("...")` at each call site; remove `import traceback` from each file — L/L effort (~12 line changes across 5 files; makes all AI-route exceptions observable through the standard logging pipeline, unblocks per-endpoint error rate metrics, and brings error logging into parity with the rest of the codebase).

- OBSERVATION: `health.py:6-12` and `geointellisense-ingestion/src/routes/health.rs:11-17` — Both service health endpoints return a static success response unconditionally, with no live dependency probe. The Python analytics service starts a TimescaleDB connection pool at `main.py:49` (`await get_pool()`), a Redis client at `main.py:50` (`await get_redis()`), and three background polling tasks at `main.py:51-54` (`start_water_polling`, `start_fire_polling`, `start_inversion_polling`) — none of these is checked by `GET /api/health`. The ingestion service starts a PostgreSQL pool and Redis connection at `main.rs:30-34` — the Axum health handler at `health.rs:11` never queries either. In practice: if TimescaleDB becomes unreachable after startup (e.g., after a failover), `GET /api/health` still returns `{"status": "ok", "service": "geointellisense-analytics"}` with HTTP 200. A Kubernetes readiness probe configured against `/api/health` would continue routing requests to the broken pod indefinitely. The consequence is not merely missed alerting — in a Kubernetes or load-balanced deployment, traffic continues hitting the failed instance until a human detects it via user-reported errors. The Python fix is approximately 8 lines: add a `try`/`except` block that executes `await (await get_pool()).fetchval('SELECT 1')` and `await (await get_redis()).ping()` and returns `{"status": "degraded", "reason": "..."}` with HTTP 503 on failure. The Rust fix is similar using `sqlx::query_scalar("SELECT 1")` on the pool. PROPOSAL: Add live DB and Redis pings to `health.py` returning 503 on failure; do the same for `health.rs` — L/M effort (~8-12 lines per service; converts the health endpoint from a static stub into an operational readiness probe; prerequisite for any Kubernetes readiness gate or SLO alerting).

- OBSERVATION: `chat.py:43,70`, `deep_analysis.py:33,61`, `low_latency.py:31`, `predictive_analysis.py:91` — None of the `client.messages.create()` call sites log the `resp.usage` object returned by the Anthropic API. Every Anthropic API response includes `resp.usage.input_tokens` and `resp.usage.output_tokens`; extended-thinking responses additionally include `resp.usage.cache_creation_input_tokens` and `resp.usage.cache_read_input_tokens`. Without logging these counts: (a) there is no way to attribute Anthropic API cost to specific endpoints — a single `POST /api/deep-analysis` call using `claude-opus-4-6` with `max_tokens=40000` and `budget_tokens=32768` across up to 3 tool-use rounds (`deep_analysis.py:48`) can consume ≈218k output+thinking tokens per request, yet this is invisible in any log or metric; (b) there is no observable signal if token consumption spikes (e.g., because the AI context injected at `claude.py:93-97` grows unexpectedly large, consuming most of the 200k-token context window); (c) developers cannot identify which query patterns are most expensive, making prompt optimization a blind exercise. The fix requires one `logger.info()` call after each `client.messages.create()` response, e.g. `logger.info("claude usage endpoint=chat input=%d output=%d", resp.usage.input_tokens, resp.usage.output_tokens)` — L/L effort (~5 lines total; provides per-endpoint token cost visibility with zero external dependencies and enables cost attribution, anomaly detection, and prompt optimization).

- OBSERVATION: `main.py:1-117` (full file) — The Python analytics service contains no call to `logging.basicConfig()`, `logging.config.dictConfig()`, or any other logging configuration. Python's `logging` module defaults to a root logger at WARNING level with a `lastResort` handler that writes WARNING-and-above to stderr. The result is that every `logger.info()` and `logger.debug()` call in the codebase is silently discarded at runtime: cache HIT/MISS at `cache.py:70,72`, rate-limit-failure-allowed at `middleware.py:77`, retrain-scheduler-started at `predict.py:33`, model-retrain-complete at `predict.py:45,47,49`, and the weekly retrain log at `predict.py:49` all emit no output in production. The Rust ingestion service correctly configures `tracing_subscriber::fmt().with_env_filter(EnvFilter::try_from_default_env()...)` at `main.rs:23-25`, making its log level runtime-configurable via `RUST_LOG` — the Python service has no equivalent. In addition, Uvicorn's own access log is separate from the application logger; without configuring the application logger, a developer running the service sees Uvicorn request lines (`INFO: POST /api/chat HTTP/1.1 200 OK`) but no application-level context about what happened inside the request handler. PROPOSAL: Add four lines near the top of `main.py` before the `FastAPI()` instantiation: `import logging; logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s %(message)s")` (or read the level from an env var for runtime control, e.g. `level=getattr(logging, os.getenv("LOG_LEVEL", "INFO").upper(), logging.INFO)`) — L/L effort (~4 lines; activates all existing `logger.info()` calls throughout the codebase, making cache hit rates, rate-limit events, and background task lifecycle visible in production logs without any other code changes).

**Proposed actions:**

### Run #249 — 2026-06-10 — Lens: Security
**Scope:** Eighteenth security pass. Files examined: `geointellisense-analytics/app/middleware.py` (full), `geointellisense-analytics/app/routes/admin.py` (full), `geointellisense-analytics/app/main.py` (full), `geointellisense-analytics/app/config.py` (full), `geointellisense-analytics/app/routes/epa_aqi.py` (full), `geointellisense-analytics/app/routes/demographics.py` (full), `geointellisense-analytics/app/routes/explore.py` (full), `geointellisense-analytics/app/routes/chat.py` (full), `geointellisense-analytics/app/routes/predictive_analysis.py` (full), `geointellisense-analytics/app/routes/grounded_search.py` (full), `geointellisense-analytics/app/routes/low_latency.py` (full). Cross-checked against Active Recommendations and archived security runs #9, 24, 39, 54, 69, 84, 99, 114, 129, 144, 159, 174, 189, 204, 219, 234.

**Findings:**

- OBSERVATION: `epa_aqi.py:77–102` and `demographics.py:149–162` — Two POST endpoints that trigger long-running external-API backfill tasks are completely unauthenticated. `POST /api/epa-aqs/backfill` at `epa_aqi.py:77` accepts arbitrary `start_year` and `end_year` query parameters with no range validation and no auth check; a caller can pass `start_year=1900&end_year=2030` to trigger 130 years × 8 SJV counties × 3 EPA parameter codes = 3,120+ sequential EPA AQS API calls, exhausting the configured `EPA_AQS_EMAIL`/`EPA_AQS_KEY` quota and holding `_backfill_task` indefinitely. `POST /api/demographics/backfill` at `demographics.py:149` is similarly unauthenticated and will trigger Census Bureau ACS API calls for all SJV counties (no county specified = all-SJV). Neither endpoint requires an `x-api-key` or `x-admin-token` header. Compare with `POST /api/predict/train` (Active Rec #3) which is also unauthenticated but only burns local compute; these two backfill endpoints burn paid third-party API quotas that may have hard usage limits. PROPOSAL: Add `check_ai_auth(request)` (or a lighter `_check_admin` call) to both POST backfill endpoints — L/L effort (~4 line changes across 2 files; consistent with how `/api/admin/cache/flush` already guards its mutation with `_check_admin`). Also add `if end_year - start_year > 5:` validation at `epa_aqi.py:86` — L/L.

- OBSERVATION: `middleware.py:106` and `admin.py:14` — Both `check_ai_auth()` at `middleware.py:106` (`if api_key == settings.admin_token:`) and `_check_admin()` at `admin.py:14` (`if token != settings.admin_token:`) compare the admin token using Python's built-in string `==`/`!=` operators. Python's Unicode string comparison short-circuits at the first differing byte, meaning the comparison exits faster when more leading bytes are wrong — on a co-located network with sub-millisecond jitter, an attacker can enumerate the correct admin token one character at a time by measuring response time differences across thousands of requests (the standard "timing oracle" technique; documented in OWASP A07:2021 and Python's own `hmac` module docs). While exploiting this over the internet requires overcoming substantial network noise, the fix is trivial: Python's standard library provides `hmac.compare_digest(a, b)` which performs a constant-time comparison with guaranteed identical execution time regardless of how many bytes match. The same issue applies to the rate-limit `_client_id()` function at `middleware.py:37` which uses `hashlib.md5()` — MD5 is cryptographically broken and should not be used to derive a client identifier for security-relevant rate-limit keys; `hashlib.blake2s()` or even `sha256()[:12]` would be appropriate. PROPOSAL: Replace `api_key == settings.admin_token` at `middleware.py:106` and `token != settings.admin_token` at `admin.py:14` with `hmac.compare_digest(api_key, settings.admin_token)` (add `import hmac` at both files) — L/L effort (~2 line changes + 2 imports; eliminates timing oracle for admin token, costs zero performance). Replace `hashlib.md5` at `middleware.py:37` with `hashlib.blake2s` — L/L (~1 word change).

- OBSERVATION: `main.py:69–78` — When `settings.admin_token` is empty (dev mode), `_allowed_origins` is reassigned to `["*"]` at `main.py:70`. However, `allow_credentials=True` at `main.py:77` is unconditional. The combination of `allow_origins=["*"]` (i.e., `allow_all_origins=True`) with `allow_credentials=True` is explicitly prohibited by RFC 6454 §6.3 and the WHATWG Fetch Living Standard §4.7: `Access-Control-Allow-Origin: *` MUST NOT be accompanied by `Access-Control-Allow-Credentials: true` because it would allow any origin to read credentialed responses. Starlette's `CORSMiddleware.__init__` (versions ≥0.27.0, i.e., FastAPI ≥0.100) raises `ValueError: Cannot use allow_credentials=True with allow_origins=['*']` at application startup — meaning any developer who runs the analytics service without setting `ADMIN_TOKEN` will see the server fail to start with an unhandled exception in `lifespan()`. Even with Starlette versions that silently suppress the error, the browser will reject responses because the browser enforces the CORS spec independently. Notably, `allow_credentials=True` is unnecessary here anyway: the app uses `x-api-key` header auth (not cookies), and non-simple CORS requests with custom headers only require `allow_headers=["x-api-key", ...]` — `allow_credentials` is not needed for header-based auth. PROPOSAL: Remove `allow_credentials=True` from `main.py:77` entirely (or set it to `False`) — L/L effort (~1 line change; eliminates the startup crash in dev mode and removes a CORS spec violation, with no loss of functionality since `x-api-key` auth does not use credentials mode).

- OBSERVATION: `explore.py:41,151–160` — `GET /api/analysis/explore` accepts a `bucket: str` parameter (default `"1 day"`) with no whitelist validation. This string is passed as `$1::interval` to TimescaleDB's `time_bucket()` in five separate `pool.fetch()` calls at `explore.py:151–217`. While `bucket` is used as a properly parameterized value (not string-interpolated), it is not restricted to a set of reasonable granularities. A caller who passes `bucket=1+second` (a perfectly valid PostgreSQL interval) combined with `days=365` (the maximum, validated by `ge=1, le=365`) will cause `time_bucket()` to produce one row per second for 365 days = 31,536,000 rows from `sensor_readings` — none of the five `_query_source` queries has a `LIMIT` clause. asyncpg will attempt to deserialize and allocate a Python dict for each of the ~31.5 million rows, causing memory exhaustion in the analytics process. The `sources` query parameter IS properly whitelisted at `explore.py:44` (`if s.strip() in SOURCES_META`), so there is no SQL injection risk; the vulnerability is purely a resource-exhaustion DoS in the time-bucket dimension. PROPOSAL: Replace `bucket: str = Query(...)` at `explore.py:41` with `bucket: Literal["1 hour", "6 hours", "1 day", "1 week", "1 month"] = Query("1 day", ...)` (add `from typing import Literal`) — L/L effort (~2 line changes; eliminates the unbounded result-set DoS while preserving all currently documented granularities, consistent with the endpoint's own description "1 hour, 6 hours, 1 day").

**Proposed actions:**
- Add auth guard (`_check_admin` or `check_ai_auth`) to `epa_aqi.py:77` and `demographics.py:149`; add `if end_year - start_year > 5: return 400` to `epa_aqi.py:86` — L/L effort (~6 lines; prevents quota exhaustion of EPA AQS and Census API credentials)
- Replace `==` at `middleware.py:106` and `!=` at `admin.py:14` with `hmac.compare_digest()`; replace `hashlib.md5` at `middleware.py:37` with `hashlib.blake2s` — L/L effort (~3 changes; eliminates timing oracle for admin token)
- Remove `allow_credentials=True` at `main.py:77` — L/L effort (~1 line; fixes startup crash in dev mode, removes CORS spec violation)
- Replace `bucket: str` at `explore.py:41` with `bucket: Literal[...]` — L/L effort (~2 lines; eliminates unbounded time-bucket DoS)

### Run #248 — 2026-06-10 — Lens: Data pipeline integrity
**Scope:** Seventeenth data-pipeline-integrity pass. Files examined: `geointellisense-ingestion/src/broadcast.rs` (full), `geointellisense-ingestion/src/purpleair.rs` (full), `geointellisense-ingestion/src/db/persist.rs` (full), `geointellisense-ingestion/src/usgs.rs` (full), `geointellisense-analytics/app/http_client.py` (full), `geointellisense-analytics/app/clients/airnow.py` (full), `geointellisense-analytics/app/clients/nasa_firms.py` (full), `geointellisense-analytics/app/routes/fires.py` (full), `geointellisense-analytics/app/source_toggles.py` (full). Cross-checked against Active Recommendations and archived data-pipeline runs #8, 23, 38, 53, 68, 83, 98, 113, 128, 143, 158, 173, 188, 203, 218, 233.

**Findings:**

- OBSERVATION: `broadcast.rs:68–73` — The PurpleAir polling task uses Redis availability as an implicit gate: when `redis_pa.lock()` resolves to `None` (i.e., Redis could not connect at startup), the loop body executes `continue` on every tick, permanently skipping all PurpleAir API fetches for the lifetime of the process. The comment at line 69 acknowledges this as "fail-safe: don't burn API points," but the consequence is that a Redis connection failure at startup silently freezes PurpleAir data indefinitely — the in-memory `cache_w` is never updated, the broadcast ticker falls back to `aqi::generate_readings()` mock data (`broadcast.rs:111–112`), and operators have no observable signal that live data has stopped. Unlike the `Err` branch at `broadcast.rs:91` which logs a `warn!` per tick, the Redis-gate `continue` at line 71 emits only a `debug!` message. In production, where log verbosity is typically set to `info`, this silent degradation is invisible. The `PurpleAirClient` returned by `cfg.purpleair_api_key.map(...)` at `main.rs:36` indicates the API key is configured and live data is expected, so silently serving mock data is misleading. PROPOSAL: Promote the Redis-unavailable log at `broadcast.rs:71` from `tracing::debug!` to `tracing::warn!` and add a `tracing::info!` on re-entry each time the toggle check succeeds after a prior skip, so operators can distinguish "intentionally disabled" from "Redis is down" in production logs — L/L effort (~2 log-level changes; turns a silent infinite degradation into an observable operational event).

- OBSERVATION: `db/persist.rs:6–34` — `write_readings()` inserts each `AqiReading` with a plain `INSERT INTO sensor_readings ... VALUES (...)` with no `ON CONFLICT DO NOTHING` clause. The broadcast ticker in `broadcast.rs:98–130` fires on every `interval.tick()` — including the tick that fires immediately on startup before any prior readings have a chance to be deduped. If the ingestion service restarts mid-tick (e.g., a Kubernetes pod eviction followed by rapid restart), the last batch of readings can be inserted twice, creating duplicate rows for the same `(time, location_id)`. This is materially different from the earthquake persist at `usgs.rs:167` and the fire persist at `fires.py:239`, both of which use explicit `ON CONFLICT DO NOTHING`. TimescaleDB hypertables do not automatically enforce uniqueness on `(time, location_id)`, so these duplicates accumulate silently. The historical AQI chart queries in `historical_aqi.py:44–101` aggregate over `sensor_readings` using `AVG`; duplicate rows do not skew the average but double-count `COUNT(*)` queries and inflate `raw_sensor_count` history. PROPOSAL: Add `ON CONFLICT (time, location_id) DO NOTHING` to the INSERT at `persist.rs:7` — L/L effort (~1 line; aligns with the duplicate-prevention pattern already used by `usgs.rs` and `fires.py` and prevents duplicate row accumulation on restart); if the unique constraint does not exist, also add `CREATE UNIQUE INDEX IF NOT EXISTS sensor_readings_time_location_idx ON sensor_readings(time, location_id)` to the DB migration — L/M effort total.

- OBSERVATION: `clients/airnow.py:48,64,79` — `AirNowClient` creates its own `httpx.AsyncClient(timeout=15.0)` at `__init__:48` and calls it directly at lines 64 and 79 via `resp = await self._http.get(...)`. The project's shared `http_client.py` (which provides 3-retry exponential backoff, 429 `Retry-After` header respect, and 5xx retry) is NOT used for AirNow calls — it is used by the USGS water client (`usgs_water.py:84`), NASA FIRMS (`nasa_firms.py:73`), and `usgs_water.py:101`. The `http_client.py` docstring explicitly states "All outbound API calls should use this instead of raw httpx." AirNow does occasionally return 5xx responses during maintenance windows; when it does, the direct `resp.raise_for_status()` at `airnow.py:65` immediately surfaces an `HTTPStatusError` to the per-city loop at `get_all_sjv_current():99`, which catches it with a `logger.warning` and skips that city entirely — no retry attempted. Three retries would recover from transient maintenance events without data loss. PROPOSAL: Replace `self._http.get(url, params=params)` at `airnow.py:64` and `airnow.py:79` with `await http_fetch(url, params=params, timeout=15.0)` from `app.http_client`; remove the `self._http` client construction at `airnow.py:48` and the `close()` method at `airnow.py:50–51` — L/L effort (~4 line changes; brings AirNow in line with all other API clients and adds 3-retry protection against transient 5xx).

- OBSERVATION: `routes/fires.py:57,65,67` — `_poll_loop()` updates `_smoke_context` in exactly two places: line 57 (success with fires) and line 65 (success with empty result). When the loop body raises an exception caught at line 66 (`except Exception as e`), `_smoke_context` is neither updated nor cleared — it retains its previous non-empty value. This means if a FIRMS poll fails (e.g., after all 3 retries are exhausted by `http_client.fetch()`), the module-level `_smoke_context` continues to report active fires to Claude AI via `get_current_smoke_context()` at `fires.py:27`, which is called by the AI context builder for every chat and analysis request. A 30-minute poll interval means stale fire context can be injected for up to 30 minutes after fires have been extinguished or the API has become unreachable. Claude may then advise users about smoke impacts from fires that no longer exist. There is also no timestamp attached to `_smoke_context` so callers cannot know when it was last successfully populated. PROPOSAL: Add `_smoke_context = ""` inside the `except` block at `fires.py:67` to clear stale context on poll failure; add a module-level `_smoke_context_updated_at: datetime | None = None` set at line 57 alongside the context update, and include it in the `/api/fires/smoke-context` response at `fires.py:183` — L/L effort (~3 lines; prevents stale fire advisories in AI responses after a FIRMS API failure and gives operators a freshness signal).

**Proposed actions:**
- Promote `broadcast.rs:71` Redis-gate log from `tracing::debug!` to `tracing::warn!`; add `tracing::info!` on successful toggle check after a prior skip — L/L effort (~2 lines; makes silent PurpleAir degradation observable in production logs)
- Add `ON CONFLICT (time, location_id) DO NOTHING` to `persist.rs:7` INSERT — L/L effort (~1 line; prevents duplicate sensor readings on service restart, aligns with usgs.rs and fires.py patterns)
- Replace `self._http.get()` at `airnow.py:64,79` with `http_fetch()` from `app.http_client`; remove `self._http` and `close()` — L/L effort (~4 lines; brings AirNow in line with all other clients and adds retry protection)
- Add `_smoke_context = ""` in `fires.py:67` except block; add `_smoke_context_updated_at` timestamp — L/L effort (~3 lines; prevents stale fire advisories in AI responses after FIRMS API failure)
