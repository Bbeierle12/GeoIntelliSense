- OBSERVATION: `chat.py:51-84` — The tool-use loop correctly builds messages as `get_session_history(session_id) + [{"role": "assistant", "content": resp.content}, {"role": "user", "content": tool_results}]` for each subsequent API call, but after the loop only calls `append_to_session(session_id, "assistant", text)` at line 84, where `text` is the final text output extracted at lines 79-83. The practical consequence: in a multi-turn conversation, `get_session_history(session_id)` on turn 2 returns a sequence of alternating user/text-assistant messages — the tool call interactions from turn 1 are invisible. - OBSERVATION: `claude.py:78-110` — `get_system_with_live_context()` is an `async def` that reads and writes three module-level variables (`_cached_context`, `_cached_context_ts`, `_cached_context` at lines 70-71, 85-89, 95-96) without an `asyncio.Lock`. In FastAPI's asyncio event loop, multiple concurrent coroutines handling simultaneous requests can interleave at every `await` point. The TTL check at `claude.py:88` — `if _cached_context and (now - _cached_context_ts) < 60` — is not atomic: if 10 requests arrive within the same event loop tick after the 60-second TTL expires, all 10 coroutines evaluate `(now - _cached_context_ts) < 60` as `False`, all 10 then `await build_context_text()`, and all 10 fire concurrent calls to `build_live_context()`. `build_live_context()` at `context.py:52-70` runs 8 sequential DB queries (`_get_aqi_context`, `_get_forecast_context`, `_get_fire_context`, `_get_earthquake_context`, `_get_water_context`, `_get_enviroscreen_context`, `_get_inversion_context`, `_get_prediction_context`) plus a Redis scan. 10 simultaneous stampedes = 80+ simultaneous DB queries to TimescaleDB every 60 seconds. The Anthropic API counts `ThinkingBlock` tokens from prior turns toward the input token total for the current call. Each continuation call therefore pays for: (a) prior-round thinking tokens at input rates, and (b) new thinking tokens at output rates. Cost structure for a 3-round tool-use deep-analysis call: round 0 generates up to 32,768 thinking tokens (output billed); round 1 receives those 32,768 as input + generates 32,768 new output; round 2 receives 65,536 as input + generates 32,768 new output; round 3 receives 98,304 as input + generates 32,768 new output. **Findings:**

- OBSERVATION: `geointellisense-analytics/Dockerfile:1` uses `FROM python:3.12-slim` — a floating tag that resolves to the latest Python 3.12.x patch release at build time. Python publishes point releases (e.g., 3.12.8 → 3.12.9 → 3.12.10) that include stdlib bug fixes and security patches; each new release changes the image digest. Two builds of the analytics image from the same Dockerfile weeks apart may produce images running different Python versions with different behavior. There is no mechanism in the repository to detect when the resolved base image changes — no digest pin (`FROM python:3.12-slim@sha256:…`), no CI check, no base-image update policy. This is distinct from the requirements.txt version pinning issue (below): even with exact requirements, the Python runtime itself is floating. In contrast, `geointellisense-ingestion/Dockerfile:1` uses `rust:1.88-slim` which is similarly floating (though Rust's patch releases are less likely to affect stdlib ABI). The analytics service uses `rasterio`, `scipy`, `scikit-learn`, and `numpy` — all sensitive to the underlying Python C extension ABI; a stdlib regression in a Python 3.12.x point release could manifest as a silent runtime failure. PROPOSAL: Pin the analytics Dockerfile base image to a specific patch version (e.g., change `FROM python:3.12-slim` to `FROM python:3.12.10-slim`) and update it intentionally on each Python patch release — L/L effort (~1 line change; eliminates the non-reproducible base image in the analytics service and makes Python version upgrades visible in git history).

- OBSERVATION: `geointellisense-ingestion/Dockerfile:11` uses `RUN cargo build --release 2>/dev/null || true` to pre-compile Cargo dependencies using a dummy `main.rs`. The `2>/dev/null` suppresses ALL stderr from the Cargo compilation step — not just the expected link error that occurs when the real `src/main.rs` is not yet present. If a crate fails to compile due to a missing system header (e.g., if `libssl-dev` were removed from line 3 or a new version of `openssl-sys` requires an additional library), the compilation error is silently discarded, `|| true` marks the layer as succeeded, and the Docker build continues. The subsequent `RUN touch src/main.rs && cargo build --release` at line 14 then fails with a confusing linker error ("undefined reference to `SSL_CTX_new`") rather than the clear compilation error ("error: could not compile `openssl-sys`"). In a CI environment, the resulting 15-minute wait for a Rust build before encountering a cryptic error adds significant debugging time. A safer pattern preserves compilation errors while only suppressing the expected link failure: `RUN cargo build --release; true` (removes the stderr redirect) or more precisely separates the dependency compile phase from the link phase. PROPOSAL: Change `geointellisense-ingestion/Dockerfile:11` from `RUN cargo build --release 2>/dev/null || true` to `RUN cargo build --release 2>&1 | grep -v "^error\[E\].*src/main.rs" || true` — this keeps compilation errors visible while suppressing only the expected dummy-source link failure — L/L effort (~1 line change; surfaces Cargo dependency compilation errors that are currently silently discarded).

- OBSERVATION: `geointellisense-analytics/requirements.txt` uses loose version constraints (`fastapi==0.115.*`, `scikit-learn>=1.5,<1.7`, `scipy>=1.13,<1.15`, `numpy>=1.26,<2.1`) with no lock file in the repository. `analytics/Dockerfile:9-10` runs `pip install --no-cache-dir -r requirements.txt`, which resolves the latest compatible versions at image build time. Two builds of the analytics Docker image from the same source tree on different days can install different package versions if a new minor release has been published (e.g., `scikit-learn 1.6.0` → `scikit-learn 1.6.1`). The repository has no `pip-compile`-generated lock file (`requirements.lock` or `requirements.txt.lock`), no `Pipfile.lock`, and no `poetry.lock`. For the ML pipeline specifically — `aqi_model.py` trains and serializes scikit-learn `RandomForestRegressor` models — a version change in scikit-learn's serialization format between builds would render stored models (`MODEL_DIR=/app/data/models`) unloadable, causing the predictive analysis endpoint to silently fall back to mock predictions with no error. PROPOSAL: Run `pip-compile requirements.txt --output-file=requirements.lock` (or `pip install pip-tools && pip-compile`) and commit the resulting `requirements.lock`; change `analytics/Dockerfile:10` to `pip install --no-cache-dir -r requirements.lock` — M/L effort (~1 Dockerfile line + committed lock file; guarantees reproducible analytics images and makes dependency upgrades intentional and visible in git diff).

- OBSERVATION: `geointellisense-analytics/Dockerfile` has no `RUN mkdir -p /app/data/dem /app/data/landsat /app/data/models` instruction. `docker-compose.yml:93-95` sets `DEM_DATA_DIR=/app/data/dem`, `LANDSAT_DATA_DIR=/app/data/landsat`, and `MODEL_DIR=/app/data/models`; `docker-compose.yml:101-103` mounts named Docker volumes at those three paths. When Docker mounts a named volume to a path that does not exist in the image filesystem, it creates the directory at runtime with `root:root` ownership. Today this is unproblematic because the analytics container runs as root (no `USER` directive in the Dockerfile).
