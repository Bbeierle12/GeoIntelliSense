**Findings:**

- OBSERVATION: `tsconfig.json` has no `strict` flag and no individual strict-mode flags (`noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `alwaysStrict`). TypeScript strict mode has been the recommended baseline for new projects since TypeScript 2.3 (released 2017). The practical impact on this codebase is systemic: (a) Without `noImplicitAny`, untyped variables and parameters silently acquire `any` — `const forecast = []` at `data/dashboardData.ts:196` is typed as `any[]` rather than raising a compile error, and this `any[]` propagates to all 7 `dailyForecast` fields in the `dashboardData` object, then to the `day: any` callback parameters in `useDashboardData.ts:179,223,267,311`. (b) Without `strictNullChecks`, the non-null assertion operator `!` at `useDashboardData.ts:186,230,274,318` (`monthMap.get(monthKey)!`) is vacuous — the compiler already treats `Map.get()` as returning `T` (not `T | undefined`) because it does not model nullable types, making the `!` appear protective while checking nothing. (c) Without `strictFunctionTypes`, callback parameter variance is unsound: a function typed `(value: string) => void` may be silently passed where `(value: string | number) => void` is expected, as in `AccessibleChart.tsx:66`'s `format?: (value: any) => string` pattern. The effective type safety level of the whole frontend is therefore lower than it appears from reading the TypeScript syntax. PROPOSAL: Add `"strict": true` to `tsconfig.json` compilerOptions (~1 line). This will surface compile errors that require correction — primarily adding a `DailyForecastEntry` interface to `data/dashboardData.ts:195`, changing `catch (e: any)` to `catch (e: unknown)` in `AnalysisView.tsx:255`, and adding null guards where `Map.get()` results are used without `!`; the total remediation is approximately 20 targeted annotations — L/M effort total (~1 tsconfig line + ~20 annotation fixes; the highest-leverage type safety improvement possible for the entire project as it enforces all other type checks simultaneously).

- OBSERVATION: `data/dashboardData.ts:195-196` — `generateDailyForecast(location: string, days: number)` has no explicit return type annotation and initializes `const forecast = []` without a type. Without `noImplicitAny` (confirmed absent from `tsconfig.json`), this empty array literal is typed as `any[]`. The function pushes objects with at least 25 distinct fields (`date`, `temp`, `tempMin`, `tempMax`, `humidity`, `windSpeed`, `windDirection`, `windGust`, `feelsLike`, `dewPoint`, `pressure`, `uv`, `precipProb`, `precipAmount`, `precipType`, `cloudCover`, `visibility`, `evapotranspiration`, `solarRadiation`, `aqi`, `pm25`, `sunrise`, `sunset`, `dayLength`, `condition`) — all inferred but never checked. - OBSERVATION: `components/3d/AQI3DScene.tsx:57` — `const controlsRef = useRef<any>(null)`. The `OrbitControls` component imported at line 8 from `@react-three/drei` exposes an instance type of `OrbitControls` from the `three-stdlib` package (which `@react-three/drei` re-exports). The correct ref type annotation is `useRef<import('three-stdlib').OrbitControls>(null)`. Two problems arise from `useRef<any>`: (1) `controlsRef.current.getTarget(target)` at line 70 is completely unchecked — any typo (`controlsRef.current.getTraget(target)`) or API change in `drei`/`three-stdlib` compiles silently and produces a runtime exception inside the `useFrame` callback (which runs 60 times per second, making the error difficult to diagnose from browser logs). - OBSERVATION: `components/AccessibleChart.tsx:66,79` — Two `any` usages in the public prop interface of a component used across the dashboard: (a) `format?: (value: any) => string` in the `DataTableColumn` interface at line 66, and (b) `data: Record<string, any>[]` in the `AccessibleChartProps` interface at line 79. The `format?: (value: unknown) => string` fix (using `unknown` instead of `any`) forces each formatter to perform type checks or casts before use, preventing wrong-typed formatters. A generic `AccessibleChart<TRow extends Record<string, unknown>>` would further constrain `columns[i].key` to `Extract<keyof TRow, string>`, catching the `"avgAqi"` vs `"aqi"` class of bug at compile time. PROPOSAL: (a) Immediately change `(value: any) => string` to `(value: unknown) => string` at `AccessibleChart.tsx:66` (~1 line; forces type-safe formatters without changing the call signature); (b) generify the component: replace `interface AccessibleChartProps` with `interface AccessibleChartProps<TRow extends Record<string, unknown>>` and update `data: TRow[]`, `columns: DataTableColumn<TRow>[]`, and `key: Extract<keyof TRow, string>` — M/L effort total (~12 lines; makes the accessible table's column key validated against actual data shape, preventing silent accessibility regressions in the one code path most critical for users relying on screen readers).

**Findings:**

- OBSERVATION: `broadcast.rs:83-97` and `db/persist.rs:8-13` — The broadcast ticker runs every `broadcast_interval_secs` (default: 5 seconds, confirmed by `docker-compose.yml:57`). For every tick it reads the cached PurpleAir readings and replaces their `timestamp` field with `Utc::now()` before persisting: `live.iter().map(|r| AqiReading { timestamp: now, ..r.clone() }).collect()`. These freshly-timestamped rows are then written to `sensor_readings.time` by `persist.rs:13` (`.bind(r.timestamp)`). The same overwrite occurs in `routes/aqi.rs:snapshot` for the `/api/aqi-snapshot` HTTP endpoint. This means `sensor_readings.time` records the DB write time (every 5 seconds), not the actual PurpleAir measurement time. `context.py:_freshness()` at line 31-37 uses the `MAX(sr.time)` from the query at line 237-249 as `last_updated` and computes `age_seconds = (now - last_updated).total_seconds()` — which is always approximately 5 seconds, regardless of when the PurpleAir API was last called. With `purpleair_interval_secs` defaulting to 600 seconds (10 minutes, per `config.rs:15` and `docker-compose.yml:56`), the PurpleAir API may not have been called in up to 599 seconds, but `_freshness()` always returns `{"ageSeconds": ~5, "stale": False, "status": "live"}`. The actual sensor measurement time is never stored anywhere in the system — neither in `sensor_readings` nor in the Redis snapshot. PROPOSAL: Add a `fetched_at` column to `sensor_readings` (TimescaleDB supports additional columns) or store the original PurpleAir `timestamp` from the API response in a separate field; update `broadcast.rs` to use `r.timestamp` (the true measurement time from PurpleAir) for the `fetched_at` column while still using `Utc::now()` for the hypertable partitioning `time` column; update `context.py:_get_aqi_context` to compute freshness from `MAX(fetched_at)` rather than `MAX(sr.time)` — M/M effort (~1 DB migration + 4 Rust lines + 3 Python lines; makes the freshness calculation reflect actual sensor measurement age rather than DB write age, enabling Claude to correctly identify stale data).

- OBSERVATION: `context.py:17` defines `SOURCE_INTERVALS = {"purpleair": 120, ...}` (2-minute freshness threshold for PurpleAir), but `config.rs:15` defines `purpleair_interval_secs` with a default of 600 seconds, and `docker-compose.yml:56` confirms the production default as `${PURPLEAIR_INTERVAL_SECS:-600}`. The staleness threshold in `_freshness()` at `context.py:34` is `stale = age_seconds > interval * 2` — for purpleair this is `120 * 2 = 240 seconds`. If the timestamp-overwrite bug (finding above) were fixed and `fetched_at` reflected real measurement age: data that is 5 minutes old (a normal condition mid-cycle with the 10-minute poll interval) would have `age_seconds = 300 > 240` and be flagged as "stale" to Claude — but it is actually the most recent available data. The freshness label in `build_context_text()` would read "STALE data sources: purpleair" for entirely normal, in-cycle operational conditions, causing Claude to caveat its AQI analysis with staleness warnings on nearly every call even when the system is functioning perfectly. The mismatch is specifically between `context.py` (Python, part of the analytics service) and `config.rs` (Rust, part of the ingestion service) — two services that have no shared configuration source, allowing this drift. For comparison, `SOURCE_INTERVALS["earthquakes"] = 300` correctly matches `earthquake_interval_secs = 300` in `config.rs`, and `SOURCE_INTERVALS["fires"] = 1800` correctly matches `FIRE_TTL = 1800` in `fires.py`. PROPOSAL: Update `context.py:17` to `"purpleair": 600` to match the actual default Rust poll interval; also extract the interval as a shared configuration value injected via environment variable (e.g., read `PURPLEAIR_INTERVAL_SECS` in both Rust and Python from the same `.env`) — L/L effort (~1 line fix + optional env-var DRY-up; ensures freshness labels are accurate when/if the timestamp overwrite bug is fixed).
