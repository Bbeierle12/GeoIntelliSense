### Run #280 — 2026-06-11 — Lens: Observability
**Scope:** Nineteenth observability pass. Files read: `geointellisense-analytics/app/routes/chat.py`, `geointellisense-analytics/app/routes/deep_analysis.py`, `geointellisense-analytics/app/routes/predictive_analysis.py`, `geointellisense-analytics/app/routes/low_latency.py`, `geointellisense-analytics/app/claude.py`, `geointellisense-analytics/app/middleware.py`, `geointellisense-analytics/app/routes/health.py`, `geointellisense-analytics/app/database.py`, `geointellisense-analytics/app/cache.py`, `geointellisense-analytics/app/main.py`, `geointellisense-analytics/app/routes/predict.py`, `geointellisense-analytics/app/ml/aqi_model.py`, `geointellisense-ingestion/src/routes/health.rs`, `geointellisense-ingestion/src/routes/sse.rs`, `geointellisense-ingestion/src/main.rs`, `geointellisense-ingestion/src/db/persist.rs`. Cross-checked against Active Recommendations and archived observability runs #10, 25, 40, 55, 70, 85, 100, 115, 130, 145, 160, 175, 190, 205, 220, 235, 250, 265.

**Findings:**

- OBSERVATION: `chat.py:88`, `deep_analysis.py:87`, `predictive_analysis.py:99`, `low_latency.py:39` — all four AI route exception handlers call `traceback.print_exc()` (Python stdlib) to emit the stack trace, bypassing the `logging` framework entirely. Each module defines a `logger = logging.getLogger(__name__)` but never calls it inside the `except` block. `traceback.print_exc()` writes directly to `sys.stderr`; in production, uvicorn routes application `logging` calls through its log handler (typically JSON to stdout), but stderr is a separate stream that may be discarded, redirected differently, or not aggregated by the same log shipper. As a result, exceptions in the four highest-cost AI routes (Sonnet chat, Opus deep-analysis, Sonnet predictive-analysis, Haiku low-latency) produce no structured log entries and cannot be monitored, filtered, or alerted on by log-based tooling. The error detail IS returned in the HTTP response body (`"details": str(e)`), but the stack trace is unreachable outside raw stderr. PROPOSAL: Replace `traceback.print_exc()` with `logger.exception("<endpoint> error")` in each of the four handlers — `logger.exception` emits the full traceback at ERROR level through the logging framework and does not require the traceback import — L/L effort (4 one-line changes; enables log-based alerting for AI route failures).

- OBSERVATION: `claude.py:271-272` — `execute_tool` (the function that runs Claude's tool calls at runtime) catches all exceptions and returns a JSON error string to Claude, but never calls `logger.warning` or `logger.error`. The module defines `logger = logging.getLogger(__name__)` at `claude.py:8`, but this logger is never used in the tool execution error path. Tool calls are the mechanism by which Claude fetches live environmental data (AQI snapshots, earthquakes, fires, water levels, NWS forecasts). When a tool call fails due to a network timeout, 5xx from a downstream API, or service unavailability, Claude receives a JSON error message and may generate a plausible-sounding but factually incorrect response using stale system-prompt data instead. The application log is completely silent about these failures, making it impossible to diagnose systematic tool failures (e.g., the AQI snapshot endpoint has been timing out for the past hour, so Claude has been answering from stale data) without correlating user-facing response quality degradation. The chat and deep-analysis loops at `chat.py:51-76` and `deep_analysis.py:46-76` may run up to 5 and 3 rounds of tool calls respectively, each silently failing. PROPOSAL: Add `logger.warning("tool %s failed (input=%s): %s", tool_name, tool_input, e)` before the `return json.dumps(...)` at `claude.py:272` — L/L effort (1 line; makes tool failures visible in application logs and enables systematic monitoring of AI data freshness).

- OBSERVATION: `middleware.py:64-75` — `check_rate_limit` returns a 429 `JSONResponse` when a client exceeds the sliding-window limit, but never emits a log entry at any level for the throttle event. `logger = logging.getLogger(__name__)` at `middleware.py:17` is defined but only called for the Redis-failure warning at line 77. As a result, operators cannot tell from application logs alone: (a) which clients or IP addresses are being rate-limited and how frequently; (b) whether the configured thresholds (`ai_chat: 20/min`, `ai_deep: 5/min`, `ai_low_latency: 30/min`) are correctly calibrated or too tight for legitimate users; (c) whether a client is systematically probing or abusing the API. The client identifier is already computed at `middleware.py:46` (`client = _client_id(request)`) and the current request count is available in `count = results[2]`, so all the information needed for a useful log entry exists at the point the 429 decision is made — it is simply never logged. Observing rate-limit events requires scraping HTTP access logs and joining on status code 429, which loses the tier and client-identity context that is available at this level. PROPOSAL: Add `logger.warning("rate_limited tier=%s client=%s count=%d limit=%d", tier, client, count, max_requests)` immediately before the `return JSONResponse(status_code=429, ...)` at `middleware.py:64` — L/L effort (1 line; makes rate-limit events observable with full context: tier, client, current count, and limit).

- OBSERVATION: `health.py:6-12` (Python) and `health.rs:11-17` (Rust) — both health endpoints return `{"status": "ok"}` unconditionally without probing actual dependency health (database pool, Redis connection). In the Python service, `database.py` and `cache.py` each hold a module-level singleton (`_pool`, `_client`) that can fail silently after startup (connection dropped, auth token rotated, DB restarted); the health route never imports or queries these. In the Rust service, `main.rs:30` creates a `PgPool` and `main.rs:33` creates a Redis connection, but `routes/health.rs:11-17` never accesses either. In a containerized deployment (Kubernetes, Docker Swarm, Docker Compose with `healthcheck`), the orchestrator uses the health endpoint to decide whether to route traffic to an instance or restart it. An instance with a severed DB connection or Redis connection still returns HTTP 200, so the orchestrator continues routing traffic to it instead of draining and replacing it. This extends incidents: during a DB failover or Redis restart, degraded instances keep serving user traffic (producing 500 errors from DB calls) instead of being automatically recycled. The fix is a shallow dependency liveness check (a single `SELECT 1` and `PING` call with a short timeout), not a deep health check. PROPOSAL: In `health.py`, import `get_pool` and `get_redis`, issue a `SELECT 1` and `PING` with `asyncio.wait_for(timeout=2.0)`, and return `{"status": "degraded", "db": False, "redis": False}` with HTTP 503 on failure; mirror the pattern in `health.rs` using sqlx's `executor.execute("SELECT 1")` — M/L effort (~20 lines across both files; makes the health endpoint an accurate dependency liveness signal for orchestrators and prevents routing to degraded instances).

**Proposed actions:**
- Replace `traceback.print_exc()` with `logger.exception(...)` in `chat.py:88`, `deep_analysis.py:87`, `predictive_analysis.py:99`, `low_latency.py:39` — L/L effort (4 one-line changes; enables log-based alerting for AI route exceptions)
- Add `logger.warning("tool %s failed: %s", tool_name, e)` at `claude.py:272` before returning the error JSON — L/L effort (1 line; makes Claude tool failures visible in application logs)
- Add `logger.warning("rate_limited tier=%s client=%s count=%d limit=%d", ...)` at `middleware.py:64` — L/L effort (1 line; makes rate-limit events observable with client and tier context)
- Add shallow DB + Redis liveness checks to `health.py:6-12` and `health.rs:11-17` returning HTTP 503 on failure — M/L effort (~20 lines; enables orchestrators to route away from degraded instances)

### Run #279 — 2026-06-11 — Lens: Security
**Scope:** Twenty-first security pass. Files read: `geointellisense-analytics/app/routes/explore.py`, `geointellisense-analytics/app/routes/traffic.py`, `geointellisense-analytics/app/routes/enviroscreen.py`, `geointellisense-analytics/app/routes/calgem.py`, `geointellisense-analytics/app/routes/water_quality.py`, `geointellisense-analytics/app/routes/weather_historical.py`, `geointellisense-analytics/app/routes/elevation.py`, `geointellisense-analytics/app/routes/nws_forecast.py`, `geointellisense-analytics/app/middleware.py`, `geointellisense-analytics/app/routes/admin.py`, `geointellisense-ingestion/src/routes/admin.rs`, `geointellisense-analytics/app/config.py`. Cross-checked against Active Recommendations and archived security runs #9, 24, 39, 54, 69, 84, 99, 114, 129, 144, 159, 174, 189, 204, 219, 234, 249, 264.

**Findings:**

- OBSERVATION: `explore.py:41-43` — `GET /api/analysis/explore` accepts a free-form `bucket: str` parameter with no validation against the documented allowed values ("1 hour, 6 hours, 1 day"). The value is passed as `$1` to PostgreSQL's `time_bucket($1::interval, time)` function. With `days=365` (the maximum) and `bucket=1 second`, PostgreSQL generates up to 31,536,000 time-bucket groups for a GROUP-BY aggregation, saturating database work memory and blocking the executor pool with a single unauthenticated GET request. `GET /api/analysis/explore/csv` at `explore.py:92` has the identical flaw and streams the unbounded result as an in-memory CSV with no payload cap. Neither endpoint has authentication or rate limiting applied — `check_rate_limit` from `middleware.py` is never called in `explore.py`. PROPOSAL: Restrict `bucket` to an explicit `Literal["1 hour", "6 hours", "1 day", "7 days"]` type annotation; add `await check_rate_limit(request, "data_default")` to both explore endpoints — L/L effort (~4 lines; eliminates single-request DB DoS via unbounded time_bucket GROUP BY). — promotes to Active Recommendation #9.

- OBSERVATION: The unauthenticated write surface is far broader than the 2 endpoints noted in Active Rec #9. A full survey of all `@router.post` handlers finds 7 additional unauthenticated backfill/write endpoints: `traffic.py:108` (`POST /api/traffic/backfill` — no auth, no source-toggle guard), `enviroscreen.py:122` (`POST /api/enviroscreen/backfill` — no auth; `counties=all` downloads and DB-imports ~8,000 California census tracts), `calgem.py:132` (`POST /api/calgem/backfill` — no auth, no source-toggle), `water_quality.py:313` (`POST /api/water-quality/backfill` — source-toggle check only, no auth), `weather_historical.py:82` (`POST /api/weather/backfill` — no auth; gated only by `noaa_cdo_token` being set), `elevation.py:232` (`POST /api/elevation/download` — no auth, triggers USGS 3DEP tile downloads), `elevation.py:247` (`POST /api/elevation/tiles/add` — no auth, allows registering arbitrary USGS tiles and immediately downloading them). Combined with the 2 already in Active Rec #9, 9 of 9 backfill endpoints are unauthenticated. PROPOSAL: Apply a shared admin-token guard (mirroring `admin.py:11-16`'s `_check_admin` pattern) to all 9 endpoints — M/M effort (~18 lines; closes the entire unauthenticated write surface using the existing pattern). — extends Active Recommendation #10.

- OBSERVATION: `middleware.py:106` (`if api_key == settings.admin_token`) and `admin.py:15` (`if token != settings.admin_token`) compare authentication tokens using Python's built-in `==` operator, which short-circuits on the first mismatching byte. A timing oracle attack via high-precision latency measurement can recover the admin token one character at a time. Python's `hmac.compare_digest` (stdlib since 3.3) performs constant-time comparison and prevents this class of attack. The same non-constant-time pattern appears in `geointellisense-ingestion/src/routes/admin.rs:28` (`if provided != token`). PROPOSAL: Replace the two Python comparisons with `hmac.compare_digest(api_key or "", settings.admin_token)` at `middleware.py:106` and `admin.py:15`; update the Rust comparison at `admin.rs:28` to use `ring::constant_time::verify_slices_are_equal` — L/L effort (~2–4 lines; closes timing oracle).

- OBSERVATION: `nws_forecast.py:93-130` — `GET /api/forecast?lat=X&lon=Y` makes 2 sequential HTTP requests to `api.weather.gov` for any arbitrary float coordinate pair with no geographic bounding check and no rate limiting. A caller sweeping unique lat/lon pairs at 60+/min can fan out 120+ simultaneous HTTP connections to NWS, risking an IP-level ban that would disable weather forecasts for all users. The NWS `User-Agent` at `nws_forecast.py:11` explicitly identifies the server, making per-IP bans trivial to apply. The 1-hour cache at `nws_forecast.py:95` only deduplicates identical rounded coordinates; a grid sweep bypasses it entirely. `check_rate_limit` is never called from `nws_forecast.py`. PROPOSAL: Add `await check_rate_limit(request, "data_default")` to the ad-hoc forecast path; add CONUS bounds validation (`24 ≤ lat ≤ 50`, `-125 ≤ lon ≤ -66`) rejecting non-CONUS coordinates before the NWS call — L/L effort (~4 lines; prevents NWS IP ban).

**Proposed actions:**
- Restrict `bucket` to a `Literal` allowlist and add `check_rate_limit` to both endpoints in `explore.py:41-43,92` — L/L effort (~4 lines; eliminates single-request DB DoS) — references Active Rec #9
- Apply `_check_admin` guard to all 9 unauthenticated backfill/write endpoints across `traffic.py`, `enviroscreen.py`, `calgem.py`, `water_quality.py`, `weather_historical.py`, `elevation.py` — M/M effort (~18 lines) — references Active Rec #10
- Replace `==` token comparison with `hmac.compare_digest` at `middleware.py:106` and `admin.py:15`; fix Rust `admin.rs:28` — L/L effort (~2–4 lines; closes timing oracle)
- Add `check_rate_limit` and CONUS bounds guard to `nws_forecast.py:93` — L/L effort (~4 lines; prevents NWS IP ban)
