**Findings:**

- OBSERVATION: `broadcast.rs:83-97` and `db/persist.rs:8-13` — The broadcast ticker runs every `broadcast_interval_secs` (default: 5 seconds, confirmed by `docker-compose.yml:57`). For every tick it reads the cached PurpleAir readings and replaces their `timestamp` field with `Utc::now()` before persisting: `live.iter().map(|r| AqiReading { timestamp: now, ..r.clone() }).collect()`. These freshly-timestamped rows are then written to `sensor_readings.time` by `persist.rs:13` (`.bind(r.timestamp)`). The same overwrite occurs in `routes/aqi.rs:snapshot` for the `/api/aqi-snapshot` HTTP endpoint. This means `sensor_readings.time` records the DB write time (every 5 seconds), not the actual PurpleAir measurement time. `context.py:_freshness()` at line 31-37 uses the `MAX(sr.time)` from the query at line 237-249 as `last_updated` and computes `age_seconds = (now - last_updated).total_seconds()` — which is always approximately 5 seconds, regardless of when the PurpleAir API was last called. With `purpleair_interval_secs` defaulting to 600 seconds (10 minutes, per `config.rs:15` and `docker-compose.yml:56`), the PurpleAir API may not have been called in up to 599 seconds, but `_freshness()` always returns `{"ageSeconds": ~5, "stale": False, "status": "live"}`. The actual sensor measurement time is never stored anywhere in the system — neither in `sensor_readings` nor in the Redis snapshot. PROPOSAL: Add a `fetched_at` column to `sensor_readings` (TimescaleDB supports additional columns) or store the original PurpleAir `timestamp` from the API response in a separate field; update `broadcast.rs` to use `r.timestamp` (the true measurement time from PurpleAir) for the `fetched_at` column while still using `Utc::now()` for the hypertable partitioning `time` column; update `context.py:_get_aqi_context` to compute freshness from `MAX(fetched_at)` rather than `MAX(sr.time)` — M/M effort (~1 DB migration + 4 Rust lines + 3 Python lines; makes the freshness calculation reflect actual sensor measurement age rather than DB write age, enabling Claude to correctly identify stale data).

**Findings:**

- OBSERVATION: `chat.py:51-84` — The tool-use loop correctly builds messages as `get_session_history(session_id) + [{"role": "assistant", "content": resp.content}, {"role": "user", "content": tool_results}]` for each subsequent API call, but after the loop only calls `append_to_session(session_id, "assistant", text)` at line 84, where `text` is the final text output extracted at lines 79-83. The intermediate assistant messages (which contain `tool_use` content blocks) and user messages (which contain `tool_result` blocks) are never written back to the session via `append_to_session`. The practical consequence: in a multi-turn conversation, `get_session_history(session_id)` on turn 2 returns a sequence of alternating user/text-assistant messages — the tool call interactions from turn 1 are invisible. When turn 2's initial API call is made, Claude's context shows: `[user:turn1_message, assistant:"The AQI near Fresno is 78..."]` with no evidence that Claude fetched live data to generate that answer. Claude may therefore: (a) re-invoke `get_air_quality` in turn 2 to answer a follow-up question it could have answered from turn-1 context; (b) appear inconsistent if the live data changed between turns 1 and 2; (c) miss that the prior turn had tool failures (tool_result errors are also not persisted). PROPOSAL: After extracting the final `text` at `chat.py:79-83`, also append all intermediate assistant+tool_result pairs to the session history — change line 84 to first call `append_to_session(session_id, "assistant", [tool_use_blocks])` + `append_to_session(session_id, "user", tool_results)` for each tool round before appending the final text response — M/L effort (~8 lines; preserves complete tool-call context in multi-turn sessions, preventing redundant tool invocations and context loss).

- OBSERVATION: `claude.py:78-110` — `get_system_with_live_context()` is an `async def` that reads and writes three module-level variables (`_cached_context`, `_cached_context_ts`, `_cached_context` at lines 70-71, 85-89, 95-96) without an `asyncio.Lock`. In FastAPI's asyncio event loop, multiple concurrent coroutines handling simultaneous requests can interleave at every `await` point. The TTL check at `claude.py:88` — `if _cached_context and (now - _cached_context_ts) < 60` — is not atomic: if 10 requests arrive within the same event loop tick after the 60-second TTL expires, all 10 coroutines evaluate `(now - _cached_context_ts) < 60` as `False`, all 10 then `await build_context_text()`, and all 10 fire concurrent calls to `build_live_context()`. `build_live_context()` at `context.py:52-70` runs 8 sequential DB queries (`_get_aqi_context`, `_get_forecast_context`, `_get_fire_context`, `_get_earthquake_context`, `_get_water_context`, `_get_enviroscreen_context`, `_get_inversion_context`, `_get_prediction_context`) plus a Redis scan. 10 simultaneous stampedes = 80+ simultaneous DB queries to TimescaleDB every 60 seconds. Additionally, there is no `asyncio.wait_for()` timeout on `build_context_text()` — if TimescaleDB is under heavy load during the stampede it caused, all 10 concurrent AI API calls block indefinitely waiting for context construction, starving all incoming requests. PROPOSAL: Add a module-level `_context_lock: asyncio.Lock = asyncio.Lock()` at `claude.py:72` and wrap the cache-miss path in `async with _context_lock:`, re-checking the TTL inside the lock to implement double-checked locking (~8 lines); also wrap `build_context_text()` in `asyncio.wait_for(..., timeout=5.0)` (~2 lines) — M/L effort total (~10 lines; prevents stampede and bounds context-build latency, protecting the DB and ensuring AI requests are never blocked indefinitely by a slow DB).

- OBSERVATION: `grounded_search.py:12-16,79` and `grounded_maps.py:86` — The `groundingChunks` field in both response payloads is always `[]`. The field name `groundingChunks` is the exact response field used by Google's Vertex AI Grounding API, and the endpoint names `grounded-search` and `grounded-maps` match Google Gemini's "grounded generation" terminology. These routes appear to have been migrated from a Google Gemini implementation without replacing the grounding infrastructure. `SEARCH_SUFFIX` at `grounded_search.py:12-16` instructs Claude to "cite specific sources, studies, or data points you reference" and "Format citations as inline references with titles and URLs where possible." However, the `TOOLS` list in `claude.py:127-214` contains only five geospatial data tools (`get_air_quality`, `get_earthquakes`, `get_active_fires`, `get_water_levels`, `get_weather_forecast`) — no web search, no retrieval tool. Claude responds to the citation instruction by producing plausible-looking inline citations drawn from its training data, but has no mechanism to verify whether a URL is current or even exists.
