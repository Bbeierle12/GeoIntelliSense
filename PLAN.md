### Run #258 — 2026-06-11 — Lens: Dependency health

**Findings:**

- OBSERVATION: `node_modules/shell-quote@1.8.3` (devDependency of `concurrently@9.2.1`, declared at `package.json:devDependencies.concurrently:"^9.1.2"`) — GHSA-w7jw-789q-3m8p, **critical** severity. `shell-quote`'s `quote()` function does not escape newline characters (`\n`) in object `.op` values. An attacker who controls a string passed to `concurrently`'s shell-quoting path can inject a newline and have the text after it interpreted as a separate shell command by the underlying shell. While `concurrently` is a devDependency used only for parallel script execution (e.g., running the Vite dev server and the analytics backend simultaneously via `npm run dev`), any CI pipeline or developer machine that executes concurrently with environment variables or arguments sourced from untrusted input is exposed. The installed version `1.8.3` is the last vulnerable version in the range `>=1.1.0 <=1.8.3`; the fix requires `shell-quote >=1.9.0`. Running `npm update concurrently` to pull a version of concurrently whose dependency tree includes `shell-quote >=1.9.0` resolves the transitive exposure. PROPOSAL: Run `npm update concurrently` to pull a fixed concurrently that depends on `shell-quote >=1.9.0`; commit the updated `package-lock.json` — L/L effort (~0 code change, one npm command; eliminates critical GHSA-w7jw-789q-3m8p shell-injection vector in the dev script runner).

- OBSERVATION: `node_modules/rollup@4.53.2` (dependency of `vite@6.4.1`, resolved transitively from `package.json:devDependencies.vite:"^6.2.0"`) — GHSA-mw96-cpmx-2vgc, **high** severity. Rollup 4.x in range `>=4.0.0 <4.59.0` has an Arbitrary File Write via Path Traversal in its plugin API: a crafted plugin output path can escape the intended output directory and write to arbitrary locations on the filesystem during `npm run build`. In a CI/CD pipeline (including the Docker build referenced in `geointellisense-analytics/Dockerfile`), this means a malicious or compromised rollup plugin — or crafted build input — could overwrite production artifacts, environment config files, or Docker layer contents during the frontend build step. The installed `rollup@4.53.2` is within the vulnerable range. This finding is distinct from and additive to the two existing vite CVEs in Active Recommendations (#8 — GHSA-p9ff-h696-f583 and GHSA-4w7w-66w2-5vf9); upgrading `vite` to `>=6.5.0` resolves all three simultaneously by pulling `rollup >=4.59.0`. PROPOSAL: Upgrade `vite` in `package.json:devDependencies` from `"^6.2.0"` to `"^6.5.0"` — L/L effort (~1 line in `package.json`; eliminates arbitrary-file-write risk in production builds via rollup GHSA-mw96-cpmx-2vgc, along with existing vite path-traversal CVEs from Active #8).

- OBSERVATION: `node_modules/picomatch@4.0.3` (transitive dependency of `vite@6.4.1`, `vitest@4.0.13`, and `tinyglobby`, each requiring `picomatch ^4.0.2` or `^4.0.3`) — GHSA-c2c7-rcm5-vvqj (**high**, CVSS 7.5, ReDoS via extglob quantifiers) + GHSA-3v7f-55p6-f55p (**moderate**, method injection via POSIX character classes causing incorrect glob matching). The ReDoS advisory: `picomatch`'s extglob quantifier parser (`+(...)`, `*(...)`, `@(...)`) contains a polynomial-time backtracking regex; a crafted glob pattern or file path with deeply nested extglob constructs causes the regex engine to hang indefinitely. In Vite's dev server, file-system watch events pass asset paths through `picomatch` for HMR routing; in Vitest, test file discovery uses `picomatch` for include/exclude pattern matching (`test: { include: [...] }` in `vite.config.ts:34`). A crafted file path in the project (e.g., an adversarially named asset or fixture file) can cause Vite's watcher or Vitest's runner to hang the CI pipeline. The installed `4.0.3` is the last vulnerable version; the fix is `>=4.0.4`. Upgrading `vite` to `>=6.5.0` and `vitest`/`@vitest/ui`/`@vitest/coverage-v8` to `>=4.1.0` (both already in Active Recommendations #6 and #8) resolves the picomatch ReDoS transitively at no additional cost. PROPOSAL: The picomatch ReDoS is fully resolved by the upgrades already proposed in Active Recommendations #6 (vitest ≥4.1.0) and #8 (vite ≥6.5.0) — no separate fix required; flagged here to document that the CI pipeline hang risk is an additional consequence of the pending dependency upgrades.

Every other production dependency uses a caret range (e.g., `"react": "^19.2.0"`, `"recharts": "^3.3.0"`). The `latest` dist-tag is a mutable server-side pointer on the npm registry: any time the `@googlemaps/markerclusterer` maintainers (or an attacker who compromises their npm account) publish a new version and tag it `latest`, all subsequent `npm install` executions — including Docker builds, CI pipelines, Vercel/cloud deployments, and new developer setups — will silently resolve to that version with no semver guard. The `markerclusterer` library is rendered directly in the browser map view (`AirQualityMapView.tsx`) and handles all city marker clustering; a malicious version could exfiltrate the Google Maps API key visible in the DOM, hijack map click events, or execute arbitrary JavaScript in every user's browser session. **Findings:**

- OBSERVATION: `hooks/useRealtimeAQI.ts:8` — The hook imports a domain type directly from a component: `import type { CityData } from '../components/3d/CityMarkers';`. `CityData` is defined as an interface at `components/3d/CityMarkers.tsx:20` alongside JSX rendering logic for the 3D city marker component. In a clean layered architecture, hooks are below components — hooks should not import anything from the `components/` tree. This upward dependency creates a bidirectional coupling: any refactor of `CityMarkers.tsx` (e.g., renaming or restructuring `CityData` as the 3D visualization evolves) propagates a breaking change into `useRealtimeAQI.ts`, which in turn can break every consumer of that hook. Because `CityData` (`{ id, name, lat, lng, aqi, category, pm25, temperature, humidity }`) is a pure domain-data interface with no JSX or visual dependencies, there is no technical reason for it to live inside a component file. PROPOSAL: Move the `CityData` interface from `components/3d/CityMarkers.tsx:20` to `types.ts` (which is already the designated home for shared domain types in this repo); update `useRealtimeAQI.ts:8` to `import type { CityData } from '../types'` and update the import inside `CityMarkers.tsx` similarly — L/L effort (~5 line change across 2 files; breaks the upward hook→component dependency, makes `CityData` a stable shared contract not coupled to the 3D visualization layer).

- OBSERVATION: `geointellisense-analytics/app/claude.py:103,116` and `geointellisense-analytics/app/routes/chat.py:7`, `grounded_search.py:7`, `grounded_maps.py:7`, `deep_analysis.py:7`, `predictive_analysis.py:8`, `low_latency.py:7`, `weather_forecast.py:8` — A logical circular dependency exists between `claude.py` and the route layer. Seven route files import from `claude.py` (e.g., `from app.claude import get_client, CHAT_SYSTEM, TOOLS, execute_tool`) making it the shared AI orchestration module. However, `claude.py` itself lazy-imports from a route module at lines 103 and 116: `from app.routes.fires import get_current_smoke_context`. The lazy import avoids Python's circular import error at module load time, but the logical cycle (routes → claude.py → routes.fires) persists. Concretely: if `fires.py` is renamed, split, or its `get_current_smoke_context()` function is moved to a background task, `claude.py`'s runtime import silently fails with an `ImportError` at the moment an AI tool call tries to include smoke context — an error that would not be caught by static analysis or tests that don't exercise that specific branch. The function `get_current_smoke_context()` at `fires.py:25` reads module-level state (`_smoke_context`) set by the route's polling loop, meaning `claude.py` is coupled to both the specific route module and its internal polling architecture. PROPOSAL: Extract a `geointellisense-analytics/app/stores/context_store.py` module with a simple `ContextStore` class holding `smoke_context`, `inversion_context`, and other live state fields; have `fires.py`'s polling loop call `context_store.set_smoke(...)` and have `claude.py` import from `context_store` instead of from `routes.fires` — M/M effort (~30 lines across new `context_store.py` + `fires.py` + `claude.py`; eliminates the logical cycle, decouples AI orchestration from route internals, makes polling state refactoring safe).

- OBSERVATION: `geointellisense-analytics/app/context.py:323,471` — The context builder (a utility module that constructs the live-data paragraph injected into Claude's system prompt) also lazy-imports from route modules: `from app.routes.fires import get_current_smoke_context` at line 323 and `from app.routes.inversion import get_current_inversion` at line 471. This means two non-route modules (`claude.py` and `context.py`) both reach into the `routes/` layer to read polling state. The pattern forces route modules to serve two distinct roles simultaneously: (1) HTTP request handlers via FastAPI routers and (2) live-state registries with module-level state accessors (`get_current_smoke_context`, `get_current_inversion`) exposed as non-HTTP exports. Any developer working on a route file must be aware that its internal polling state is consumed by external callers — a responsibility invisible from the route file itself and undocumented in any interface. The direction inversion is architecturally significant: utilities that aggregate data (context.py) depend on specific route implementations, so adding a new data source to the live context (e.g., traffic, pollen) requires modifying `context.py` to lazy-import from yet another route file, spreading the coupling further with each addition. PROPOSAL: Apply the same `ContextStore` fix as Finding 2: `fires.py` and `inversion.py` write to `context_store` on each poll cycle; `context.py` reads from `context_store` instead of lazy-importing route modules — M/M effort (covered by the same `context_store.py` module; eliminates both upward dependencies from utility layer to routes, makes adding new live-data sources a single-file change in `context_store.py`).

PROPOSAL: Move `LocationKey` and location constants (`locations`, `cityLocations`) to `types.ts` so they are importable without depending on the data module; expose `dashboardData` access only through `dataService.ts` (which already has the fallback logic) — M/M effort (~20 lines: type moves to `types.ts`, component imports updated; reduces the blast radius of `dashboardData` structure changes from 7 files to 1).

### Run #256 — 2026-06-10 — Lens: Type safety
**Scope:** Eighteenth type-safety pass. Files examined: `components/charts/AQITrendChart.tsx`, `components/charts/PM25TrendChart.tsx`, `components/charts/WeatherForecastChart.tsx`, `components/charts/TemperaturePrecipitationChart.tsx`, `hooks/useDashboardData.ts`, `services/dataService.ts`, `services/WeatherService.ts`, `components/AccessibleChart.tsx`. Grep for `: any`, `as any`, `Record<string, any>`, `response.json() as`, `JSON.parse.*as` across all `.ts` and `.tsx` files. Cross-checked against Active Recommendations and archived type-safety runs #1, 16, 31, 46, 61, 76, 91, 106, 121, 136, 151, 166, 181, 196, 211, 226, 241.

**Findings:**

- OBSERVATION: `components/charts/AQITrendChart.tsx:15`, `components/charts/PM25TrendChart.tsx:15`, `components/charts/WeatherForecastChart.tsx:14`, `components/charts/TemperaturePrecipitationChart.tsx:15` — All four Recharts wrapper components in `components/charts/` declare their `data` prop as `any[]` in their props interfaces. Each component uses `<Line dataKey="…">` or `<Bar dataKey="…">` with hardcoded string literals. Because `data` is `any[]`, TypeScript cannot verify at compile time that those `dataKey` strings correspond to actual properties on the data objects. The data flowing into these charts is constructed via the `result: any[]` / `entry: any` pattern in `useDashboardData.ts` (lines 197–199, 241–243, 285–287, 330–332), which also loses all type information. The combined effect is a fully `any`-typed pipeline from data construction through to chart rendering: if a field name in the data builder is renamed (e.g., `${loc}_aqi` → `${loc}_aqiValue`), the chart silently renders an empty series at runtime with no compile-time error. PROPOSAL: Define a concrete row type for each chart (e.g., `type AQIChartRow = { month: string } & { [K: string]: number }`) and replace `data: any[]` with the concrete type in each chart's props interface; similarly replace `result: any[]` / `entry: any` in `useDashboardData.ts` with the same concrete row type — L/L effort (~20 lines across 4 chart files + `useDashboardData.ts`; enables compile-time detection of field-name mismatches between data builders and chart `dataKey` strings).

- OBSERVATION: `hooks/useDashboardData.ts:179,223,267,311` — Four parallel data-aggregation `useMemo` blocks (humidity trends, wind speed trends, AQI monthly means, temperature monthly means) each iterate `locEntry.dailyForecast.forEach((day: any) => {…})`. The `dailyForecast` property on each location entry has a structurally defined shape in the dashboard data (it comes from typed source data in `data/`), but the forEach callback parameter is explicitly typed as `any`, bypassing field-level type checking inside the entire callback. Immediately after each forEach, results are accumulated into `const result: any[]` / `const entry: any = { month }` (lines 197–199, 241–243, 285–287, 330–332) — four repetitions of the same `any`-chain pattern in one file. If `dailyForecast` items' fields are renamed (e.g., `day.humidity` → `day.relativeHumidity`), each callback silently reads `undefined` and produces NaN chart data with no compile-time warning. PROPOSAL: Look up the inferred type of `locEntry.dailyForecast[number]` (inferrable from the typed `dashboardData` structure in `data/`) and replace each `(day: any)` with the concrete inferred type; replace each `result: any[]` + `entry: any` with a typed row interface — L/L effort (~8 targeted substitutions in `useDashboardData.ts`; eliminates 8 `any` usages in one file, closes the channel through which dashboard data field renames produce silent NaN chart data).

- OBSERVATION: `services/dataService.ts:206,228` and `services/WeatherService.ts:103` — Three `response.json() as T` casts are silently unsound: `response.json()` is typed `Promise<any>` in the Fetch API's `lib.dom.d.ts`. Casting `any → ConcreteType` with `as` does not constitute type narrowing — TypeScript accepts it unconditionally regardless of actual runtime shape, because `any` is both a top and bottom type. Concretely: if the analytics service at `GET /historical-aqi` renames `aqi` to `aqiValue`, `dataService.ts:206`'s cast (`await response.json() as HistoricalAQIRecord[]`) still compiles, and all downstream code reading `.aqi` receives `undefined` silently. The same applies to `GET /historical-weather` at `dataService.ts:228` and the forecast response at `WeatherService.ts:103`. This pattern also directly amplifies the TS ↔ Python contract drift risk that prior audit runs have documented: the TypeScript side has no guard that would fire when the Python analytics response shape diverges. PROPOSAL: Treat `response.json()` as `unknown` (via `const raw: unknown = await response.json()`) and add minimal type guards or Zod/Valibot schema parse at each call site in `dataService.ts:206,228` and `WeatherService.ts:103`; throw an explicit error if validation fails — M/M effort (~15 lines across the 3 call sites plus 2–3 schema definitions; converts silent `undefined` field-access bugs into explicit boundary errors, provides a type-safety backstop for TS ↔ Python schema drift).

- OBSERVATION: `components/AccessibleChart.tsx:66,79` — The `AccessibleChart` component provides a screen-reader-friendly data table alternative for all dashboard charts. Its public props interface contains two `any`-typed entries: `format?: (value: any) => string` (line 66, the column value formatter) and `data: Record<string, any>[]` (line 79, the table rows). The `DataTableColumn` type has a `key: string` field used at runtime as `row[column.key]` inside the table renderer. Because `data` is `Record<string, any>[]` rather than a generic parameter, TypeScript does not enforce that `DataTableColumn.key` values match actual fields of the data objects. A misspelled column key (e.g., `"pm2_5"` instead of `"pm25"`) will silently render `undefined` in accessible table cells — an invisible a11y regression that sighted users testing the visual chart would never notice. Given that `AccessibleChart` is a reusable wrapper consumed by every chart in the dashboard, this gap affects the entire accessible table surface. PROPOSAL: Make `AccessibleChart` generic over its row type: `interface AccessibleChartProps<T extends Record<string, unknown>>` with `data: T[]`, `DataTableColumn<T>` typed as `{ key: keyof T & string; … }`, and `format: (value: T[keyof T]) => string` — M/L effort (~15 lines in `AccessibleChart.tsx`; constrains column keys to actual data fields at compile time, preventing silent `undefined` cells in the accessible table for every chart in the dashboard).

**Proposed actions:**
- Define concrete row types for each chart in `components/charts/`; replace `data: any[]` with typed arrays — L/L effort (~20 lines; enables compile-time field-name checking for Recharts `dataKey` strings)
- Replace `(day: any)` + `result: any[]` + `entry: any` patterns at `useDashboardData.ts:179,197,223,241,267,285,311,330` with inferred concrete types — L/L effort (~8 changes; closes `any`-chain for all 4 dashboard data-aggregation functions)
- Add `unknown` + type-guard or Zod parse for `response.json()` in `dataService.ts:206,228` and `WeatherService.ts:103` — M/M effort (~15 lines; converts silent schema-drift bugs into explicit boundary errors)
- Make `AccessibleChart` generic on its row type; constrain `DataTableColumn.key` to `keyof T` — M/L effort (~15 lines in `AccessibleChart.tsx`; prevents silent `undefined` in accessible table cells)
